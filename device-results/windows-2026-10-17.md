- A "home" Pending server (no box) now shows on Home and can't be cancelled. Not cleaned up; needs a `.com` side look at routing rows for `home.<account>` and `home2.<account>`.
- Code reading: `CreateServerScreen.mintAndRegister()` -> `mintRecipeBundle` generates a random `Ed25519Sign.KeyPair.newKeyPair()` RCK per mint (CreateServerScreen.kt ~line 1359) and `D1RoutingStorage.register` (packages/storage/src/d1.ts:690) refuses any second RCK for the same subdomain. So any second mint for one name (a retry, a reconnect after the builder socket dropped, a re-tap) 409s, and the first registration is orphaned. Suggest: derive the RCK from the account root + subdomain (or reuse the pending order's RCK on retry), and let Cancel order release a name whose recipe was never delivered.

## Hosted VM on Windows: root causes found (2026-10-18)
Two bugs in the "Host on this PC" path, found with QMP screendumps and the guest's serial console (`serialConsoleEnabled` in the VM's config.json, then attach to the chardev port):

1. **Studio (Windows) ignores `FLAGSHIP_CONTROL_HOST` for the install-status and health polls** (`VMManager.cs:672`, `VMServerHealth.cs:36` hard-coded `flagshipserver.com`). Against any other control plane the UI sat on "Waiting for the first guest checkpoint" even though the guest was reporting. Fixed on branch `fix/appliance-resize-key` (commit f68d8d9bc). Prod users are unaffected; matters for the gym and for any self-hosted control plane.
2. **The prebuilt appliance's first-boot specializer dies at "Expanding the disk"** (`packages/flagship-builder/src/appliance.ts`): `cryptsetup resize` was run without `--key-file`, so it asked for a passphrase on stdin ("Nothing to read on input") and the service exited rc=1. Every hosted VM on the published appliance (amd64, 2026-10-13) would stop at its login prompt. The Mac path never hit it (different mapper state). Fix: pass `/etc/flagship/appliance-build.key`, and let `growpart` NOCHANGE (rc 1) pass so a retry works (commit b3722ee65). Verified on a CI-built image: `EXT4-fs (dm-0): resized filesystem to 16445179`, then "cloned disk expansion complete".
3. **Next failure (specializer still stops, now one step later):** `Setup stopped while Setting up this server's identity and disk key (line 78)`. Root cause of the *reporting* is that `set +e` does not stop an ERR trap, so the bootstrap's exit code was never handled and its own FATAL line never reported. Fixed (commit on the same branch). What the bootstrap actually failed on is not yet known; hypothesis: gym control plane needs the gym CA chain (`.maintainers`, only on branch `gym`), so a `main` image can't verify a gym recipe. Building `fix/appliance-gym` (= origin/gym + the two fixes) to test.
