## Failures

### Failure 1 (R, blocks every prebuilt-appliance host on every Studio): the published 0.3 appliance can't specialize
- Symptom: `[flagship-bootstrap] FATAL: appliance release  does not match signed recipe commit 52c67f88...` ~2 min into first boot; the appliance commit read is the empty string.
- Cause (code reading, 1e1840f2c): the appliance factory installs the signed release with `install-box-artifact.sh`, which writes `/var/flagship/artifact-current.json` (`.commit`) and `artifact-sequence`; the generalize step then runs `rm -rf /var/flagship/*` (`packages/flagship-builder/src/appliance.ts:321`). The first-boot bootstrap under `FLAGSHIP_APPLIANCE_PREINSTALLED=1` reads `jq -r .commit /var/flagship/artifact-current.json` (`packages/flagship-builder/src/userdata.ts:701-702`) and gets "".
- When: the check came with the 0.3 security commit `cc5425c8a` (2026-10-23); the wipe has been in the factory since `fe16fc3c6` (2026-07-21). So every 0.3 appliance is affected, including both published 2026-11-05 images (amd64 `ecd620cb`, arm64 `08514894`, bake 52c67f88): Mac, Windows and Linux Studio "Host on this PC" on production all fail for 0.3 recipes. `vm-appliance.yml`'s boot smoke doesn't run a real recipe through the specializer, so CI couldn't see it.
- Suggested fix (release manager): keep the release record through generalization (e.g. exclude `artifact-current.json`/`artifact-sequence` from the wipe, or have the bootstrap read `/opt/flagship-releases/<commit>/INSTALLED.json` / `BUILD-INFO.json` through the `/opt/flagship` link), add a specializer test with a real seed, rebuild + republish both appliances. Workaround until then: `FLAGSHIP_VM_FORCE_ISO=1` (W8).
- Evidence: Studio log lines (verified appliance sha256, prebuilt disk created, both checkpoints, the FATAL line); VM folder kept at `%LOCALAPPDATA%\FlagshipBuilder\VMs\<server>` (config, 197 KB overlay, seed).

### Failure 2 (R, blocks the installer-ISO path, Save installer and USB burn on every Windows PC without MSYS2): the bundled xorriso can't open Studio's paths
- Symptom: after the Debian ISO downloads, "Create server on this PC" does nothing on screen; the log shows `no Debian boot config found` (stderr). No VM, no error sentence.
- Cause (reproduced by hand with the zip's own `tools\xorriso.exe`, 1.5.8-1): `NativeIsoRemaster.ToXorrisoDiskPath` turns `C:\...` into `/c/...`. That form only resolves under a full MSYS2 install, whose `/etc/fstab` sets the cygdrive prefix to `/`. The bundled copy ships the MSYS DLLs but no `/etc/fstab`, so its prefix is the default `/cygdrive`: `-indev /c/Users/.../flagship-base-debian-13.6.0.iso` fails with `libburn : SORRY : Neither stdio-path nor its directory exist` / `Cannot acquire drive`, every `-extract` is skipped, and `DebianIso` throws "no Debian boot config found" (`apps/builder-windows/src/NativeIsoRemaster.cs`). The same call with `/cygdrive/c/...` extracts `grub.cfg` at once. `ResolveXorriso` prefers the bundled `tools\xorriso.exe` over `C:\msys64`, so even a PC with MSYS2 uses the broken one.
- History: the 2026-10-17 round fixed the path form against MSYS2's own xorriso (`docs/coordination/desktop-windows.md:66`); the bundled copy came later, and the earlier rounds list "installer-ISO fallback, USB burn" as not yet run on Windows.
- Impact: the hosted-VM fallback (FORCE_ISO, and any recipe with no matching appliance), Save installer (W16) and Burn to USB (W15) all remaster through this. Together with Failure 1, Windows Studio cannot create a server on production at all.
- Suggested fix: pass `/cygdrive/c/...` to the bundled tool (or ship an `etc/fstab` beside it: `none / cygdrive binary,posix=0,noacl,user 0 0`), keep `/c/...` only for an MSYS2 xorriso; show a remaster failure as a sentence on screen; add a Windows CI test that remasters a small ISO with the zip's own `tools\xorriso.exe`.
- Second defect behind the first: with `FLAGSHIP_XORRISO=C:\msys64\usr\bin\xorriso.exe` (MSYS2's own copy, which reads `/c/...`), the extract works, but xorriso gives the extracted `cfg0` the ISO's mode `r--r--r--` (Windows `ReadOnly`), and `DebianIso`'s `File.WriteAllTextAsync` over it fails: `Access to the path 'C:\Users\<user>\AppData\Local\Temp\flagship-remaster-<id>\cfg0' is denied.` (log drawer only, nothing on screen). So the remaster can't work on any Windows PC, MSYS2 or not. Fix: clear the ReadOnly attribute (or write to a new file) before editing each extracted config; the test above should edit and rebuild, not just extract. The failed attempts also leave their `%TEMP%\flagship-remaster-*` folders behind.
- No workaround short of a code change, so W8, W15 and W16 can't pass with this build, and the rows that need a running Windows-hosted server (W9, W10, W11, W13, W14, W17) are blocked until Failure 1 or Failure 2 is fixed.

### Failure 3 (R): a recipe that doesn't load says nothing
- Symptom: on the start screen ("Pair your phone to begin … Or provide a server recipe"), Paste from clipboard with plain text, a blank clipboard, or a production recipe in a gym-pointed Studio changes nothing: no sentence on screen, nothing in the log.
- Cause (code reading): `Wizard.AcceptRecipeText`/`RunVerifyAsync` put the error in `RecipeError` (also the "This recipe was made by an older version of the Flagship app …" refusal from `OlderAppRecipe.Refusal`), but the start screen shows no recipe row, so the sentence never appears. Not checked: Load from file (same `AcceptRecipeFile`, so very likely the same).
- Impact: W5's required sentence can't appear, so W5 fails as built; a user with a stale or wrong recipe sees a button that does nothing.
- Suggested fix: show `RecipeError` on the start screen (under the two buttons) and add a UI test that pastes junk and an old-app recipe.

### Failure 4 (R for W18; not Studio): a phone's key file can't sign the webapp in
- Symptom: the webapp's "Import a key file" with a `.flagshipkey` just exported by the Android app (debug build of the release pin, account created on it the same day) fails with `re-pair initiate failed (403): {"error":"oldIrkPub does not match the current registered IRK"}` (a raw toast for about a second); the browser is left half signed in (Edge) or back at first run (Chrome), and polls `read-token` (403) and `stream`/`pods` (401).
- Cause (partly code reading): `apps/web/public/webapp/lib/keyfileImportTakeover.js` takes the "old" IRK as the v1 IRK derived from the recovered seed (`deriveIrkFromSeed`) and starts a re-pair; `.com` holds a different IRK for this account, so an account made on Android 0.3 does not register the seed's v1 IRK. Not checked: which key Android registers, and whether Android's or iOS's own key-file import works for such an account. Since key-file import is the recovery path (it rotates the other devices out), a user restoring from their key-file backup in a browser would be refused.
- Also: this PC has no camera, and the phone's Add a device has no text code or link, so a browser on a camera-less computer can't join an account at all.
- Suggested next step: check the IRK an Android-created account registers against `deriveIrkFromSeed(seed)`, add a cross-client key-file vector (Android export → webapp import), and show the refusal as a sentence.
