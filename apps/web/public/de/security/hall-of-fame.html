Ein alter Link der Browser-Fernbedienung konnte die Web-App mit einem fremden Server verbinden

Mittel · gemeldet und behoben im November 2026 · Fix 1f37c6c6 · Dank an: Huzaifa Jawaid

Die Web-App nahm noch einen alten Startlink für die Browser-Fernbedienung an. Er löste eine Sitzung bei dem Server ein, den der Link nannte, und speicherte den Server, den die Antwort nannte, ohne zu prüfen, ob einer von beiden zur Dienstdomain von Flagship gehörte. Ein präparierter Link konnte eine Sitzung für den Server eines Angreifers einrichten.

Der alte Link ist entfernt: Die Browser-Fernbedienung startet jetzt nur noch über den QR-Code, den das Telefon bestätigt, und jede Sitzungsantwort muss einen Server unter der Dienstdomain von Flagship nennen. Der Fix ist in Web-App-Version 260 enthalten.

Gleichzeitige Zuteilungen konnten das Platzlimit einer Organisation überschreiten

Niedrig · gemeldet und behoben im November 2026 · Fix 4fa472d9 · Dank an: Huzaifa Jawaid

Platzzuteilungen oder Einladungen, die im selben Moment gesendet wurden, konnten jeweils das Platzlimit des Tarifs passieren und einer Organisation so zusammen mehr Plätze geben, als ihr Tarif erlaubte. Außerdem wurde eine Zuteilung protokolliert, selbst wenn nichts gespeichert worden war.

Das Limit wird jetzt im selben Schreibvorgang gehalten, der die Zuteilung speichert, und der Protokolleintrag wird erst geschrieben, wenn dieser Schreibvorgang gelungen ist.

Gleichzeitige Freigabeangebote konnten das Limit für Mitverwaltende überschreiten

Niedrig · gemeldet und behoben im November 2026 · Fix 25a97cc5 · Dank an: Huzaifa Jawaid

Beim Teilen eines Servers konnten Anfragen, die im selben Moment gesendet wurden, jeweils das Limit des Tarifs für Mitverwaltende passieren, und das Limit zählte nur die neuesten 500 Freigaben.

Die Zählung umfasst jetzt jede aktive Freigabe und wird im selben Schreibvorgang gehalten, der die Freigabe anlegt.

Gleichzeitige Anfragen konnten mehr Peer-Backup-Tokens erhalten als erlaubt

Niedrig · gemeldet und behoben im November 2026 · Fix 79ca995e · Dank an: Huzaifa Jawaid

Jeder Server darf nur eine begrenzte Zahl von Peer-Backup-Tokens erhalten. Zwei Anfragen im selben Moment konnten jeweils dieses Limit passieren und zusammen mehr Tokens bekommen, als es erlaubte.

Das Limit wird jetzt in einem einzigen Schreibvorgang gezählt und reserviert, bevor irgendetwas signiert wird.

Die Gründungsperson einer Organisation konnte eine Mitteilung zur Gründerentfernung oder Wiederherstellung rückdatieren

Mittel · gemeldet und behoben im November 2026 · Fix 6dd5a89b · Dank an: Huzaifa Jawaid

Eine Mitteilung zur Entfernung der Gründungsperson oder zur Kontowiederherstellung einer Organisation nahm ihre Wartefrist von einem Datum, das die Anfrage selbst angab. So konnte die Gründungsperson sie rückdatieren und sowohl die Wartefrist als auch die Möglichkeit der anderen Admins zum Widerspruch überspringen. Die Lücke war ungenutzt: Keine App und kein Server sandte solche Anfragen.

Unser Server lehnt beide Arten von Änderung jetzt ab, bis die nächste Version die eigentliche Lösung bringt, bei der die Wartefrist beginnt, wenn unser Server die Mitteilung sieht.

Unbenutzte Server-Registrierungscodes waren für jeden lesbar, der die ID einer Organisation kannte

Mittel · gemeldet und behoben im November 2026 · Fix e5197fd9 · Dank an: Huzaifa Jawaid

Der Export einer Organisation und ihre Liste der Zeremonien konnten noch unbenutzte Server-Registrierungscodes an jeden herausgeben, der die ID der Organisation kannte, und ein Code allein reichte, um einen beliebigen Schlüssel als Server dieser Organisation zu registrieren. In der Produktion gab es keine solchen Codes, also wurde nichts offengelegt.

Der Export enthält jetzt nur Codes, die bereits benutzt wurden, und ein Code kann nicht mehr als Zeremonie eingereicht werden. Die Bindung jedes Codes an den eigenen Schlüssel des echten Servers folgt in der nächsten Version.

Über das Schwachstellen-Formular gesendete Meldungen gingen verloren

Niedrig · gemeldet und behoben im November 2026 · Fix 7221dfb1 · Dank an: Huzaifa Jawaid

Das Meldeformular auf unserer Sicherheitsseite schickte jede Meldung an eine Adresse, auf die unser Server nicht mehr antwortete. Alle über das Formular gesendeten Meldungen gingen verloren, und die meldende Person sah einen Fehler. Meldungen per E-Mail waren nicht betroffen, und nichts wurde offengelegt.

Das Formular funktioniert wieder. Jede Meldung wird beim Eingang mit unserem Sicherheitsschlüssel verschlüsselt, sodass unser Server sie nur in einer Form speichert, die allein die Inhaber des Schlüssels lesen können, und die meldende Person erhält eine Referenz. Wir werden über jede neue Meldung benachrichtigt, und die Seite behält die E-Mail-Adresse und den Schlüssel als Ausweichweg.

Nach diesem Fix lehnte das Formular dennoch jede aus einem Browser gesendete Meldung ab, sobald seine Spam-Prüfung eingeschaltet war, weil die Prüfung ein Feld hinzufügte, das unser Server nicht erwartete. Auch das fand Huzaifa Jawaid; behoben in 309516e9.

Signaturprüfungen akzeptierten drei öffentliche Schlüssel niedriger Ordnung, sodass eine gefälschte Signatur unter ihnen gültig sein konnte

Niedrig · gemeldet und behoben im November 2026 · Fix 8fd77a2b · Dank an: Atharva Savji Lokhande

Unsere Signaturprüfungen lehnten die meisten Ed25519-Schlüssel kleiner Ordnung anhand einer festen Liste ab, doch der Liste fehlten drei davon, und die Prüfungen akzeptierten auch Schlüssel in nicht kanonischer Schreibweise. Unter einem solchen Schlüssel kann jeder eine Signatur fälschen, die für jede beliebige Nachricht gültig ist, sodass eine Signatur darunter nichts beweist. Keine App sendet einen solchen Schlüssel, und eine Prüfung unserer Produktionsdaten fand keinen gespeicherten.

Jeder Schlüssel wird jetzt nach den strengen Regeln des Standards dekodiert, und Schlüssel kleiner Ordnung sowie nicht kanonische Schlüssel werden abgelehnt, bevor irgendeine Signatur geprüft wird. Unser Server lehnt sie überall ab, wo er einen Schlüssel speichert oder für ihn bürgt, und Server lehnen sie als Schlüssel von Freigabemitgliedern ab.

Ein ungenutzter Identitäts-Endpoint vertraute den Signierern, die jede Anfrage selbst nannte

Mittel · gemeldet und behoben im November 2026 · Fix caf3ce88 · Dank an: rakimans

Ein Endpoint aus der frühen Entwicklung speicherte einen signierten Eintrag unter einem Hash eines Kontonamens. Er prüfte die Signatur des Eintrags nur gegen die Schlüssel, die dieselbe anonyme Anfrage als erlaubte Signierer angab, und dieser Hash lässt sich aus jedem öffentlichen Namen berechnen. Jeder konnte für jeden Namen einen Eintrag anlegen, ihn ersetzen oder mit einer sehr hohen Versionsnummer sperren.

Keine App hat diese Einträge je gelesen oder geschrieben: Das Kontoverzeichnis, verschlüsselt und von den Geräten des Kontos signiert, enthält, was sie enthalten sollten. Keine Kontodaten und keine Schlüssel lagen offen. Da nichts den Endpoint nutzte, haben wir ihn samt Speicher und den darin liegenden Einträgen entfernt, statt ihn zu flicken.

Der Wiederherstellungsstatus eines Kontos war öffentlich, und eine abgebrochene Wiederherstellung ließ sich durch Wiederholen neu starten

Niedrig · gemeldet und behoben im November 2026 · Fix ce51f35f · Nennung wartet auf den Wunsch der meldenden Person

Wenn ein neues Gerät ein Konto wiederherstellt, sehen die anderen Geräte und Server des Kontos die anstehende Änderung, bevor sie wirksam wird. Dieser Eintrag war für jeden lesbar, der den Kontonamen kannte, einschließlich der vollständigen signierten Anfrage, die ihn ausgelöst hatte. Da die Anfrage fünf Minuten gültig blieb, konnte jeder, der sie gelesen hatte, sie nach dem Abbruch der Wiederherstellung erneut senden und sie so wieder starten.

Übernehmen ließ sich ein Konto so nicht: Nur wer den Schlüssel des neuen Geräts hat, kann eine Wiederherstellung abschließen, und der Inhaber wurde über jeden Versuch benachrichtigt. Den anstehenden Eintrag können jetzt nur die eigenen Geräte und Server des Kontos lesen, jede Anfrage wird nur einmal angenommen, und eine Anfrage mit einem Datum vor einem Abbruch wird abgelehnt.

Gleichzeitige Einlösungen ließen eine Einmal-Einladung mehr Personen aufnehmen als erlaubt

Mittel · gemeldet und behoben im November 2026 · Fix 14329ad6 und 91b992f4 · Nennung wartet auf den Wunsch der meldenden Person

Eine Einladung zu einer App kann auf eine Person oder eine feste Anzahl begrenzt sein. Unser Server zählte die bereits Aufgenommenen und fügte dann die neue Person hinzu, in zwei getrennten Schritten; viele gleichzeitig gesendete Einlösungen desselben Links konnten daher alle die Zählung passieren. Auch die Server, auf denen die App läuft, hielten das Limit nicht selbst ein, und läuft eine App auf mehreren Servern, wurden Personen, die ein Server abgelehnt hatte, später auf einem anderen aufgenommen.

Jeder Weg brauchte den Einladungslink selbst. Zählen und Hinzufügen sind jetzt ein Schritt, das Einlösen von Einladungen ist in der Rate begrenzt, und jeder Server hält das Limit einer Einladung ein und nimmt dieselben ersten Personen auf wie die anderen Server der App, ab dem nächsten Update des jeweiligen Servers. Testeinladungen, die in der Produktion über ihrem Limit lagen, wurden widerrufen.

Review-Notizen: eine veränderliche Installationsreferenz, Manipulation beim Start und der App-Browser

Design-Review · Oktober 2026 · behoben in Version 0.3 · Dank an: Jay

Jay hat uns drei Beobachtungen aus dem Lesen des Codes geschickt. Keine kam mit einem funktionierenden Exploit, aber jede zeigte auf eine echte Lücke, und zwei davon haben verändert, was Version 0.3 ausliefert.

Das signierte Installationsrezept nannte einen Branch, keinen Commit. Das Telefon signiert das Rezept, von dem ein neuer Server installiert, aber die darin genannte Revision war standardmäßig main, und das kann sich ändern: Die Signatur legte einen Namen fest, nicht den Code dahinter. Neue Server installieren jetzt ein signiertes Release für genau einen Commit (einen 40-stelligen Hex-SHA), geprüft, bevor irgendetwas läuft.

Die Browser-Freigabe einer App reichte über ihre Website-Liste hinaus. Die Liste wurde beim Öffnen eines Tabs oder beim Navigieren geprüft, nicht bei späteren Klicks, Eingaben oder Lesezugriffen, und alle Apps teilten sich ein Browserprofil. Version 0.3 ersetzt das: Jede App bekommt ihren eigenen Browser-Kontext, jede Anfrage wird so, wie der Browser sie sieht, gegen die Liste der App geprüft, und die aktuelle Adresse wird vor und nach jeder Aktion geprüft, sonst wird der Tab geschlossen und nichts zurückgegeben.

Physischer Zugriff auf einen ausgeschalteten Server. Die Boot-Partition ist nicht verschlüsselt und wird nicht gemessen, sodass jemand mit ein paar Minuten allein an der Maschine den frühen Startcode ändern und den Festplattenschlüssel beim nächsten Entsperren abgreifen könnte, auch bei Freigabe per Telefon. Das gilt heute. Wir beschreiben die Freigabe per Telefon und die Fernsperre nicht mehr als Schutz dagegen, und Measured Boot (TPM) ist geplant.

Nicht authentifizierter Austausch des Identitätsschlüssels bei einem Konto ohne zweiten Faktor

Kritisch · gemeldet und behoben im Oktober 2026 · Fix 7d49a444 · Nennung wartet auf den Wunsch der meldenden Person

Die Kontowiederherstellung plant den Austausch des Root-Identitätsschlüssels eines Kontos. Der Endpunkt, der sie startet, prüfte die Anfrage gegen den neuen Schlüssel, also eine Selbstbehauptung, und seine einzige andere Eingabe, den aktuellen Identitätsschlüssel des Kontos, liefert die öffentliche Benutzernamensuche an jeden aus. Bei einem Konto ohne eingerichteten zweiten Faktor blieb damit nichts, was ein Fremder nicht liefern konnte: Ein öffentlicher Name genügte, um einen feindlichen Schlüsseltausch zu planen, der nach Ablauf der Schonfrist wirksam wurde.

Entgegen unserer eigenen Dokumentation gab es auch kein Veto des Inhabers. Der Einspruchs-Endpunkt wird mit dem neuen Schlüssel signiert, ist also das eigene Rückgängigmachen der wiederherstellenden Person und nichts, was der verdrängte Inhaber nutzen kann. Die Schonfrist war eine Benachrichtigungsfrist, keine Bremse.

Eine Wiederherstellung zu starten erfordert jetzt ein eingerichtetes Anmeldemerkmal: einen TOTP- oder Wiederherstellungscode, den kurzlebigen Nachweis aus dem passphrasegeschützten Abruf des verpackten Schlüssels oder eine Signatur des aktuell registrierten Schlüssels des Kontos. Ein Konto ohne Anmeldemerkmal kann niemand wiederherstellen, so wie es unsere Richtlinie zu Namen und Wiederherstellung immer gesagt hat. Eine Wiederherstellung abzuschließen erfordert jetzt eine Signatur des zu installierenden Schlüssels, wo es vorher ein nicht authentifizierter POST war. Derselbe Durchgang hat einen verwandten Fehler behoben, der uns nicht gemeldet worden war: Ohne seinen Schlüssel fiel der Server auf eine reine Strukturprüfung der TOTP-Codes zurück, sodass der zweite Faktor gerade bei den Konten, die einen eingerichtet hatten, eine Formsache war.

Nicht authentifiziertes CA-Signaturorakel stellt einen Relay-Hub-Segen für beliebige Schlüssel oder Hosts aus

Kritisch · gemeldet und behoben im Oktober 2026 · Fix 54889a4c, Härtung 484ef162 und 771db538 · Nennung wartet auf den Wunsch der meldenden Person

Der Endpunkt, der Relay-Hub-Segen ausstellt, authentifizierte seinen Aufrufer nicht, sodass jeder einen gültig signierten Segen für Schlüssel und Host seiner Wahl erhalten konnte: ein Signaturorakel gegen die Vertrauenskette, mit der eine Box entscheidet, ob der Hub vor ihr der echte ist.

Der Aussteller ist jetzt authentifiziert, und Segen sind an den erwarteten Apex gebunden. Zwei Folgeänderungen härten die Box-Seite statt der Lücke selbst: Eine Box schlägt geschlossen fehl, wenn der Hub keinen Segen vorlegt, und verlangt den erwarteten Apex, und die Vertrauenssperre schließt jetzt auch bereits offene Verbindungen, statt nur neue abzulehnen.

Kostenlose Umbenennung des Benutzernamens umging die kostenpflichtige Namensänderung und die Liste reservierter Namen

Mittel · gemeldet und behoben im Oktober 2026 · Fix b3d6852b, Härtung c4132973 · Nennung wartet auf den Wunsch der meldenden Person

Neue Konten können nur einen vom Server vorgeschlagenen Namen nehmen, und einen eigenen Namen zu wählen soll die kostenpflichtige Namensänderung sein; die Gebühr verhindert, dass begehrte Namen gehortet werden. Ein alter Umbenennungs-Endpunkt aus der frühen Entwicklung war noch aktiv und setzte nichts davon durch. Er prüfte nur die eigene Signatur des Kontos, sodass jeder Kontoinhaber zu einem Namen seiner Wahl wechseln konnte, kostenlos und so oft er wollte, auch zu Namen, die wir für unsere eigene Infrastruktur reservieren. Da Namen nie zurückgenommen werden, wäre jede solche Vergabe dauerhaft gewesen.

Daten oder Schlüssel anderer Konten wurden nicht offengelegt, und ein gehorteter reservierter Name ließ sich nicht nutzen: Die Registrierung eines Servers prüft den Namen erneut, sodass keiner DNS-Einträge oder ein Zertifikat bekommen konnte. Keine App hat den Endpunkt je aufgerufen, also haben wir ihn entfernt statt ihn zu flicken. Die kostenpflichtige Namensänderung wird ein eigener, neuer Endpunkt, der diese Prüfungen von Anfang an hat. Neben dem Test der meldenden Person fanden wir eine frühere Umbenennung in der Produktion, auf einen reservierten Namen der Testumgebung; beide Vergaben wurden rückgängig gemacht.

Eine zweite Prüfung des Fixes fand zwei Stellen, an denen er sich darauf verließ, dass etwas anderes stimmt, und beide sind jetzt geschlossen. Unser Edge-Server leitet jede API-Anfrage, die er nicht kennt, an das Backend weiter, sodass der entfernte Endpunkt nur deshalb mit „nicht gefunden“ antwortete, weil auch das Backend ihn nicht mehr hatte; die Edge lehnt ihn jetzt direkt ab, in jeder Schreibweise, und ein Test beweist, dass eine solche Anfrage nie das Backend oder die Datenbank erreicht. Außerdem löscht unser Compiler nie die Ausgabe einer entfernten Quelldatei, sodass der kompilierte Code des alten Handlers noch im lokalen Build-Verzeichnis lag. Er war nie Teil des bereitgestellten Dienstes, da nichts ihn geladen hat, aber jedes Deployment baut jetzt aus einem leeren Verzeichnis neu und verweigert die Auslieferung von kompiliertem Code ohne Quelle.

Die Web-App und die Browser-Fernbedienung konnten von einer anderen Website eingerahmt werden

Niedrig · gemeldet und behoben im Oktober 2026 · Fix d0658fb6 · Nennung wartet auf den Wunsch der meldenden Person

Die Web-App, die Browser-Fernbedienung und diese Website sendeten nichts, was einem Browser sagte, sie nicht im Frame einer anderen Website anzuzeigen. Eine feindliche Seite konnte sie unsichtbar laden und eigene Schaltflächen darüberlegen, sodass ein Klick, der für die feindliche Seite gedacht war, auf unserer landete (Clickjacking).

Die Reichweite war begrenzt. Eine eingerahmte Kopie startet abgemeldet: Browser geben einem Frame in einer anderen Website seinen eigenen Speicher, er sieht also nie die Schlüssel der echten Sitzung, und Passkey- und Face ID-Abfragen erscheinen über jeder Seite, wo ein Overlay sie nicht erreicht. Relevant war der Fall der Browser-Fernbedienung. Wer ihren Code scannte und sie mit dem Telefon genehmigte, während sie in einer feindlichen Seite steckte, hinterließ eine genehmigte Sitzung in diesem Frame, wo darübergelegte Schaltflächen die Klicks lenken konnten.

Jede Antwort von flagshipserver.com und seinen Subdomains verweigert jetzt das Einrahmen (frame-ancestors 'none' und X-Frame-Options: DENY), und die Web-App weigert sich außerdem, in einem Frame zu starten, falls sie je ohne diese Header ausgeliefert wird. Derselbe Durchgang gab der Web-App und der Fernbedienung eine strenge Content Security Policy: Skripte nur aus der App selbst, kein Inline-Skript und Verbindungen nur zu Flagship und den eigenen Servern des Kontos. Die Seiten, die ein Flagship-Server selbst ausliefert (Einladungen, Anmeldung, Zugriffsanfrage), verweigern das Einrahmen ebenfalls, ab dem nächsten Update des jeweiligen Servers.
