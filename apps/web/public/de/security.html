Sicherheit

Flagship ist ein Produkt für die persönliche Cloud. Dein Telefon ist die Vertrauenswurzel, und du hostest deine eigenen Daten auf Hardware, die dir gehört. Das nehmen wir ernst.

Sicherheitsmodell

Das Bedrohungsmodell in einem Absatz

Dein Telefon hält deinen User Master Key (UMK), umhüllt von einem Schlüssel in seiner sicheren Hardware (Secure Enclave beim iPhone, hardwaregestützter Keystore bei Android); solange die App entsperrt ist, liegt er im Speicher des Telefons. Er verlässt das Telefon nie unverpackt. Abgeleitete Schlüssel haben bestimmte Aufgaben: BAK steuert den Serverstart, IRK signiert Vorgänge auf Kontoebene wie Image-Neuaufbau und Widerruf, und SWK wird auf dem Server bereitgestellt, damit das Backup eigenständig läuft, ohne dein Telefon wach zu halten. Peer-Hosts, die die Fragmente deines Backups speichern, sehen immer nur undurchsichtigen Geheimtext. Die Steuerungsebene flagshipserver.com ist ein Zustellkanal und Vermittler; sie sieht nie Geheimnisse im Klartext.

Drei Gerätefamilien. Die native iOS-App und die Android-App nutzen Secure Enclave / StrongBox: starke Schlüsselspeicherung. Die installierbare Web-App nutzt rein softwarebasiertes IndexedDB mit Passphrase: schwächer, geeignet für Tests oder Barrierefreiheit. Schlüssel teilen wir zwischen den Familien bewusst nicht: Eine Web-App-Identität und eine iOS-Identität sind unabhängige Konten, so wie Apple Pay nie zu Google Pay wechselt.

Was wir versprechen

  • Der gesamte sicherheitskritische Code (Schlüsselableitung, Signatur, Verschlüsselung, Daemon, Boot-Pfad, mobile Clients) ist Open Source unter Apache 2.0.
  • Das Boot-Image wird reproduzierbar gebaut: Du kannst prüfen, dass die Bytes zum Quellcode passen.
  • Nur Standardprimitive: Ed25519, X25519, AES-256-GCM, HKDF-SHA-256. Keine selbstgebastelte Kryptografie.
  • Der Serverstart erfordert eine vom Telefon signierte Freigabe über das Netzwerk. Ein gestohlener Server kann sich nicht selbst entsperren.
  • Die Authentifizierungsdomain (flagshipserver.com) ist von der Domain für Nutzerinhalte (*.flagship.services) getrennt, damit Nutzer-Apps nicht durch Subdomain-Verwechslung an Sitzungs-Cookies gelangen.
  • flagshipserver.com kann das TLS der Nutzerinhalte physisch nicht lesen: Die Bytes werden per SNI geroutet und nur auf deinem eigenen Server entschlüsselt.
  • Niemals KYC. Wir erheben, speichern oder zeigen keine Merkmale der realen Identität eines Nutzers: keinen bürgerlichen Namen, keine E-Mail, keine Telefonnummer, keinen Ausweis. Die vollständige Richtlinie lesen →

Quellcode

Protokoll, Daemon, Image-Builder und mobile Clients liegen unter github.com/ibisllc/flagship (der Link wird aktiv, sobald das Repository veröffentlicht ist). Prüfe es, baue es, betreibe es.

Koordinierte Offenlegung & Prämien

Wir bezahlen für schwerwiegende Schwachstellen in einem festgelegten Umfang und beantworten Meldungen nach einem veröffentlichten SLA. Koordinierte Offenlegung ist Pflicht: Exploit-Details bleiben privat, bis ein Fix ausgeliefert ist.

Geltungsbereich

Im GeltungsbereichAußerhalb des Geltungsbereichs
  • flagshipserver.com: der Cloudflare Worker, alle /api/*-Routen, die statische Website sowie Domain-Konfiguration und Cookie-Geltungsbereich.
  • webapp.flagshipserver.com: die Web-App-PWA: WebAuthn-, IRK-Signatur-, Lease-Hinterlegungs- und Wiederherstellungs-Upload-Pfade.
  • remote.flagshipserver.com: die Browser-Fernsteuerung: die Freigabezeremonie am Telefon und die schlüssellose Sitzung, die sie ausstellt.
  • *.flagship.services: die SNI-Passthrough-Ebene auf Fly, der Tunnel-Hub und der Tunnel-Transport von jedem Flagship-Server.
  • Der Flagship-Daemon, wie ihn Flagship Studio auf dem Debian-basierten Boot-Image ausliefert. Umfasst ACME, den lokalen TLS-Server, die Datenschicht (Postgres / Forgejo / Chromium unter /var/flagship/data/ sowie das Dateivolumen jeder App).
  • Das Boot-Image und Flagship Studio, der Image-Builder.
  • Die Schicht der kanonischen Bytes in @flagship/protocol: Signier-/Verifizierroutinen, Schlüsselableitung, Verschlüsselung.
  • Die Flagship-Apps für iOS und Android.
  • Schwachstellen in Apps, die einzelne Nutzer installiert haben (dafür ist der App-Autor verantwortlich; melde sie ihm direkt).
  • Selbst gehostete Forks von Flagship (nur die kanonischen Builds gehören zum Geltungsbereich).
  • Probleme in Abhängigkeiten von Drittanbietern: bitte upstream melden und uns in Kopie setzen.
  • Probleme, die physischen Zugriff auf das bereits entsperrte Telefon oder den Laptop eines Nutzers erfordern.
  • Theoretische Angriffe auf gut geprüfte Primitive (Ed25519, X25519, AES-256-GCM, SHA-256, HKDF) ohne funktionierenden PoC.
  • Rate-Limiting-, Denial-of-Service- oder volumetrische Angriffe auf öffentliche Endpunkte. (Dafür verlassen wir uns auf den Edge von Cloudflare.)
  • Fehlende Sicherheits-Header auf statischen Seiten, auf denen es keine XSS-Senke gibt.
  • Von Scannern automatisch erzeugte Meldungen ohne manuelle Analyse.
  • Social Engineering gegen Mitarbeitende oder Nutzer.

Reaktionsziele

  • Erste Bestätigung innerhalb von 2 Werktagen.
  • Triage-Entscheidung (im/außerhalb des Geltungsbereichs, Schweregrad) innerhalb von 7 Tagen.
  • Ziel für die Auslieferung des Fixes nach Schweregrad: kritisch innerhalb von 7 Tagen; hoch innerhalb von 30; mittel innerhalb von 90; niedrig nach bestem Bemühen, meist im nächsten Release.
  • Öffentliche Offenlegung (mit Nennung der meldenden Person): mit dir abgestimmt, nachdem der Fix über alle Auto-Update-Kanäle ausgeliefert wurde.

  • Kein Embargo, sobald der Fix ausgeliefert ist. Veröffentliche deine Erkenntnisse, wann immer du möchtest. Frag uns vorher, wenn du eine Prüfung auf technische Richtigkeit willst; wir werden dich nicht bitten, etwas abzuschwächen.

Safe Harbor

Gutgläubige Recherchen im Rahmen dieser Richtlinie ziehen keine rechtlichen Schritte von Flagship nach sich. Du darfst Produktionsendpunkte untersuchen, sofern du nicht:

  • Daten anderer Nutzer über das zur Demonstration nötige Minimum hinaus einsehen, ändern oder löschen. Nutze dein eigenes Konto.
  • Das Problem nutzen, um mehr als Testkonto-Daten abzugreifen.
  • Automatisierte Scanner einsetzen, die dauerhafte Last erzeugen.
  • Details veröffentlichen, bevor der Fix ausgeliefert wurde oder bevor unser gemeinsam vereinbarter Offenlegungstermin erreicht ist (wir streben höchstens 90 Tage an, bei kritischen Problemen verhandelbar).

Unauthenticated identity-key swap on an account with no second factor

Critical · reported and fixed October 2026 · fix 7d49a444 · credit pending the reporter’s preference

Account recovery schedules a replacement of the account’s root identity key. The endpoint that starts it verified the request against the incoming key, a self-assertion, and its only other input, the account’s current identity key, is served to anyone by the public username lookup. On an account with no second factor enrolled, that left nothing a stranger could not supply: knowing a public handle was enough to schedule a hostile key swap, which completed once the grace window elapsed.

There was also no owner veto, contrary to what our own documentation claimed. The objection endpoint is signed by the incoming key, so it is the recoverer’s own undo rather than something the displaced owner can exercise. The grace window was a notification window, not a brake.

Starting a recovery now requires an enrolled credential: a TOTP or recovery code, the short-lived proof minted by the passphrase-gated wrapped-key fetch, or a signature from the account’s currently registered key. An account with no credential cannot be recovered by anyone, which is what our naming and recovery policy always said. Finalising a recovery now requires a signature from the key being installed, where it had been an unauthenticated POST. The same pass closed a related fault we had not been told about: with its key unavailable the server fell back to a structural check on TOTP codes, so the second factor was a formality on exactly the accounts that had enrolled one.

Unauthenticated CA-signing oracle mints a relay-hub blessing for any key or host

Critical · reported and fixed October 2026 · fix 54889a4c, hardening 484ef162 and 771db538 · credit pending the reporter’s preference

The endpoint that issues relay-hub blessings did not authenticate its caller, so anyone could obtain a validly signed blessing for a key and host of their choosing: a signing oracle against the trust chain a box uses to decide whether the hub in front of it is the real one.

The issuer is now authenticated and blessings are bound to the expected apex. Two follow-ups harden the box side rather than the hole itself: a box fails closed when the hub presents no blessing and requires the expected apex, and trust lockdown now closes connections that are already open instead of only refusing new ones.

Free username rename bypassed the paid name change and the reserved-name list

Medium · reported and fixed October 2026 · fix b3d6852b, hardening c4132973 · credit pending the reporter’s preference

New accounts can only take a handle the server suggested, and choosing your own name is meant to be the paid name change; the fee is what keeps desirable names from being squatted. An old rename endpoint from early development was still live and enforced none of that. It checked only the account’s own signature, so any account holder could move to a handle of their choosing, for free, as often as they liked, including names we reserve for our own infrastructure. Because names are never taken back, every such allocation would have been permanent.

No other account’s data or keys were exposed, and a squatted reserved name could not be put to use: registering a server re-validates the name, so none could obtain DNS records or a certificate. No app ever called the endpoint, so we removed it rather than patching it. The paid name change will be a separate, new endpoint built with these checks from the start. Besides the reporter’s own test, we found one earlier rename in production, onto a reserved test-environment name; both allocations have been reverted.

A second review of the fix found two places where it relied on something else being true, and both are now closed. Our edge server forwards any API request it does not recognise to the backend, so the removed endpoint answered “not found” only because the backend lacked it too; the edge now refuses it directly, whatever its spelling, and a test proves such a request never reaches the backend or the database. And our compiler never deletes the output of a removed source file, so the old handler’s compiled code was still sitting in the local build directory. It was never part of the deployed service, since nothing loaded it, but every deploy now rebuilds from an empty directory and refuses to ship compiled code that has no source.

The webapp and the browser remote could be framed by another site

Low · reported and fixed October 2026 · fix d0658fb6 · credit pending the reporter’s preference

The webapp, the browser remote and this site sent nothing telling a browser not to show them inside another site’s frame. A hostile page could load them invisibly and lay its own buttons on top, so a click meant for the hostile page landed on ours (clickjacking).

The reach was limited. A framed copy starts signed out: browsers give a frame inside another site its own storage, so it never sees the keys of the user’s real session, and passkey and Face ID prompts appear above any page, where an overlay cannot reach them. The case that mattered was the browser remote. Someone who scanned its code and approved it with their phone while it sat inside a hostile page would leave an approved session in that frame, where buttons laid over it could steer their clicks.

Every response from flagshipserver.com and its subdomains now refuses framing (frame-ancestors 'none' and X-Frame-Options: DENY), and the webapp also refuses to start inside a frame if it is ever served without those headers. The same pass gave the webapp and the remote a strict Content Security Policy: scripts only from the app itself, no inline script, and connections only to Flagship and the account’s own servers. The pages a Flagship server serves itself (invites, sign-in, request access) refuse framing too, from each server’s next update.
