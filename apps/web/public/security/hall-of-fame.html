Hall of fame

Researchers who reported a vulnerability to us, with the commits that closed it. Credited in whatever form each reporter asks for: name, handle, or anonymous, with a link if they want one. Listed without attribution until they have told us their preference; we never publish a name we have not been given.

The browser-remote approval accepted a session before its 6-digit code was confirmed

Low · reported and fixed November 2026 · fix 1b123ed0 · credit: Atharva Savji Lokhande

The QR relay gave the phone’s place to the first device that connected, and the remote page took the first approval it received. Someone holding the QR link within its five minutes could connect the waiting browser to their own server. The person’s account was never reachable.

The browser now asks “Does your phone show this code?” and takes the approval only after Yes. Moving the link’s codes out of the address query follows in the next app release.

Anyone who knew a server’s name could read and cancel its pending update order

Medium · reported and fixed November 2026 · fixes 1837ac01 and 8913cbb5 · credit: Huzaifa Jawaid

An owner-approved update order waited on our server until the box read it, and that read used it up. Unlike the box’s other one-time deliveries, it didn’t need the box’s own token, so a stranger could use it up and the box would silently skip the update.

The box now sends its token there, and our server now requires it.

The app egress fence judged only the first plain-HTTP request on each connection

Low · reported and fixed November 2026 · fix 58f6f453 · credit: Huzaifa Jawaid

On plain HTTP, the fence that holds an app to its approved hosts checked only the first request of a connection, so later requests on the same connection could reach any host.

Each request is now judged by its own host. The fix reaches each server with its next update.

An old browser-remote link could connect the webapp to another server

Medium · reported and fixed November 2026 · fix 1f37c6c6 · credit: Huzaifa Jawaid

The webapp still accepted an old start-up link for the browser remote. It redeemed a session at whatever server the link named, and stored the server the answer named, without checking that either belonged to Flagship’s service domain. A crafted link could install a session for an attacker’s server.

The old link is gone: the browser remote now starts only from the QR code the phone approves, and every session answer must name a server under Flagship’s service domain. The fix shipped in webapp version 260.

Simultaneous grants could pass an organization’s seat limit

Low · reported and fixed November 2026 · fix 4fa472d9 · credit: Huzaifa Jawaid

Seat grants or invites sent at the same moment could each pass the plan’s seat limit, so together they could give an organization more seats than its plan allowed. A grant was also logged even when nothing had been stored.

The limit is now held in the same write that stores the grant, and the log entry is written only after that write succeeds.

Simultaneous share offers could pass the co-manager limit

Low · reported and fixed November 2026 · fix 25a97cc5 · credit: Huzaifa Jawaid

When sharing a server, requests sent at the same moment could each pass the plan’s co-manager limit, and the limit counted only the newest 500 shares.

The count now covers every live share and is held in the same write that creates the share.

Simultaneous requests could get more peer-backup tokens than allowed

Low · reported and fixed November 2026 · fix 79ca995e · credit: Huzaifa Jawaid

Each server may be issued only so many peer-backup tokens. Two requests at the same moment could each pass that limit and together get more tokens than it allowed.

The limit is now counted and reserved in one write before anything is signed.

An organization’s founder could backdate a founder-removal or recovery notice

Medium · reported and fixed November 2026 · fix 6dd5a89b · credit: Huzaifa Jawaid

An organization’s founder-removal or account-recovery notice took its waiting period from a date the request itself stated, so a founder could backdate it and skip both the waiting period and the other admins’ chance to object. This was dormant: no app or server sent these requests.

Our server now refuses both kinds of change until the next release ships the real fix, in which the waiting period starts when our server sees the notice.

Unused server enrollment codes could be read by anyone who knew an organization’s id

Medium · reported and fixed November 2026 · fix e5197fd9 · credit: Huzaifa Jawaid

An organization’s export and its list of ceremonies could hand out server enrollment codes that had not been used yet to anyone who knew the organization’s id, and a code alone was enough to enroll any key as that organization’s server. No such codes existed in production, so nothing was exposed.

The export now carries only codes that have already been used, and a code can no longer be posted as a ceremony. Binding each code to the real server’s own key follows in the next release.

Reports sent with the vulnerability form were lost

Low · reported and fixed November 2026 · fix 7221dfb1 · credit: Huzaifa Jawaid

The report form on our security page sent each report to an address our server no longer answered, so every report sent with the form was lost and the reporter saw an error. Reports sent by email were not affected, and nothing was exposed.

The form works again. Each report is encrypted to our security key as soon as it arrives, so our server keeps it only in a form the key’s holders can read, and the reporter gets a reference. We are notified of each new report, and the page keeps the email address and key as a fallback.

After that fix, the form still refused every report sent from a browser once its spam check was turned on, because the check added a field our server did not expect. Huzaifa Jawaid found this too; it was fixed in 309516e9.

Signature checks accepted three low-order public keys, so a forged signature could verify under them

Low · reported and fixed November 2026 · fix 8fd77a2b · credit: Atharva Savji Lokhande

Our signature checks refused most small-order Ed25519 public keys by a fixed list, but the list missed three of them, and the checks also accepted keys written in a non-canonical form. Under such a key anyone can forge a signature that verifies for any message, so a signature under it proves nothing. No app sends such a key, and a scan of our production data found none stored.

Every key is now decoded under the standard’s strict rules, and small-order and non-canonical keys are refused before any signature is checked. Our server refuses them wherever it stores or vouches for a key, and servers refuse them too starting with their next release.

An unused identity-record endpoint trusted the signers each request named

Medium · reported and fixed November 2026 · fix caf3ce88 · credit: rakimans

An endpoint from early development stored a signed record under a hash of an account name. It checked the record’s signature only against the keys the same anonymous request listed as allowed signers, and that hash can be computed from any public name. Anyone could create a record for any name, replace one, or lock it with a very high version number.

No app ever read or wrote these records: the account directory, which is encrypted and signed by the account’s devices, holds what they were meant to hold. No account data or keys were exposed. Because nothing used the endpoint, we removed it, with its storage and the records in it, instead of patching it.

Account recovery state was public, and a cancelled recovery could be restarted by replaying it

Low · reported and fixed November 2026 · fix ce51f35f · credit pending the reporter’s preference

When a new device recovers an account, the account’s other devices and servers can see the pending change before it takes effect. That record was readable by anyone who knew the account name, including the complete signed request that started it. Because the request stayed valid for five minutes, anyone who read it could send it again after the recovery was cancelled and start it once more.

Nobody could take over an account this way: only the holder of the new device’s key can complete a recovery, and the owner was notified of each attempt. The pending record can now be read only by the account’s own devices and servers, each request is accepted once, and a request dated before a cancellation is refused.

Parallel redemptions let a single-use invite admit more people than it allowed

Medium · reported and fixed November 2026 · fix 14329ad6 and 91b992f4 · credit pending the reporter’s preference

An invite to an app can be limited to one person or a set number. Our server counted the people already in and then added the new one as two separate steps, so many redemptions of the same link sent at once could all pass the count. The servers that run the app did not hold the limit themselves either, and when an app runs on several servers, people one server had refused were let in later elsewhere.

Every path needed the invite link itself. The count and the addition are now one step, redeeming invites is rate-limited, and each server holds an invite’s limit and admits the same first people as the app’s other servers, from each server’s next update. Over-limit test invites left in production were revoked.

Review notes: a mutable install ref, boot tampering, and the app browser

Design review · October 2026 · addressed in release 0.3 · credit: Jay

Jay sent us three observations from reading the code. None came with a working exploit, but each pointed at a real gap, and two of them changed what release 0.3 ships.

The signed install recipe named a branch, not a commit. The phone signs the recipe a new server installs from, but the revision it named defaulted to main, which is mutable: the signature fixed a name, not the code behind it. New servers now install a signed box release for one exact commit (a 40-hex SHA), checked before anything runs.

An app's browser grant reached past its site list. The list was checked when a tab opened or navigated, not on later clicks, form fills or reads, and every app shared one browser profile. Release 0.3 replaces it: each app gets its own browser context, every request is checked against the app's list as the browser sees it, and the current address is checked before and after every action, or the tab is closed and nothing is returned.

Physical access to a powered-off server. The boot partition is not encrypted and nothing measures it, so someone with a few minutes alone with the machine could change the early-boot code and capture the disk key at the next unlock, phone approval included. This is true today. We no longer describe phone approval or the remote lock as protection against it, and measured boot (TPM) is planned work.

Unauthenticated identity-key swap on an account with no second factor

Critical · reported and fixed October 2026 · fix 7d49a444 · credit pending the reporter’s preference

Account recovery schedules a replacement of the account’s root identity key. The endpoint that starts it verified the request against the incoming key, a self-assertion, and its only other input, the account’s current identity key, is served to anyone by the public username lookup. On an account with no second factor enrolled, that left nothing a stranger could not supply: knowing a public handle was enough to schedule a hostile key swap, which completed once the grace window elapsed.

There was also no owner veto, contrary to what our own documentation claimed. The objection endpoint is signed by the incoming key, so it is the recoverer’s own undo rather than something the displaced owner can exercise. The grace window was a notification window, not a brake.

Starting a recovery now requires an enrolled credential: a TOTP or recovery code, the short-lived proof minted by the passphrase-gated wrapped-key fetch, or a signature from the account’s currently registered key. An account with no credential cannot be recovered by anyone, which is what our naming and recovery policy always said. Finalising a recovery now requires a signature from the key being installed, where it had been an unauthenticated POST. The same pass closed a related fault we had not been told about: with its key unavailable the server fell back to a structural check on TOTP codes, so the second factor was a formality on exactly the accounts that had enrolled one.

Unauthenticated CA-signing oracle mints a relay-hub blessing for any key or host

Critical · reported and fixed October 2026 · fix 54889a4c, hardening 484ef162 and 771db538 · credit pending the reporter’s preference

The endpoint that issues relay-hub blessings did not authenticate its caller, so anyone could obtain a validly signed blessing for a key and host of their choosing: a signing oracle against the trust chain a box uses to decide whether the hub in front of it is the real one.

The issuer is now authenticated and blessings are bound to the expected apex. Two follow-ups harden the box side rather than the hole itself: a box fails closed when the hub presents no blessing and requires the expected apex, and trust lockdown now closes connections that are already open instead of only refusing new ones.

Free username rename bypassed the paid name change and the reserved-name list

Medium · reported and fixed October 2026 · fix b3d6852b, hardening c4132973 · credit pending the reporter’s preference

New accounts can only take a handle the server suggested, and choosing your own name is meant to be the paid name change; the fee is what keeps desirable names from being squatted. An old rename endpoint from early development was still live and enforced none of that. It checked only the account’s own signature, so any account holder could move to a handle of their choosing, for free, as often as they liked, including names we reserve for our own infrastructure. Because names are never taken back, every such allocation would have been permanent.

No other account’s data or keys were exposed, and a squatted reserved name could not be put to use: registering a server re-validates the name, so none could obtain DNS records or a certificate. No app ever called the endpoint, so we removed it rather than patching it. The paid name change will be a separate, new endpoint built with these checks from the start. Besides the reporter’s own test, we found one earlier rename in production, onto a reserved test-environment name; both allocations have been reverted.

A second review of the fix found two places where it relied on something else being true, and both are now closed. Our edge server forwards any API request it does not recognise to the backend, so the removed endpoint answered “not found” only because the backend lacked it too; the edge now refuses it directly, whatever its spelling, and a test proves such a request never reaches the backend or the database. And our compiler never deletes the output of a removed source file, so the old handler’s compiled code was still sitting in the local build directory. It was never part of the deployed service, since nothing loaded it, but every deploy now rebuilds from an empty directory and refuses to ship compiled code that has no source.

The webapp and the browser remote could be framed by another site

Low · reported and fixed October 2026 · fix d0658fb6 · credit pending the reporter’s preference

The webapp, the browser remote and this site sent nothing telling a browser not to show them inside another site’s frame. A hostile page could load them invisibly and lay its own buttons on top, so a click meant for the hostile page landed on ours (clickjacking).

The reach was limited. A framed copy starts signed out: browsers give a frame inside another site its own storage, so it never sees the keys of the user’s real session, and passkey and Face ID prompts appear above any page, where an overlay cannot reach them. The case that mattered was the browser remote. Someone who scanned its code and approved it with their phone while it sat inside a hostile page would leave an approved session in that frame, where buttons laid over it could steer their clicks.

Every response from flagshipserver.com and its subdomains now refuses framing (frame-ancestors 'none' and X-Frame-Options: DENY), and the webapp also refuses to start inside a frame if it is ever served without those headers. The same pass gave the webapp and the remote a strict Content Security Policy: scripts only from the app itself, no inline script, and connections only to Flagship and the account’s own servers. The pages a Flagship server serves itself (invites, sign-in, request access) refuse framing too, from each server’s next update.
