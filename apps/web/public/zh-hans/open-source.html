开源

Flagship 是开源软件。平台的价值属于用户，运行在用户自己的硬件上，由用户掌控的密钥保护。许可证保证：即使我们明天消失，你的安装依然继续运行，任何人都可以分叉代码库让它继续存活。

许可证

Flagship 采用 Business Source License 1.1（BUSL-1.1）许可，转换日期为 2030-05-03。到那一天，整个代码库会自动重新授权为 Apache 2.0。在此之前，你可以：

  • 阅读每一行源码：没有任何隐藏。
  • 在你自己的硬件上运行整套系统，供自己使用。
  • 与运行自己盒子的朋友分享修改。
  • 如果我们消失，可以分叉项目让它继续存活。

许可证只限制一件事：在转换日期之前搭建商业化的托管式 Flagship 即服务竞争对手。这一限制条款为原本需要靠风险投资才能支撑的工作提供资金，并将在 2030 年失效。

仓库

官方仓库是 github.com/ibisllc/flagship，包含一切：驱动 flagshipserver.com 的 Cloudflare Worker、驱动 flagship.services 的 Fly 应用、服务器守护进程、apkovl + ISO 构建器、安装脚本，以及 iOS / Android 脚手架。

如何贡献

  • 缺陷报告与小型 PR：在官方仓库中提交 issue 或 PR。我们每周回复一次；测试必须通过。
  • 安全披露：请参阅 /security 和 /.well-known/security.txt。请先私下报告。
  • 较大的功能：请在写代码之前先发起讨论。代码库有很强的架构不变量（TLS 在用户的盒子上终止；flagship.services 确实无法读取用户内容；所有跨 pod 消息都经规范字节签名），我们宁愿事先对齐，也不愿拒绝一个耗时两周的 PR。

治理

Flagship 项目目前由 Anthropic 资助的贡献者和开放社区共同维护。目前还没有正式的基金会；在达到 1.0 并超越早期用户之前，我们会成立一个。在此之前，“什么能被合并”在 issue 跟踪器上公开决定，不存在闭门的技术决策。

可复现构建

可启动的 ISO 是可复现的：任何人都可以从相同的源码标签构建它，并验证个性化尾部没有绕过用户视线夹带任何东西。这对信任主张至关重要：安装介质的杠杆作用太大，不能让它无法被验证。

为什么用 BUSL，而不是从第一天就用 Apache？

我们选择变更日期为 2030 年的 BUSL-1.1，有一个具体的原因：如果第一年就有超大规模云厂商推出“Flagship，但这是我们的产品”这类托管服务，就会在我们交付那些耗时的东西（手机应用、对等备份、硬件合作）之前，扼杀项目自我筹资的能力。2030 年是那道门槛；之后整个代码库都是 Apache 2.0，没有任何隐藏的私有模块。我们不是在玩 SSPL 式的先诱后换。

贡献者

完整的贡献者名单见官方仓库中的 CONTRIBUTORS.md。重要贡献者会在其 PR 合并后的下一个版本中被列入项目公开网站。
