セキュリティ

Flagship はパーソナルクラウド製品です。スマートフォンが信頼の起点であり、データはあなた自身のハードウェア上でホストします。私たちはこれを真剣に受け止めています。

セキュリティモデル

脅威モデルを 1 段落で

スマートフォンには、安全なハードウェア内の鍵（iPhone では Secure Enclave、Android ではハードウェア保護された Keystore）でラップされたユーザーマスターキー（UMK）が保管され、アプリのロック解除中はスマートフォンのメモリ上に保持されます。ラップされていない状態でスマートフォンの外に出ることはありません。派生鍵はそれぞれ役割を持ちます。BAK はサーバーの起動を制御し、IRK はイメージの再構築や取り消しといったアカウントレベルの操作に署名し、SWK はサーバーに配布されて、スマートフォンを起こしておかなくてもバックアップが自律的に動くようにします。バックアップの断片を保管するピアホストには、意味のわからない暗号文しか見えません。flagshipserver.com のコントロールプレーンは配送路と仲介役であり、平文の秘密を見ることはありません。

2 種類の鍵の保管方法。 iPhone と Android のアプリは、スマートフォンのセキュアなハードウェア（iPhone では Secure Enclave、Android ではハードウェア保護された Keystore、搭載機種では StrongBox）で鍵をラップします。強力な鍵の保管です。インストール可能な Web アプリは、パスフレーズで保護された鍵をブラウザー内に保管します。強度は劣り、使い始めるときにもそうお伝えしています。どちらも同じアカウントのデバイスにできます。

お約束すること

  • セキュリティ上重要なコードのすべて（鍵導出、署名、暗号化、デーモン、ブート経路、モバイルクライアント）は BUSL-1.1 のもとで公開されており、2030-05-03 に Apache 2.0 になります。
  • 起動イメージは再現可能な方法でビルドされています。バイト列が公式の Debian と一致することを確認できます。
  • 標準的なプリミティブのみ：Ed25519、X25519、AES-256-GCM、HKDF-SHA-256、そして 0.3 からは従来の方式とハイブリッドで組み合わせた ML-DSA-65 と ML-KEM-768。独自暗号は使いません。
  • サーバーの起動には、ネットワーク経由でスマートフォンが署名した承認が必要です。盗まれたサーバーが自力でロック解除することはできません。
  • 認証ドメイン（flagshipserver.com）はユーザーコンテンツのドメイン（*.flagship.services）から分離されているため、ユーザーのアプリがサブドメインの混同によってセッション Cookie に到達することはできません。
  • flagshipserver.com は、ユーザーコンテンツの TLS を物理的に読むことができません。バイト列は SNI で振り分けられ、復号されるのはあなた自身のサーバー上だけです。
  • KYC は一切行いません。 現実世界の ID に関する属性（本名、メールアドレス、電話番号、公的身分証）を、どのユーザーについても収集、保存、公開しません。ポリシー全文を読む →

0.3 で変わったこと

0.3 では、サーバーの一部が攻撃されうることを前提に、各部分が持つ権限を必要最小限にしました。わかりやすく言うと、次のとおりです。

  • サーバープログラムは root で動作しなくなりました。 一般ユーザーとして動作します。root が必要な数少ない処理（電源、コンテナ、ファイアウォール、リリースのインストール）は小さなブローカーを経由します。ブローカーは、型の決まった要求の固定リストだけを受け付け、それ以外はすべて拒否して記録します。
  • 鍵はサーバープログラムとは別の場所にあります。 サーバーの ID 鍵、TLS 鍵、Let's Encrypt アカウント鍵は、独立した鍵サービスに置かれます。サーバープログラムは鍵サービスに署名を依頼するだけで、鍵を持つことはありません。これは同じマシン上のソフトウェアによる境界であり、ハードウェアによる境界ではありません。
  • スマートフォンは、最初の接続時に各サーバー自身の鍵をピン留めします。 新しいサーバーは、一度しか使えないシークレットによって、あなたのレシピから作られたことを証明し、6 桁のコードを表示します。このコードは、スマートフォンもサーバーの鍵から独自に計算します。それ以降、別の鍵を提示するサーバーは拒否されます。
  • 重要な操作には管理者の鍵が必要です。 管理者を把握しているサーバーでは、アップデート、権限レベルの変更、ジャーナルの読み取り、グラフィックカードの承認などの指示は、管理者デバイスが署名していない限り拒否されます。サーバーの制御インターフェイスのすべてのルートは、既定で拒否する単一のチェックを通ります。
  • 署名付きインストールパッケージ。 サーバーは、Flagship のメンテナーが署名した 1 つのリリースパッケージからインストールとアップデートを行います。パッケージには、増える一方のシーケンス番号と、最低限必要なランタイムのバージョンが含まれます。インストールやアップデートのために、パッケージマネージャー、コンパイラー、git チェックアウトがサーバー上で動くことはありません。ロールバックは、すでにディスク上にあるリリースに切り替えるだけです。
  • 起動。 各 VM アプライアンスは、初回起動時に独自のディスク鍵を作成し、共通の出荷時鍵を削除します。ディスク鍵の封印されたコピーは起動専用の鍵宛てに作られ、サーバーに TPM がある場合は、それを開く鍵が TPM 内に保管されます。計測ブート（measured boot）やアテステーションについては、何も主張していません。
  • アプリは自分の領分にとどまります。 各アプリは gVisor の下で動作し、あなたが承認したインターネット上のホストにしか接続できません。アプリのデータベースのマイグレーションは、厳しく制限された使い捨てのコンテナで実行されます。バックアップから復元したアプリは、あなたがアクセスリストを承認するまで、リストに誰も載っていない状態で起動し、バックアップに記録されたものとまったく同じイメージだけを実行します。グラフィックカードが必要なアプリは、あなたの署名付き承認を待ちます。
  • AI は囲いの中にとどまります。 AI モデルが行うすべてのツール呼び出しは、あなたが許可したものだけを通すブローカーを経由します。サーバーがモデルに見せるものからは、名前、メールアドレス、時刻、言語、ネットワークアドレスがすべて取り除かれます。ローカルAI は、インターネットに接続せずにサーバー上で動作します。
  • リカバリーでパスキーを確認します。 flagshipserver.com は、パスキーによる有効な署名を受け取った後でなければ、クラウドリカバリーの記録を渡しません。また、新しい記録はその内容全体に対して署名されます。0.3 より前に設定したリカバリーは、アプリに一度だけ表示される「アカウントのリカバリーを更新してください」の案内を受け入れると、この保護が適用されます。
  • 耐量子化の土台。 サーバーとスマートフォンは、それぞれの Ed25519 鍵に結び付けられた ML-DSA-65 鍵を持ち、ハイブリッドなチャネル（X-Wing：ML-KEM-768 と X25519）も実装済みで、iPhone と Android には任意で有効にできる設定があります。リリース署名、インストールパッケージ、ブートリースで耐量子側が必須になるのは、当社の署名セレモニーの後です。これらはすべて外部レビュー待ちであり、Flagship が現時点で耐量子であると主張するものではありません。
  • 指摘事項の修正。 0.3 では、製品全体のセキュリティレビューで出荷停止レベルとされた指摘事項と、当社の敵対的テストスイートによる 24 件の指摘事項を修正しました。このテストスイートは現在、すべてのリリースで実行されています。外部による評価はまだ行われていません。

変わっていないこと：TLS はあなた自身のサーバーで終端されるため、私たちはアプリが送る内容を読めません。当社のリレーに見えるのは接続のメタデータ、つまりどのサーバーか、いつか、どれだけの量かです。AI モデルが、あなたが誰でどこにいるかを知ることはありません。

協調的開示と報奨金

定義された範囲内の重大な脆弱性には報奨金をお支払いし、報告には公表している SLA に従って対応します。協調的開示が必須で、修正が出荷されるまでエクスプロイトの詳細は非公開にしてください。

対象範囲

対象対象外
  • flagshipserver.com：Cloudflare Worker、すべての /api/* ルート、静的サイト、ドメイン設定／Cookie のスコープ。
  • webapp.flagshipserver.com：Web アプリの PWA。WebAuthn／IRK 署名／リース預託／リカバリーのアップロードの各経路。
  • remote.flagshipserver.com：ブラウザーリモートの画面。スマートフォンでの承認手順と、それによって発行される鍵なしセッション。
  • *.flagship.services：Fly 上の SNI パススルー基盤、トンネルハブ、各 Flagship サーバーからのトンネル伝送。
  • Debian ベースのブートイメージ上で Flagship Studio が配布する Flagship デーモン。ACME、ローカル TLS サーバー、データ層（/var/flagship/data/ 配下の Postgres／Forgejo／Chromium と、各アプリのファイルボリューム）を含みます。
  • ブートイメージと、イメージビルダーである Flagship Studio。
  • @flagship/protocol の正規バイト列レイヤー：署名／検証ルーチン、鍵導出、暗号化。
  • Flagship の iOS アプリと Android アプリ。
  • 個々のユーザーがインストールしたアプリの脆弱性（アプリ作者の責任範囲ですので、作者に直接報告してください）。
  • Flagship のセルフホスト版フォーク（対象は正規ビルドのみ）。
  • サードパーティ依存関係の問題：上流に報告し、私たちにもコピーを送ってください。
  • ユーザーのロック解除済みのスマートフォンやノートパソコンへの物理アクセスが必要な問題。
  • 十分に検証されたプリミティブ（Ed25519、X25519、AES-256-GCM、SHA-256、HKDF）に対する、動作する PoC のない理論上の攻撃。
  • 公開エンドポイントに対するレート制限、サービス拒否、ボリューム型の攻撃。（これらは Cloudflare のエッジに任せています。）
  • XSS の注入点がない静的ページでのセキュリティヘッダーの欠如。
  • スキャナーが自動生成しただけで、手作業の分析がない報告。
  • スタッフやユーザーに対するソーシャルエンジニアリング。

対応目標

  • 最初の受領確認は営業日 2 日以内。
  • トリアージの判断（対象内／対象外、重大度）は 7 日以内。
  • 修正の出荷目標は重大度別です。クリティカルは 7 日以内、高は 30 日以内、中は 90 日以内、低はベストエフォートで、通常は次のリリースに含めます。
  • 公開（報告者のクレジット付き）：修正がすべての自動更新チャネルに配信された後、あなたと調整のうえで行います。

報奨金の支払い

状況：プレリリース段階で、資金が十分には確保されていません。 Flagship はまだ商用リリース前で、報奨金プログラムの資金も確保できていないため、支払いはそれが整うまで保留となります。下の区分は、資金確保後に支払う見込みの金額であり、現時点での提示ではありません。それまでは、本ポリシーに従ってトリアージ、修正、クレジットの記載を行い、条件を満たす報告はすべて未払いの債務として記録し、商用リリース時にこれらの区分に照らして評価します。時間を使っていただいた後ではなく、その前にお伝えしたいと考えています。

プログラムの資金が確保されるまでの、実際の扱いは次のとおりです。

  • トリアージと修正は、引き続き公表している SLA に従って行います。 資金の有無は、報告への対応の速さに影響しません。下の殿堂に載っている報告はすべて、SLA の範囲内で修正、デプロイされました。
  • 条件を満たす報告はすべて未払いの債務として記録し、当社が評価した重大度とともに、商用リリース時に下の区分に沿って精算します。
  • 重大度は当社が自ら評価し、必要なら引き上げます。 最初にいただいた報告のように、報告内容が事実よりも控えめな場合は、申告された重大度ではなく、より高い重大度を記録します。
  • クレジットはすぐにご用意できます。 ご希望の形式で記載し、何にも左右されません。今お渡しできる唯一のものなので、きちんとお渡ししたいと考えています。
  • 修正の出荷後は、公表を妨げません。 調査結果はいつでも公開していただけます。技術的な正確さの確認が必要な場合は、先にご相談ください。表現を和らげるようお願いすることはありません。
  • 支払いの遅れで本当にお困りの場合は、お知らせください。 後から資金状況を知って、だまされたと感じさせてしまうより、先にうかがいたいのです。

セーフハーバー

本ポリシーに沿って誠実に行われた調査に対して、Flagship が法的措置をとることはありません。本番のエンドポイントを調査してもかまいませんが、次の行為は行わないでください。

  • 問題を実証するのに必要な最小限を超えて、他のユーザーのデータにアクセス、変更、削除すること。ご自身のアカウントを使用してください。
  • その問題を利用して、テストアカウントのデータを超える情報を取得すること。
  • 継続的な負荷を生じさせる自動スキャナーを実行すること。
  • 修正の出荷前、または相互に合意した公開日より前に詳細を公表すること（目安は最大 90 日で、クリティカルな問題は相談に応じます）。
