クイックスタートアーキテクチャしくみインストールサーバーを組み立てるスマートフォンのペアリングアプリとマニフェストURL の多重化復旧API リファレンス

クイックスタート

3 ステップ。所要時間は約 10 分。

1. スマートフォンアプリをインストールし、ユーザー名を決めて、生体認証を承認します。マスターキーがスマートフォンの外に出ることはありません。

2. コンピューターに Flagship Studio を入れます。スマートフォンアプリで「サーバーを追加」→「Studio とペアリング」を選び、Studio に表示される QR コードをスキャンします。Studio が署名済みレシピを受け取り、起動用 USB メモリを書き込みます。あとは挿して起動するだけです。組み立て済みの箱を注文することもできます。

3. スマートフォンから最初のアプリをバイブコーディングで作ります。これで完了です。

アーキテクチャ

3 つの層があります。flagshipserver.com が ID を扱い、flagship.services はステートレスな土管（SNI パススルー＋トンネルハブ）です。TLS はお手元の箱自身が、本物の Let's Encrypt 証明書で終端します。私たちには文字どおり、あなたのデータを読めません。

鍵を持つのはスマートフォンです。.com の Worker は登録機関で、平文のコンテンツを見ることはありません。.services の Fly アプリは単なるルーターで、暗号化されたバイトしか見えません。

Flagship のしくみ

最初から最後まで 5 つの段階があります。すべての手順にスマートフォンが署名するため、初めて登録するときでも、私たちがコンテンツを見ることはありません。

1 · スマートフォンをペアリングする。 Flagship アプリをインストールすると、マスターキーが生成され、スマートフォンの安全なハードウェア内の鍵（iPhone では Secure Enclave、Android ではハードウェア保護された Keystore）でラップされます。ロック解除には Face ID、Touch ID、または指紋を使います。マスターキーがスマートフォンの外に出ることはありません。ここから、ID 用（ユーザー名）、バックアップ認可用（LUKS のロック解除）、作業鍵用（サーバーごとの秘密）の 3 つの鍵を導き出します。ユーザー名を選ぶと、スマートフォンが登録リクエストに署名し、flagshipserver.com がユーザー名と公開鍵の側を記録します。メールもパスワードも SMS も使いません。

2 · レシピを作成して渡す。 スマートフォンは、Studio に表示される QR コードまたは短いコードで Flagship Studio と直接ペアリングします。表示されたセキュリティコードが一致することを確認すると、スマートフォンがサーバー名を記した、有効期間が短く一度しか使えない小さな署名付きレシピを作成して送ります。Studio が適切なベース OS を取得して起動用 USB メモリに書き込むので、OS イメージを自分で選んだりダウンロードしたりする必要はありません。

3 · 起動とインストール。 USB メモリが、堅牢化された Linux ベースをお手元のハードウェアで起動します。初回起動スクリプトがレシピの署名をローカルで検証し、固定された正確な参照で GitHub リポジトリから公開インストーラー（監査可能な数百行のシェル）を取得します。ディスクを LUKS でフォーマットし、箱ごとの ID を生成し、本物の Let's Encrypt 証明書（DNS-01 ワイルドカード）を要求し、flagshipserver.com に登録して、定常状態で起動します。スマートフォンに「Flagship がオンラインになりました」と表示されます。

4 · 起動のたびのロック解除。 箱が再起動すると、LUKS で暗号化されたルートは開きません。ブート段階は flagshipserver.com に、封印を解いたロック解除キーがないか問い合わせ続けます。プッシュで起こされたスマートフォンが生体認証を求め、封印された blob をローカルで復号し、封印を解いたキーを有効期間 10 分で預けます。箱はそれを使い、行は読み出した時点で削除され、ディスクが開きます。スマートフォンのない盗難品の箱は文鎮です。封印を解いたキーを私たちは一度も持ったことがないので、私たちにも手助けはできません。

5 · 公開。バイブコーディング。共有。 スマートフォンからサービスを普通の言葉で説明すると、LLM がそれを書きます（ご自身のプロバイダーキー、または Flagship Inference の無料クレジットを使用）。デーモンがコンテナをビルドし、そのサービス専用の Postgres データベースとファイルフォルダーを用意してデプロイし、サブドメインを登録します。app.you.flagship.services で 1 分以内に公開されます。共有はタップ 1 回で、署名付き招待またはユーザー検索で行います。サービスが Cookie を目にすることはなく、デーモンがメンバーシップを確認した後に ID ヘッダーを付与します。

スマートフォンをなくしたら。 クラウド復旧が保存するのは、マスターキーの暗号化されたコピーだけです。iOS では、復旧にリカバリーパスフレーズと、Flagship のパスキーを保持する iCloud キーチェーンへのアクセスの両方が必要です。Flagship がキーを読んだり、パスフレーズをリセットしたりすることはできません。クラウド復旧がない場合、単一デバイスのアカウントは、待機期間のある、より時間のかかる申請手続きを使う必要があります。

インストールと初回起動

インストーラーは、当社のオープンソースリポジトリにある公開シェルスクリプトで、署名付きレシピの中でハッシュにより固定されています。インストーラーはディスクを LUKS でフォーマットし、サーバーの ID を生成し、DNS-01 で Let's Encrypt 証明書を要求して、.com に登録します。

以降の起動では、毎回スマートフォンが LUKS のロック解除を承認する必要があります。スマートフォンのない盗難品の箱は文鎮です。

サーバーを組み立てる

Flagship Studio は、使っていないコンピューターをあなた専用のサーバーに変えます。証明書（署名付きレシピ）と USB メモリの 2 つを渡すと、適切な堅牢化済み Linux ベースを取得し、レシピを組み込みます。それぞれが何で、どう動くのかを説明します。

証明書

証明書は、スマートフォンが署名する小さな JSON ファイルです。作成するサーバーの名前が記され、リクエストがあなたからのものであることを証明します。新しい Flagship サーバーを認可できるのはスマートフォンだけで、それはポケットの外には出ません。

証明書を入手するには、コンピューターに Flagship Studio をインストールします。Studio に QR コードと短いコードが表示されるので、スマートフォンアプリの「サーバーを追加」からスキャンまたは入力します。セキュリティコードが一致することを確認すると、アプリがサーバーのレシピに署名し、Studio に直接送ります。Web アプリの場合は、署名済みの JSON レシピをダウンロードして Studio で開くこともできます。

一度しか使えず、有効期間も短いものです。 証明書は数時間有効で、認可するのはサーバー 1 台だけなので、ディスクに残ったファイルが再利用されることはありません。必要なときに新しいものを生成してください。

証明書を入手する

ベース OS：こちらで用意します

OS イメージをダウンロードしたり選んだりする必要はありません。 ビルダーが適切な堅牢化済み Linux ベースを自動的に取得して検証し、レシピを組み込みます。固定されているベースは Debian 13 で、最も幅広いマシンで起動できるために選びました。

以下の技術リファレンスは、何が書き込まれるのかを正確に知りたい方や、ビルダーを上級者向けの独自イメージモードで使う方向けです。それ以外の方は読み飛ばして構いません。

Debian 13 (trixie) amd64 · 推奨

最も互換性の高い選択肢です。インストーラーは、頑固な UEFI ファームウェアでも見つけられる場所にブートローダーを配置できるため、他のインストーラーが諦めるマシンでも Debian はインストールして起動できます。ダウンロードサイズも小さく（ネットワークインストーラー）、BIOS と UEFI の両方で起動します。

なぜ固定リストなのか。 ビルダーは、何かを書き込む前に、イメージの SHA-256 をこのリストと照合します。破損したダウンロード、改ざんされたミラー、未検証のバージョンは拒否されるので、チェックサムを手で確認する必要はありません。実機でのエンドツーエンドのインストールを確認した後にだけ、イメージをここに追加します。

起動用ドライブ

USB メモリは、サーバーそのものではなく一度きりのインストーラーです。証明書を運び、使っていないマシンを Flagship サーバーに変えたら役目は終わりで、消去して再利用できます。

ドライブを作成する

証明書と USB メモリをビルダーにドロップして「組み立て」を押します。ベース OS を取得し、証明書をインストーラーイメージの内部に組み込むため、どのサーバーをセットアップするかを知るためにドライブがネットワークから何かを取得する必要はありません。

ドライブは消去されます。中身はすべて上書きされるので、使っていないものを使ってください。

対象マシンを起動する

サーバーにしたいコンピューターにドライブを挿して電源を入れ、起動デバイスとして USB メモリを選びます。インストーラーは無人で動作し、ディスクのパーティション分割、ベースシステムのインストール、Flagship デーモンのセットアップを行います。キーボードの前で見張る必要はありません。

無人で登録

初回起動時に、新しいサーバーが自分自身の ID を生成し、署名付き証明書を提示して、サブドメインを登録します。この時点から TLS はお手元の箱で終端され、flagship.services は、あなたのコンテンツを文字どおり読めない単なる土管になります。

ドライブを取り戻す

サーバーが稼働したら、起動用ドライブの役目は終わりです。入っていた証明書は一度しか使えず有効期間も限られているため、古いドライブが再利用されることはありません。USB メモリはフォーマットし直して、好きに使ってください。

スマートフォンのペアリング

Web コンソールを使うには、スマートフォンで QR コードをスキャンします。スマートフォンが 32 バイトのセッショントークンを表示して add-paired-session オーダーに署名し、デーモンがそのトークンを保存します。ブラウザーはそれを Cookie として保持し、すべての管理呼び出しがそれを携えます。

ペアリングは 設定 → ペアリング済みデバイス に一覧表示されます。いつでも取り消せます。

アプリとマニフェスト

アプリは、サーバーがソースコードと、リポジトリのルートにある flagship.app.json マニフェストからビルドするコンテナです。マニフェストには、ビルドに使うランタイム、必要なデータストア（Postgres、ファイルフォルダー）、アクセスしてよいインターネット上のホスト、サインインなしで誰でも開けるものを記します。サーバーが ID ヘッダーを付与するので、アプリがパスワードを扱うことはありません。

アプリは、ビルドチャットで説明するか（AI がソースとマニフェストを書き、Dockerfile は書きません）、git リポジトリをインポートして用意します。いずれの場合も、サーバーがビルドし、専用のサンドボックスで実行し、ルーティングします。

マニフェストリファレンス

各フィールドは、アプリのインストール時にすべて検証されます。

  • schema_version：常に 1。name：DNS ラベル（小文字、数字、ハイフン）。version：1.2.0 のようなセマンティックバージョン。description：省略可。
  • runtime：base は node-24、python-3.13、static のいずれか。加えて port（アプリは $PORT で待ち受け）、start（起動コマンドをリストで指定。node-24 の既定は npm start）、env。FLAGSHIP_ で始まるキーはサーバーのものです。独自の Dockerfile を持つインポート済みリポジトリは、base の代わりに image を指定します。
  • data.stores：postgres: true でアプリに Postgres 18 のデータベース（FLAGSHIP_PG_URL、pgvector と一般的な拡張を含む）が付き、files: true で /data に書き込み可能なフォルダー（FLAGSHIP_FILES_DIR）が付きます。後者は再起動や再デプロイをまたいで保持されます。S3 や Redis はありません。
  • network：subdomain（<subdomain>.<server>.<you>.flagship.services で提供）と、アプリが接続を求めるホストとその理由を記す egress。アプリのアクセスリストで承認するまで、外部への通信は一切行われません。
  • access：enabled: true（アプリは ID の利用を拒否できません）、default_role、省略可の custom_roles、public_routes（メンバー限定のアプリで誰でも開けるパス）、queryable_by。
  • migration.verification：standard（生体認証）または elevated（生体認証＋第二要素）。金銭、健康、パスワードのデータを扱うアプリ向けです。
  • 省略可：browser.domains。アプリがサーバー自身のブラウザーで操作してよいサイトで、インストール時に承認します。
{
  "schema_version": 1,
  "name": "habits",
  "version": "0.1.0",
  "description": "Daily habit tracker.",
  "runtime": { "base": "node-24", "port": 8080, "start": ["node", "server.js"] },
  "data": { "stores": { "postgres": true } },
  "network": { "subdomain": "habits" },
  "access": { "enabled": true, "default_role": "member" },
  "migration": { "verification": "standard" }
}

URL の多重化

game のインストールが 1 つだけなら、URL game.john.flagship.services はそのまま使えます。別々の箱に game が 2 つインストールされている場合は、この短い URL が曖昧になるため、選択ページを表示します。完全な長い形式（game.home.john.flagship.services）は常に使えます。

短い URL のエイリアスは、スマートフォンから宣言および解放します。設計の詳細 →

復旧

アカウントキーは、あなたのデバイスの中にあります。新しいデバイスに移す方法は 3 つあり、どれも使えない場合、データは復元できません。ハードウェアウォレットと同じです。アプリはセットアップ中にそのことをお伝えします。

  • 別のデバイス。 サインイン済みのデバイスで、設定 → 信頼済みデバイス → デバイスを追加 を開きます。新しいデバイスでは「既存のアカウントに接続」を選び、「ペアリングコードで参加」の下にあるコードをスキャンするか、そのリンクを貼り付けます（すでに別のデバイスでサインインしている場合は 設定 → ペアリングコードをスキャン）。両方に同じコードが表示され、一致したら、鍵がエンドツーエンドで暗号化されて移動します。
  • クラウドバックアップ。 復旧を有効にしていれば、iCloud キーチェーンまたは Google パスワードマネージャーに保管されたパスキーで、封印されたキーのコピーを解除できます。新しいスマートフォンでアカウント名を使ってサインインし、Face ID または指紋で確認します。
  • アカウントキーファイル。 設定 → アカウントキーをバックアップ で、パスフレーズで保護された .flagshipkey ファイルが保存されます。新しいデバイスで、そのパスフレーズを使って開きます。

動作するデバイスがない状態での復旧は乗っ取りに相当するため、盗難者が急がせられないよう待機時間があります。デバイスが 1 台のアカウントでは 7 日、複数台のアカウントでは 24 時間で、後者はさらに復旧用認証アプリのコードまたはリカバリーコードも必要です。他のデバイスにはすぐに通知され、取り消すことができます。その後、各サーバーが新しいデバイスとペアリングされます。

API リファレンス

サーバー上のアプリが前提にできること：

  • 誰が呼び出しているか。 サーバーはクライアントが送った X-Flagship-* ヘッダーをすべて破棄し、自分のものを設定します。X-Flagship-Visitor は member、api、anonymous のいずれかです。メンバーの場合、X-Flagship-User はそのアプリ内でのみ一定の ID（同じ人でも 2 つのアプリでは無関係な ID になります）で、X-Flagship-Role は member、manager、master のいずれかの権限です。匿名の訪問者にはユーザーもロールも付きません。
  • サインイン。 ユーザーをアプリ自身のホストの /__flagship/sign-in?next=/path（サインアウトは /__flagship/sign-out）に誘導します。ユーザーはスマートフォンで承認し、アプリがパスワードを目にすることはありません。
  • API キー。 スクリプトやデバイスは Authorization: Bearer fsk_<keyId>_<secret> でアプリを呼び出します。キーは所有者がアプリのページで作成し、読み取り専用または読み書き可能です。サーバーが最初にこれを検証し、アプリには X-Flagship-Visitor: api と X-Flagship-Api-Scope が渡されます。
  • ライブ接続。 レスポンスはストリーミングされ、WebSocket へのアップグレードはそのまま通過します。
  • データ。 Postgres データベースには FLAGSHIP_PG_URL、ファイルフォルダーには FLAGSHIP_FILES_DIR を使います。

それ以外の、デバイス、サーバー、flagshipserver.com の間のやり取りは、公開 API ではなく署名付きオーダーです。仕様はオープンソースリポジトリ github.com/ibisllc/flagship にあります。まず docs/app-apis.md と docs/manifest.md をご覧ください。
