第 2 要素のないアカウントで、認証なしに ID 鍵をすり替えられた問題

重大 · 2026 年 10 月に報告・修正 · 修正 7d49a444 · クレジット表記は報告者の希望を確認中

アカウントのリカバリーでは、アカウントのルート ID 鍵の置き換えが予約されます。それを開始するエンドポイントは、リクエストを新しく入ってくる鍵、つまり自己申告で検証しており、もう一つの入力であるアカウントの現在の ID 鍵は、公開のユーザー名検索で誰にでも返されていました。第 2 要素を登録していないアカウントでは、見知らぬ人に用意できないものが何も残っていませんでした。公開されているハンドルを知っているだけで悪意ある鍵のすり替えを予約でき、猶予期間が過ぎるとそれが完了していました。

また、当社のドキュメントの記載に反して、所有者による拒否の手段もありませんでした。異議申し立てのエンドポイントは新しく入ってくる鍵で署名されるため、追い出される所有者が使えるものではなく、リカバリーを行う側自身の取り消し手段にすぎませんでした。猶予期間は通知のための期間であり、歯止めではありませんでした。

リカバリーの開始には、登録済みの認証情報が必要になりました。TOTP またはリカバリーコード、パスフレーズで保護されたラップ済み鍵の取得によって発行される短時間有効の証明、またはアカウントに現在登録されている鍵による署名のいずれかです。認証情報のないアカウントは誰にもリカバリーできません。これは当社の命名とリカバリーのポリシーが元々定めていたとおりです。リカバリーの完了には、これまで認証なしの POST だったところ、インストールされる鍵による署名が必要になりました。同じ作業で、報告されていなかった関連する欠陥も修正しました。鍵が利用できないとき、サーバーは TOTP コードの形式だけを確認する処理にフォールバックしていたため、第 2 要素を登録したアカウントに限って、それが形だけのものになっていました。

認証なしの CA 署名オラクルが、任意の鍵やホストに対するリレーハブの承認を発行できた問題

重大 · 2026 年 10 月に報告・修正 · 修正 54889a4c、強化 484ef162 と 771db538 · クレジット表記は報告者の希望を確認中

リレーハブの承認を発行するエンドポイントが呼び出し元を認証していなかったため、誰でも好きな鍵とホストに対する正しく署名された承認を入手できました。これは、ボックスが目の前のハブが本物かどうかを判断するのに使う信頼チェーンに対する署名オラクルでした。

発行元は認証されるようになり、承認は想定される apex に結び付けられました。2 つの追加対応は、穴そのものではなくボックス側を強化するものです。ハブが承認を提示しない場合、ボックスは安全側に倒れて接続を拒否し、想定される apex を要求します。また、信頼のロックダウンは新しい接続を拒否するだけでなく、すでに開いている接続も閉じるようになりました。

無料のユーザー名変更で、有料の名前変更と予約名リストを回避できた問題

中 · 2026 年 10 月に報告・修正 · 修正 b3d6852b、強化 c4132973 · クレジット表記は報告者の希望を確認中

新しいアカウントはサーバーが提案したハンドルしか使えず、自分で名前を選ぶのは有料の名前変更で行う仕組みです。その料金が、人気のある名前の買い占めを防いでいます。ところが、開発初期の古い名前変更エンドポイントがまだ動いており、こうした制約を何も適用していませんでした。確認していたのはアカウント自身の署名だけだったため、どのアカウント所有者も、当社のインフラ用に予約している名前も含め、好きなハンドルに無料で何度でも移ることができました。名前は決して回収されないため、こうして割り当てられた名前はすべて恒久的なものになっていたはずです。

他のアカウントのデータや鍵が漏れることはなく、買い占められた予約名を実際に使うこともできませんでした。サーバーの登録時に名前が再検証されるため、DNS レコードや証明書を取得できたものはありません。このエンドポイントを呼び出すアプリはなかったため、修正するのではなく削除しました。有料の名前変更は、最初からこれらのチェックを組み込んだ、別の新しいエンドポイントになります。報告者自身のテストのほかに、本番環境で以前に行われた名前変更が 1 件見つかりました。予約済みのテスト環境用の名前への変更でした。両方の割り当てを元に戻しました。

修正の 2 回目のレビューで、別の前提が成り立つことに依存している箇所が 2 つ見つかり、どちらも塞ぎました。当社のエッジサーバーは認識できない API リクエストをすべてバックエンドに転送するため、削除したエンドポイントが「not found」を返していたのは、バックエンドにもそれがなかったからにすぎませんでした。現在はどんな表記でもエッジが直接拒否し、そのようなリクエストがバックエンドやデータベースに決して届かないことをテストで確認しています。また、当社のコンパイラは削除されたソースファイルの出力を消さないため、古いハンドラーのコンパイル済みコードがローカルのビルドディレクトリに残っていました。それを読み込むものがなかったため、デプロイされたサービスの一部になったことはありませんが、現在はデプロイのたびに空のディレクトリからビルドし直し、ソースのないコンパイル済みコードの出荷を拒否します。

Web アプリとブラウザリモートが他のサイトのフレーム内に表示される可能性があった問題

低 · 2026 年 10 月に報告・修正 · 修正 d0658fb6 · クレジット表記は報告者の希望を確認中

Web アプリ、ブラウザリモート、そしてこのサイトは、他のサイトのフレーム内に表示しないようブラウザに伝える指示を何も送っていませんでした。悪意あるページがそれらを見えない形で読み込み、その上に自分のボタンを重ねることで、悪意あるページへのクリックが当社のページに届くようにできました（クリックジャッキング）。

影響範囲は限られていました。フレーム内のコピーはサインアウトした状態で始まります。ブラウザは他のサイト内のフレームに専用のストレージを与えるため、ユーザーの実際のセッションの鍵は見えません。また、パスキーや Face ID の確認画面はどのページよりも上に表示され、重ねた要素は届きません。問題になったのはブラウザリモートです。悪意あるページ内に置かれたリモートのコードをスキャンし、スマートフォンで承認してしまうと、そのフレームに承認済みのセッションが残り、上に重ねたボタンでクリックを誘導される可能性がありました。

flagshipserver.com とそのサブドメインからのすべてのレスポンスは、フレーム内での表示を拒否するようになりました（frame-ancestors 'none' と X-Frame-Options: DENY）。さらに Web アプリは、万一これらのヘッダーなしで配信された場合でも、フレーム内では起動しません。同じ作業で、Web アプリとリモートに厳格な Content Security Policy を設定しました。スクリプトはアプリ自身からのみ、インラインスクリプトは不可、接続先は Flagship とアカウント自身のサーバーのみです。Flagship サーバーが自ら配信するページ（招待、サインイン、アクセスのリクエスト）も、各サーバーの次回の更新からフレーム内での表示を拒否します。
