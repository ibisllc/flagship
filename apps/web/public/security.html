Security

Flagship is a personal-cloud product. Your phone is the trust root, you host your own data on hardware you own. We take that seriously.

Security model

Threat model in one paragraph

Your phone holds your User Master Key (UMK) inside the Secure Enclave / StrongBox. It never leaves the phone unwrapped. Derived keys do specific jobs: BAK gates server boot, IRK signs account-level operations like image-rebuild and revocation, and SWK is provisioned to the server so backup runs autonomously without keeping your phone awake. Peer hosts who store your backup shards only ever see opaque ciphertext. The flagshipserver.com control plane is a delivery channel and matchmaker; it never sees secrets in the clear.

Three device families. The native iOS app and Android app use Secure Enclave / StrongBox — strong key storage. The installable webapp uses software-only IndexedDB-with-passphrase — weaker, suitable for testing or accessibility. We deliberately don't share keys between families: a webapp identity and an iOS identity are independent accounts, the way Apple Pay never crosses to Google Pay.

What we promise

  • All security-critical code (key derivation, signing, encryption, daemon, boot path, mobile clients) is open source under Apache 2.0.
  • The boot image is built reproducibly — you can verify the bytes match the source.
  • Standard primitives only: Ed25519, X25519, AES-256-GCM, HKDF-SHA-256. No homemade crypto.
  • Server boot requires a phone-signed approval over the network. A stolen server cannot self-unlock.
  • The auth domain (flagshipserver.com) is separate from the user-content domain (*.flagship.services) so user apps cannot reach session cookies via subdomain confusion.
  • flagshipserver.com is physically unable to read user-content TLS — bytes are routed by SNI and decrypted only on your own server.
  • No KYC, ever. We do not collect, store, or expose any real-world identity attribute about any user — no legal name, no email, no phone, no government ID. Read the full policy →

Source code

The protocol, daemon, image-builder, and mobile clients live at github.com/ibisllc/flagship (link will be live when the repo is published). Audit it, build it, run it.

Coordinated disclosure & bounty

We pay for serious vulnerabilities in a defined scope and respond to reports under a published SLA. Coordinated disclosure is required — exploit details stay private until a fix ships.

Scope

In scopeOut of scope
  • flagshipserver.com — the Cloudflare Worker, all /api/* routes, the static site, and domain configuration / cookie scoping.
  • webapp.flagshipserver.com — the webapp PWA: WebAuthn / IRK signing / lease deposit / recovery upload paths.
  • remote.flagshipserver.com — the browser-remote surface: the phone-approval ceremony and the keyless session it issues.
  • *.flagship.services — the SNI passthrough plane on Fly, the tunnel hub, and the tunnel transport from each Flagship server.
  • The Flagship daemon as shipped by Flagship Studio on the Debian-based boot image. Includes ACME, the local TLS server, the data layer (Postgres / MinIO / Redis / Forgejo / Chromium under /var/flagship/data/).
  • The boot image and Flagship Studio, the image-builder.
  • The canonical-bytes layer in @flagship/protocol — sign/verify routines, key derivations, encryption.
  • iOS and Android apps once shipped to TestFlight / Play Console.
  • Vulnerabilities in apps installed by individual users (those are the app author's responsibility; report to them directly via the app's marketplace listing).
  • Self-hosted forks of Flagship (only the canonical builds are in scope).
  • Issues in third-party dependencies — please report upstream and copy us.
  • Issues requiring physical access to a user's already-unlocked phone or laptop.
  • Theoretical attacks against well-vetted primitives (Ed25519, X25519, AES-256-GCM, SHA-256, HKDF) without a working PoC.
  • Rate-limiting, denial-of-service, or volumetric attacks against public endpoints. (We rely on Cloudflare's edge for these.)
  • Missing security headers on static pages where there's no XSS sink.
  • Reports auto-generated by scanners with no manual analysis.
  • Social engineering of staff or users.

Response targets

  • Initial acknowledgement within 2 business days.
  • Triage decision (in/out of scope, severity) within 7 days.
  • Fix ship target by severity: critical within 7 days; high within 30; medium within 90; low best-effort, usually rolled into the next release.
  • Public disclosure (reporter credit): coordinated with you, after the fix has shipped to all auto-update channels.

Status: pre-release, not yet fully funded. Flagship has not launched commercially and the bounty programme is not funded yet, so payouts are delayed until it is. The bands below are what we expect to pay once funding is in place — they are not a current offer. Until then we triage, fix, and credit reports under this policy, and we record every qualifying report as an outstanding obligation to be assessed against these bands at commercial launch. We would rather tell you this before you spend your time than after.

What that means in practice, until the programme is funded:

  • We still triage and fix on the published SLA. Funding has no bearing on how fast a report gets dealt with. Both reports we have received so far were fixed and deployed the same day.
  • Every qualifying report is recorded as an outstanding obligation, with the severity we assess it at, to be settled against the bands below at commercial launch.
  • We assess severity ourselves and will rate upwards. If your own write-up is more conservative than the facts support — as the first report we received was — we record the higher severity, not the one you claimed.
  • Credit is available immediately, in whatever form you ask for, and is not contingent on anything. It is the one thing we can give you now, so we would rather give it properly.
  • No embargo once the fix has shipped. Write your findings up publicly whenever you like. Ask us first if you want a technical-accuracy review; we will not ask you to soften anything.
  • If the delay causes you real hardship, tell us. We would rather hear it than have you discover our funding position afterwards and feel misled.

Safe harbor

Good-faith research conducted under this policy will not be subject to legal action by Flagship. You may probe production endpoints provided you don't:

  • Access, modify, or delete other users' data beyond the minimum needed to demonstrate the issue. Use your own account.
  • Use the issue to extract more than test-account data.
  • Run automated scanners that generate sustained load.
  • Publish details before the fix has shipped, or before our mutually agreed disclosure date (we aim for 90 days at most, negotiable for critical issues).

Unauthenticated identity-key swap on an account with no second factor

Critical · reported and fixed October 2026 · fix 7d49a444 · credit pending the reporter’s preference

Account recovery schedules a replacement of the account’s root identity key. The endpoint that starts it verified the request against the incoming key — a self-assertion — and its only other input, the account’s current identity key, is served to anyone by the public username lookup. On an account with no second factor enrolled, that left nothing a stranger could not supply: knowing a public handle was enough to schedule a hostile key swap, which completed once the grace window elapsed.

There was also no owner veto, contrary to what our own documentation claimed. The objection endpoint is signed by the incoming key, so it is the recoverer’s own undo rather than something the displaced owner can exercise. The grace window was a notification window, not a brake.

Starting a recovery now requires an enrolled credential: a TOTP or recovery code, the short-lived proof minted by the passphrase-gated wrapped-key fetch, or a signature from the account’s currently registered key. An account with no credential cannot be recovered by anyone, which is what our naming and recovery policy always said. Finalising a recovery now requires a signature from the key being installed, where it had been an unauthenticated POST. The same pass closed a related fault we had not been told about: with its key unavailable the server fell back to a structural check on TOTP codes, so the second factor was a formality on exactly the accounts that had enrolled one.

Unauthenticated CA-signing oracle mints a relay-hub blessing for any key or host

Critical · reported and fixed October 2026 · fix 54889a4c, hardening 484ef162 and 771db538 · credit pending the reporter’s preference

The endpoint that issues relay-hub blessings did not authenticate its caller, so anyone could obtain a validly signed blessing for a key and host of their choosing — a signing oracle against the trust chain a box uses to decide whether the hub in front of it is the real one.

The issuer is now authenticated and blessings are bound to the expected apex. Two follow-ups harden the box side rather than the hole itself: a box fails closed when the hub presents no blessing and requires the expected apex, and trust lockdown now closes connections that are already open instead of only refusing new ones.

Free username rename bypassed the paid name change and the reserved-name list

Medium · reported and fixed October 2026 · fix b3d6852b, hardening c4132973 · credit pending the reporter’s preference

New accounts can only take a handle the server suggested, and choosing your own name is meant to be the paid name change — the fee is what keeps desirable names from being squatted. An old rename endpoint from early development was still live and enforced none of that. It checked only the account’s own signature, so any account holder could move to a handle of their choosing, for free, as often as they liked, including names we reserve for our own infrastructure. Because names are never taken back, every such allocation would have been permanent.

No other account’s data or keys were exposed, and a squatted reserved name could not be put to use: registering a server re-validates the name, so none could obtain DNS records or a certificate. No app ever called the endpoint, so we removed it rather than patching it. The paid name change will be a separate, new endpoint built with these checks from the start. Besides the reporter’s own test, we found one earlier rename in production, onto a reserved test-environment name; both allocations have been reverted.

A second review of the fix found two places where it relied on something else being true, and both are now closed. Our edge server forwards any API request it does not recognise to the backend, so the removed endpoint answered “not found” only because the backend lacked it too; the edge now refuses it directly, whatever its spelling, and a test proves such a request never reaches the backend or the database. And our compiler never deletes the output of a removed source file, so the old handler’s compiled code was still sitting in the local build directory. It was never part of the deployed service, since nothing loaded it, but every deploy now rebuilds from an empty directory and refuses to ship compiled code that has no source.
