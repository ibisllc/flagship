Vérifier l’environnement d’exécution Node

Une partie de chaque serveur Flagship est écrite en TypeScript et tourne sur Node.js. Votre serveur exécute le binaire officiel de Node.js, exactement tel que le projet Node.js le publie sur nodejs.org : jamais une copie recompilée par nos soins. Ci-dessous figurent la version exacte et la somme de contrôle que fixe chaque version de Flagship, signées par les clés de version de Flagship, pour que vous puissiez y comparer votre serveur, et comparer les deux à la liste signée de Node.

Ce que cela prouve, et ce que cela ne prouve pas. Des sommes de contrôle identiques prouvent que votre serveur exécute les mêmes octets que ceux signés par le projet Node.js et approuvés par Flagship. Elles ne prouvent pas que ces octets ont été compilés à partir du code source publié de Node : cela demande une compilation reproductible, une autre affirmation.

Chargement du manifeste signé…

Aucun manifeste d’exécution n’est encore publié. Chaque version contient toujours son propre verrou d’exécution signé (ci-dessous).

Le manifeste n’a pas pu être chargé. Récupérez-le vous-même : /api/runtime/manifest.

Vérifiez par vous-même

1. Téléchargez l’archive officielle et la liste de sommes de contrôle signée de Node, puis vérifiez la signature de Node avec une clé obtenue sur github.com/nodejs/release-keys, pas chez nous :

curl -fsSLO https://nodejs.org/dist/v24.22.1/node-v24.22.1-linux-x64.tar.gz
curl -fsSLO https://nodejs.org/dist/v24.22.1/SHASUMS256.txt
curl -fsSLO https://nodejs.org/dist/v24.22.1/SHASUMS256.txt.sig
gpg --verify SHASUMS256.txt.sig SHASUMS256.txt
grep ' node-v24.22.1-linux-x64.tar.gz$' SHASUMS256.txt
sha256sum node-v24.22.1-linux-x64.tar.gz

2. Vérifiez la signature de Flagship sur le manifeste avec les clés de version épinglées dans le dépôt de code source (la clé ne vient jamais de ce site), et que le verrou qu’il contient est bien celui qu’il signe :

curl -fsS https://flagshipserver.com/api/runtime/manifest -o runtime-manifest.json
jq -j .lockJson runtime-manifest.json | sha256sum    # equals manifest.lockSha256
git clone https://github.com/ibisllc/flagship && cd flagship && npm ci
npx tsx tools/box-artifact/runtime-manifest.ts verify --manifest ../runtime-manifest.json

3. Sur votre propre serveur (avec l’accès de débogage activé depuis sa page dans l’app Flagship), calculez l’empreinte du Node en cours d’exécution et comparez-la au SHA-256 de l’exécutable ci-dessus :

sha256sum /opt/flagship/.runtime/node/bin/node
/opt/flagship/.runtime/node/bin/node --version

L’app Flagship affiche la même comparaison sur la page de chaque serveur, sous Environnement d’exécution.

Comment un serveur l’utilise

  • Le verrou d’exécution (release/runtime-lock.json) fait partie de chaque version signée. Une version dont le Node fourni n’est pas le binaire verrouillé est refusée avant d’être activée.
  • Le serveur récupère ce manifeste, le vérifie avec les clés de version qu’il a déjà épinglées, refuse une séquence plus ancienne ou un manifeste expiré, et garde le dernier qu’il a accepté si ce site est indisponible. Un manifeste absent n’arrête jamais un serveur en bonne santé.
  • Un nouvel environnement d’exécution n’est installé que si la somme de contrôle de l’archive, la liste signée de Node et le manifeste signé de Flagship concordent tous ; sinon, celui en cours reste en place.

La conception complète : le module d’exécution du programme de mise à jour.
