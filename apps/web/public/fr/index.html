§1
Comment ça marche

Quatre étapes. Environ dix minutes.

Vous apportez le matériel et un appareil mobile. Tout le reste tient dans une clé USB, un scan de QR code et un démon discret.

01 · Associer

L’app mobile est le trousseau.

Une clé dans le Secure Enclave (iOS) ou dans le Keystore adossé au matériel (Android) protège l’unique copie. Si vous perdez l’appareil sans récupération dans le cloud, les données sont perdues, comme avec un portefeuille matériel.

02 · Démarrer

Une clé USB, un redémarrage.

Le builder écrit votre recette sur une clé. Le disque est chiffré au premier démarrage ; l’app mobile signe le déverrouillage. Le sous-domaine s’active.

03 · Créer

Créez un service en vibe coding.

Décrivez ce que vous voulez. Le LLM produit le manifeste, le Dockerfile et le code ; le démon valide, compile et déploie en deux minutes.

04 · Partager

Donnez un lien à un ami.

Chaque service vit sur app.you.flagship.services. Un geste pour partager, un geste pour révoquer.

§2
Modèle de confiance

Structurellement, nous ne pouvons pas lire votre contenu.

Si nous sommes compromis, ce qui fuit, ce sont des métadonnées (quels serveurs existent et quand ils sont en ligne), jamais vos fichiers, messages ou prompts. Ce n’est pas une promesse, c’est une propriété de l’architecture.

flagshipserver.com gère l’identité : un nom d’utilisateur et un blob scellé qu’il ne peut pas lire. flagship.services est un simple tuyau qui route du TCP brut selon le SNI. Le TLS se termine sur votre matériel, avec un certificat Let's Encrypt signé par une clé que seul votre démon détient.

Les appareils mobiles initient chaque action importante. Les serveurs n’appellent jamais de leur propre initiative. Aucune base de données partagée chez un tiers ne décide qui voit quoi. Chaque autorisation est appliquée par le serveur même des données.

Le cadenas vert de votre navigateur est réel. Il est signé par une clé qui vit sur votre matériel. Personne d’autre n’en détient de copie.

§3
Questions

Des questions franches, des réponses franches.

Les questions qui comptent vraiment avant de nous faire confiance. Sans jargon marketing ni clichés.

Pourquoi ne pas simplement utiliser iCloud, Google Drive ou Dropbox ?

Parce qu’ils lisent vos données. Pas nous, et structurellement nous ne le pouvons pas : le TLS se termine sur votre matériel. C’est tout le produit.

Que se passe-t-il si je perds mon appareil mobile ?

Si vous avez configuré la récupération dans le cloud (une passkey enveloppe votre clé maîtresse, le texte chiffré vit sur .com), votre nouvel appareil la déballe. Sinon, les données sont perdues, comme un portefeuille matériel qui a perdu sa phrase de récupération.

Faut-il être développeur ?

Non. L’app mobile vous guide à chaque étape. Le vibe coding, c’est écrire ce que vous voulez ; le LLM le code, le démon le déploie.

Puis-je l’exécuter sur un Raspberry Pi ?

L’image actuelle est en x86_64. Les NUC, mini-PC et vieux portables fonctionnent. ARM64 est prévu ; la prise en charge du Pi suivra la même image.

Est-ce open source ?

Oui. BUSL-1.1, avec conversion automatique en Apache 2.0 le 3 mai 2030. Démon, créateur d’images, clients mobiles, app web, protocole : tout est public.

Et si Flagship, l’entreprise, disparaît ?

Votre boîtier continue de fonctionner. Votre certificat continue de se renouveler tant que Let's Encrypt est en service. Nous ne pouvons pas vous enfermer chez nous car, structurellement, nous en sommes incapables.

Comment fonctionne le partage sans système de comptes centralisé ?

Chaque pod émet des jetons d’invitation signés, de courte durée, révocables et limités à une seule app. L’autorisation est appliquée par le serveur même des données.
