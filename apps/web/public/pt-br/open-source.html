Código aberto

O Flagship é OSS. O valor da plataforma pertence ao usuário, no hardware do usuário, com chaves que o usuário controla. A licença garante que, mesmo que desapareçamos amanhã, sua instalação continua funcionando e qualquer pessoa pode fazer um fork do código para mantê-lo vivo.

Licença

O Flagship é licenciado sob a Business Source License 1.1 (BUSL-1.1) com Change Date em 2030-05-03. Nessa data, toda a base de código é relicenciada automaticamente para Apache 2.0. Até lá, você pode:

  • Ler cada linha do código-fonte: nada é escondido.
  • Executar toda a stack no seu próprio hardware, para uso próprio.
  • Compartilhar modificações com amigos que rodam as próprias caixas.
  • Fazer um fork do projeto para mantê-lo vivo caso a gente desapareça.

A licença restringe apenas uma coisa: montar um concorrente comercial de Flagship como serviço hospedado antes da Change Date. Essa exceção financia o trabalho que, de outro modo, teria de ser financiado por capital de risco, e ela desaparece em 2030.

Repositório

O repositório canônico é github.com/ibisllc/flagship. Ele contém tudo: o Worker da Cloudflare que move flagshipserver.com, o app Fly que move flagship.services, o daemon do servidor, os criadores de apkovl + ISO, os scripts de instalação e os esqueletos de iOS / Android.

Como contribuir

  • Relatos de bugs + PRs pequenos: abra uma issue ou PR no repositório canônico. Respondemos semanalmente; os testes devem passar.
  • Divulgações de segurança: veja /security e /.well-known/security.txt. Relate primeiro em particular, por favor.
  • Funcionalidades maiores: abra uma discussão antes de escrever código. A base de código tem invariantes arquiteturais fortes (o TLS termina na caixa do usuário; flagship.services literalmente não consegue ler conteúdo do usuário; toda mensagem entre pods é assinada com bytes canônicos) e preferimos alinhar de antemão a rejeitar um PR de 2 semanas.

Governança

O projeto Flagship é atualmente mantido por colaboradores financiados pela Anthropic e pela comunidade aberta. Ainda não há uma fundação formal; vamos criar uma antes de chegar à 1.0 e crescer além dos primeiros adeptos. Até lá, «o que é incorporado» é decidido em público no rastreador de issues. Não há decisões técnicas a portas fechadas.

Builds reproduzíveis

A ISO inicializável é reproduzível: qualquer pessoa pode compilá-la a partir da mesma tag de código-fonte e verificar que o apêndice de personalização não contrabandeia nada diante do usuário. Isso é essencial para a proposta de confiança: a mídia de instalação tem alavancagem demais para ficar sem verificação.

Por que BUSL e não Apache desde o primeiro dia?

Escolhemos BUSL-1.1 com Change Date em 2030 por um motivo específico: um hyperscaler que rodasse no primeiro ano um serviço hospedado do tipo «Flagship, mas é produto nosso» destruiria a capacidade do projeto de se financiar antes de entregarmos o que leva tempo (apps móveis, backup entre pares, parceria de hardware). A data de 2030 é o portão; depois dela, toda a base de código é Apache 2.0, sem módulos privados escondidos. Não estamos aplicando um bait-and-switch ao estilo SSPL.
