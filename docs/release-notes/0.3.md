Flagship 0.3 Beta is the biggest release so far. Most of it you will never see: it is a rebuild of
how your server keeps its keys, installs its software and runs your apps. Some of it you will see
every day: the apps speak your language, setting up a server is harder to fool, and your server can
now run AI and apps of new kinds without help from anyone else's cloud.

Flagship is still free. There is nothing to buy in this release.

## What you can do now

### Set up a server you can be sure is yours

- **Your phone checks it is talking to your new server.** The first time your server asks to be
  approved, your phone pins that server's own key and checks everything against it from then on. If
  the machine has a screen, it shows a six-digit code; your phone shows the same code above Approve.
  If they don't match, don't approve. When Flagship Studio hosts the server on your computer, Studio
  checks the code for you and the phone says "Confirmed by Studio".
- **A server that was not built from your recipe is refused.** Your recipe carries a one-time secret
  that only your server can prove it holds.
- **Make the installer stick with your Android phone.** Plug a USB stick into your phone and the app
  writes the installer itself, no computer needed. The stick starts from a stock Debian image that
  anyone can rebuild and check byte for byte. [TODO-RM usb-burn]
- **Servers install from one signed package.** A new server no longer downloads code from a
  repository while it installs. It installs one package that Flagship's maintainers signed, checks
  the signature first, and works offline from there.

### Run more kinds of apps

- **Each app gets its own database server.** On new servers, an app's database runs on its own,
  with its own memory, disk and connection limits, so one busy app can't slow the others down.
  [TODO-RM new-box-stack: dedicated databases exist only on the arch-v2 (Podman) stack]
- **Apps made of several parts.** An app can now be up to eight parts (for example a web server and
  a worker) that start in order and count as one app: one approval, one list of sites it may
  reach, one database.
- **WebAssembly apps.** An app can be a small WebAssembly (WASI) program. Each request runs in a
  fresh copy with hard limits on time and memory.
- **Choose how each app updates.** Manual is the default: you approve every update. Staged holds a
  checked update for a week before it installs. Automatic installs at once. Both automatic choices
  only take updates from the same publisher that ask for no new permissions; anything else waits for
  you.
- **Apps can ask to talk to another person's apps.** When an app on someone else's server wants to
  send messages to one of yours, you see a request and choose Allow, Always allow or Deny. You can
  take an Always allow back at any time.
- **Apps can use a web browser on your server**, but only on the sites you approved when you
  installed them, with a separate browser for each app. Your home network and Flagship's own
  services are always out of reach. [TODO-RM app-browser]

### Run AI on your own server

- **Local AI.** Open Local AI from your server's page and download a model. Your apps and your
  builds can then use it, and it runs only on your server: your prompts and data are not sent
  anywhere. It uses your processor, or a graphics card once your card has been qualified (below).
  Downloading a model is the only time your server contacts the model's host.
- **Train a small model on your own data.** You can train one of the small models on an app's sample
  data, on your server. This is early: small models only.
- **Agree before AI spends anything.** Before an AI repair uses your own API key or your Flagship
  Inference credits, you see an estimate and who pays, and you agree. The amount you agreed to is a
  hard stop.
- **AI still never learns who you are.** What your server sends to an outside AI model is now also
  stripped of names, mail addresses, home folders, times, time zones, languages and network
  addresses.

### Use a graphics card, with your permission

- **Your server lists its graphics cards** on its page, with which app holds each one.
- **An app that needs a graphics card waits for you.** You get a notification and approve it with
  your admin device, or withdraw the approval later. Until you approve, the app runs without the
  card if it can, or tells you why it can't.
- **Cards are qualified before use.** Flagship only gives a graphics card to an app once that model
  of card has passed our hardware tests. Until then, apps that need one say plainly that they can't
  run yet. NVIDIA, AMD and Intel cards are supported in the software.

### Keep control when Flagship can't be reached [TODO-RM offline-control]

- **Your phone finds your server on your home network** when flagshipserver.com or our relay can't
  be reached. No setup: it looks for your server on the same Wi-Fi and checks the server's own key.
- **Basic control without us:** see your server's status and its apps, start, stop or restart an
  app, restart or shut down the server, and make a backup and save it to your phone.
- **Every action is still signed by your phone** and checked by the server.
- **Limits, stated plainly.** This works while your server is running. A server that restarts still
  needs flagshipserver.com to unlock its disk. Creating an account, adding a device or recovering
  an account still need flagshipserver.com. [TODO-RM: the box refuses rescue sessions while a
  server's quantum-safe strict profile is on (rescue/authority.ts); either add the hybrid signature

### Use Flagship in your language

- The apps, the web app, the website, Flagship Studio and the pages your server shows visitors are
  now in English, Spanish, French, German, Brazilian Portuguese, Japanese and Simplified Chinese.
  Notifications arrive in your phone's language. The translations are machine-made drafts that
  native speakers have not reviewed yet; if a sentence reads wrong, tell us at
  support@flagshipserver.com.

### A calmer app

- **Home, Activity and Settings were redesigned** on iPhone, Android and the web app: shorter
  screens, one "Add / Restore a server" button, and red buttons only for what can't be undone.
- **Approve a server's start from your watch with your phone locked.** Apple Watch and Wear OS.
- **Signing out asks for Face ID, your fingerprint or your device PIN first** whenever it would
  erase keys.
- **Account recovery now checks your passkey too.** The apps ask you once to update your recovery
  so it is protected by your passkey as well as your passphrase.

### Safer updates

- **A server update proves itself or steps back.** The new release installs beside the old one and
  gets three starts to prove it is healthy. If it fails, your server goes back to the release it ran
  before, by itself. Updates and rollbacks never touch your apps, data, keys or settings.
- **Updates reach a small group of servers first**, and more only once those are healthy.
  [TODO-RM canary]
- **Share update results (optional, off by default).** Turn it on from your server's page to send
  Flagship one receipt per update saying whether it worked. It names no app and holds no content.
- **A newer foundation for new servers.** New servers run apps with Podman and keep their keys in
  small, separate programs written in Rust. Servers you already have keep their current setup.

## For the security-minded

The short version: we assumed parts of the server could be attacked, and made each part hold as
little power as it needs.

- **Review findings fixed.** This release fixes the stop-ship findings of a security review of the
  whole product, works through its follow-up items, and fixes the 24 findings of our own adversarial
  test suite, which now runs on every release. [TODO-RM findings: the review's author is not named in
  SECURITY-HARDENING-PLAN.md, so this text does not call it independent or external; N06, N07, N12
  and N13 are only partly done per SECURITY-0.3-PROGRESS.md]
- **The server program no longer runs as root.** It runs as an ordinary user. The few things that
  need root (power, containers, the firewall, installing a release) go through a small broker that
  accepts only a fixed list of typed requests and refuses everything else.
- **Keys live apart from the server program.** The server's identity, TLS and Let's Encrypt keys sit
  in a separate key service. The server program asks it to sign; it never holds the keys.
- **Sensitive actions need your admin key.** Updates, rank changes, journal reads, graphics-card
  approvals and similar orders are refused unless your admin device signed them. The account's
  everyday key is not enough on a server that knows its admin.
- **Signed install packages.** Server releases are signed by Flagship's maintainers, carry a
  sequence number that only goes up, and are checked before anything is installed. Installing or
  updating no longer runs a package manager or a compiler on your server.
- **Boot.** Each VM appliance makes its own disk key on first start; the shared factory key is
  removed. The disk key's sealed copy is addressed to a boot-only key, and where a server has a TPM,
  the key that opens it is kept in the TPM. We make no measured-boot or attestation claims yet.
- **Apps stay in their lane.** App database migrations run in a locked-down one-shot container. A
  restored backup's apps start with nobody on their access list until you approve it. A restored
  app runs only the exact image the backup recorded.
- **Quantum-safe groundwork.** Servers and phones now hold ML-DSA-65 keys beside their Ed25519 keys,
  and a hybrid channel (X-Wing: ML-KEM-768 with X25519) is built for your devices and servers. An
  opt-in "Quantum-safe protection" setting on iPhone and Android uses them. Release signatures need
  their quantum-safe half only after our signing ceremony. All of this is pending external review.
- **What has not changed.** TLS still ends on your own server, so we can't read what your apps
  send. Our relay sees connection metadata: which server, when, and how much. An AI model never
  learns who or where you are. An external security assessment has not been done yet; the package
  for it is ready.

Report a vulnerability at https://flagshipserver.com/security#report.
