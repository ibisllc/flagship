# Reproducible Flagship ISO build

The Flagship base ISO (`flagship-base-alpine-3.21.0-x86_64.iso`) is the
artifact users boot to install Flagship. For the "trust the bytes you
boot" claim to mean anything, anyone — not just us — must be able to
build the same ISO from public source and verify the bytes match what
flagshipserver.com is shipping.

This doc explains:
- How the build is structured.
- What's pinned to make it reproducible.
- How to verify a downloaded ISO yourself.

For the **operational** layer — verifier walkthrough, the
"hash-doesn't-match" investigation playbook, and the full table of
known non-determinism sources with status (Fixed / Documented / TODO) —
see [`docs/runbooks/iso-reproducibility.md`](runbooks/iso-reproducibility.md).

## TL;DR — verify a release artifact

```sh
# 1. Download the ISO + the published sha256.
curl -sLO https://flagshipserver.com/build/iso/flagship-base-alpine-3.21.0-x86_64.iso
curl -sLO https://flagshipserver.com/build/iso/flagship-base-alpine-3.21.0-x86_64.iso.sha256

# 2. Confirm the file matches the published sum.
sha256sum -c flagship-base-alpine-3.21.0-x86_64.iso.sha256

# 3. Build the ISO yourself from source at the matching git tag.
git clone https://github.com/ibisllc/flagship.git
cd flagship
git checkout iso-v3.21.0   # tag the workflow ran on
npm install
bash scripts/build-flagship-iso.sh out/flagship-base.iso

# 4. Compare. If they're identical, the published artifact is the bytes
#    that the public source produces.
sha256sum out/flagship-base.iso flagship-base-alpine-3.21.0-x86_64.iso
diff <(sha256sum out/flagship-base.iso | awk '{print $1}') \
     <(sha256sum flagship-base-alpine-3.21.0-x86_64.iso | awk '{print $1}')
```

## Architecture

```
Alpine official ISO            Flagship apkovl
(pinned URL + sha256)          (deterministic node script)
        │                              │
        ▼                              ▼
     xorriso extract             emit-apkovl.mjs
        │                              │
        └──────── inject ──────────────┘
                       │
                       ▼
              clamp all mtimes to SOURCE_DATE_EPOCH
                       │
                       ▼
               xorriso re-pack
              (deterministic flags)
                       │
                       ▼
            flagship-base.iso + .sha256
```

## What's pinned

| Input | How |
|---|---|
| Alpine ISO version | `ALPINE_VERSION="3.21.0"` in `scripts/build-flagship-iso.sh` |
| Alpine ISO sha256 | `ALPINE_SHA256["3.21.0"]="ab27d3da..."` in the same file. Mismatch aborts the build. |
| Apkovl contents | Generated by `packages/installer-apkovl/scripts/emit-apkovl.mjs`; `buildApkovl()` takes the tar `mtime` from `SOURCE_DATE_EPOCH` (no `Date.now()`, no random) and is tested for byte-stability across the second-boundary case that previously bit us. |
| All file mtimes inside the ISO | Clamped to `SOURCE_DATE_EPOCH` (the workflow derives it from the commit timestamp). |
| ISO volume id + UUID | Set explicitly to a function of `ALPINE_VERSION` + `SOURCE_DATE_EPOCH`. |
| xorriso version | The GHA workflow installs xorriso via apt on `ubuntu-22.04`; for stricter pinning, switch to a self-hosted runner with a digest-pinned VM image. |
| Node | `setup-node@v4` with `node-version: "22"` — works for the apkovl emitter (no native deps). |

## What the workflow does

1. Checkout the repo at the tag.
2. Install xorriso, curl.
3. Compute `SOURCE_DATE_EPOCH` from the commit's Unix timestamp.
4. Install npm deps (needed for `emit-apkovl.mjs`).
5. Run `scripts/build-flagship-iso.sh out/flagship-base.iso`.
6. Run it AGAIN and `cmp -s` the two outputs. If they differ, fail
   the workflow loudly — that's a reproducibility regression and we
   need to track it down before the artifact ships.
7. Upload the ISO + .sha256 as a workflow artifact (always) and as
   a GitHub Release asset (when the trigger is a `iso-v*` tag push).

The "build twice and compare" step is the single most important
guarantee: even if the rest of the toolchain has hidden non-determinism,
this catches it before the bytes leave the workflow runner.

## Things that would break reproducibility (and how we avoid them)

- **xorriso embedding a build timestamp.** Avoided by passing
  `-volume_date all_file_dates =$SOURCE_DATE_EPOCH` and a fixed UUID
  derived from the same epoch.
- **Tar archive in the apkovl having different mtimes per build.**
  `buildApkovl.ts` writes a fixed mtime field; verified by the
  package's own tests.
- **gzip embedding a timestamp / OS field.** `gzipSync` from Node
  embeds neither for its default opts; tested in `installer-apkovl/tests`.
- **Directory entry order.** xorriso sorts deterministically when
  given a single `-map` source; we use exactly one.
- **Extracted file permissions varying between filesystems.** We do
  the work inside `mktemp -d`, which is local tmpfs/ext4 on the
  runner — same on every run.

## Things that aren't pinned (and the implication)

- The Ubuntu runner image. `ubuntu-22.04` is a moving target (security
  patches). xorriso is at whatever version `apt` resolves it to. In
  practice this has been stable across runs over weeks; if it ever
  isn't, the build-twice-and-compare check fails and we investigate.
- The Cloudflare R2 upload step (separate, manual today). The
  reproducibility property is about the *bytes*; how they get hosted
  is orthogonal.

## Bumping Alpine

When Alpine releases a new point version:

1. Download the new standard ISO. Verify against Alpine's published
   sha256 (`https://dl-cdn.alpinelinux.org/alpine/v$X.$Y/releases/$ARCH/alpine-standard-$X.$Y.$Z-$ARCH.iso.sha256`).
2. Update `ALPINE_VERSION` and add the new sha256 to `ALPINE_SHA256`
   in `scripts/build-flagship-iso.sh`.
3. Update `BASE_ISO_URL` and `BASE_ISO_VERSION` and `BASE_ISO_SHA256`
   in `apps/com/wrangler.toml`.
4. Tag the commit `iso-v$X.$Y.$Z` and push — the workflow will build
   + verify + upload to Releases.
5. Manually upload the release asset to R2 (`flagship-iso` bucket)
   so it's served from `flagshipserver.com/build/iso/`.
