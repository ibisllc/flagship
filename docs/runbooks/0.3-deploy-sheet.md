# 0.3 deploy sheet: what you need ready

`bash scripts/release.sh --list` shows the 38 steps; `--phase A` then `--phase B` run them
(`docs/runbooks/final-deploy.md` is the long form). This is the checklist of what only you can bring,
and what is new in 0.3 compared with the 2026-10-20 release. Do `docs/runbooks/0.3-hardware-acceptance.md`
first; the gyms and tests are green before this starts.

## New in 0.3, so new in the release

- **D1 migrations 0107 to 0119** (boot suspensions, re-pair veto, recovery v2, watch boot keys, voici names,
  passkey recovery key, adapter attestations, server boot keys, PQ key bindings, assurance policy changes,
  server-order PQ signature, boot unlock v2, update receipts). All additive. The script finds what is pending
  from the prod ledger and applies each after a confirm; take the D1 backup first.
- **Secrets** the new code reads (names only; the script lists missing ones): `ADAPTER_ATTESTATION_SIGNING_KEY`
  (64-hex Ed25519 seed, its public half in `release/adapter-vetting-keys.json`), `ADAPTER_COMPLAINT_SALT`,
  `ADAPTER_REVIEW_ANTHROPIC_KEY`, plus the ones from earlier releases (`ACCOUNT_READ_TOKEN_SECRET`, the inference
  and recovery secrets). New bindings: the adapters R2 bucket (`ADAPTERS_BUCKET`).
- **Runtime manifest (new step 10, runbook 3d)**: `release/runtime-manifest.json` is still `null`, so
  `/api/runtime/manifest` answers 204 and every Runtime card says "not published". Step 10 previews
  `npx tsx tools/box-artifact/runtime-manifest.ts release`, then on your yes signs it (`release --sign`: YubiKey
  PIN + touch for Ed25519, again for the PQ key), verifies, commits and re-pins; the `.com` deploy (step 19)
  publishes it and refuses a `null` file without a typed `no-runtime-manifest`. Boxes then hand it to the updater,
  which refuses an update whose runtime lock it does not accept; an absent or expired manifest never stops a box.
  It is valid 45 days: put a re-sign + `.com` deploy in the calendar (`release.sh --only 10`).
- **Name dibs** window is configured in `wrangler.toml` (`DIBS_WINDOW_START/END`): check the dates still suit launch day.
- **USB seed**: release step 21 (publish) now dispatches `iso-seed.yml`, then `scripts/publish-iso-seed.sh <run id>` attaches the
  seed to a GitHub release and switches on `FLAGSHIP_ISO_SEED`. The seed hash must equal the one in
  `apps/mobile/android/.../SeedPins.kt` (a test keeps them equal); a Debian point release means a new seed and new pins.
  Without it the Android burn answers "no download".
- **Webapp shell v184** and the new `flagship-webapp` static Worker flow are unchanged from the last release.
- **Boot-chain refresh**: boxes take the new unlock scripts through an ordinary endorsed update, as a one-time trial boot
  first. An owner who uses auto-unlock with a TPM-sealed lease may be asked to approve the first reboot on their phone
  (see the OPEN list in `RELEASE-0.3-JOURNAL.md`). Do not stop a box mid-update.
- **Arch-v2 stack** (Rust keyd/broker, Podman) is what new boxes get: the gym verdict is set (`newBoxStack` arch-v2,
  `appBrowser` true in `release/box-release.json`; `scripts/set-new-box-stack.mjs`, `scripts/set-app-browser.mjs`), and
  the release notes, blog and store texts say so.
- **Launch texts** depend on three release-run steps (owner, 2026-11-02): the USB seed publish (step 21) and act 4 of
  `0.3-hardware-acceptance.md` for the phone USB burn, and the catalog root ceremony (`final-deploy.md` 2b) for "Updates
  reach a small group of servers first". If any of them does not happen, take those lines out of
  `docs/release-notes/0.3.md`, the blog post and the store listings before the `.com` deploy.
- **Rescue / offline control** are on-device; nothing to deploy beyond the app builds and the box release. The strict
  post-quantum caveat in the notes goes away only with the PQ ceremony.

## Before you start the script

1. `RELEASE-0.3-JOURNAL.md`: every box through D3 ticked, the OPEN list from B2 read and accepted or fixed.
2. `npm run release-manifest` reads green except the known receipts.
3. Nothing is deployed from a branch: merge `release/0.3` to `main` (fast-forward) only when the script asks.
4. Keep `playstore-test-0725` untouched while a store review is open.
5. On release day, before the `.com` deploy: set the 0.3 item's `<pubDate>` in `apps/web/public/blog/rss.xml` to that
   day (RFC 822, e.g. `Mon, 09 Nov 2026 00:00:00 +0000`), delete the `TODO-RM` comment above it, and commit.

## Afterwards

Weekly `npm run rate-limits`; `npm run ops -- workers --hours 72` after launch; the reap and `npm run zone-health` as in
the runbook; the hardware receipts from `0.3-hardware-acceptance.md` go in `docs/runbooks/receipts/`.
