# 0.3 hardware scenario (one sitting, the owner's devices)

One story that walks as many surfaces as possible on real hardware, in an order that opens the Windows PC
**only twice** (swap in the server drive in Act 4, put Windows back in Act 9). It covers the items of
`0.3-hardware-acceptance.md`; tick them in that file's sign-off table as you go (the step numbers below
point at it). Everything talks to the **gym** (`gym.flagshipserver.com`, the gym relay): production has no
0.3 yet. Allow about 4 to 5 hours; Acts 1 to 3 can be one evening and Acts 4 to 9 another.

## Devices and who plays what

| Device | Plays |
|---|---|
| **iPhone 14 Pro** (+ **Apple Watch S8**) | The admin phone of account **A** (throwaway, created in Act 1). Watch approves a start-up in Act 5. |
| **Friend's Android phone** (+ OTG dongle) | First a second admin device of A (Act 1: burns the `metal` USB stick; Act 3: phone name handover), then removed from A and used as account **B** (Act 7: share, invites). Wiped of Flagship at the end. |
| **Mac** | Mac Studio: hosts server **mac-vm** (Act 2). Also where the release manager watches the logs. |
| **Windows PC with NVIDIA GPU** | Act 1: Windows Studio (pair, host a VM). Act 4 onward: a **metal Flagship server** (`metal`) with the GPU, booted from the stick onto a spare drive. |
| **Chromebook** | The browser: webapp, Remote, the phone's own name page, app isolation (Act 6). Linux Studio in Crostini if it is enabled (optional). |

What you need on the table: a spare internal drive for the PC (any size ≥ 64 GB; it will be wiped), a
USB stick (16 GB+), router access (to cut the internet but keep the Wi-Fi up), the PC's screwdriver.
Never use the review account `playstore-test-0725`.

The release manager prepares before you start: the iPhone gym build (installed), the Android gym APK, the
gym builds of Mac Studio, Windows Studio (zip) and Linux Studio (AppImage), and confirms the gym is green.
Tell the release manager when you start each Act: logs are watched live, and a gym run or a gym relay
change is never started while you are mid-Act.

---

## Act 1. Accounts, the USB stick from the Android, Windows Studio (≈ 50 min)

Windows still boots from its own drive.

1. iPhone: install check. The gym build is pointed at the gym once, from the Mac:
   `xcrun devicectl device process launch --device <UDID> com.flagshipserver.app -sticky-apex-host gym.flagshipserver.com`;
   after that a tap on the icon talks to the gym too (runbook §0). **Create account A**. Turn on Face ID for approvals.
2. Android: install the gym APK (`adb install -r …` from the release manager, or sideload), then point it at
   the gym once: `adb shell am start -n com.flagshipserver.app/.MainActivity --es flagship.stickyApexHost gym.flagshipserver.com`.
   **Join account A** from the iPhone's "Add a device" (admin device, pairing code, matching SAS).
3. Android + OTG dongle + USB stick: **Add a server → burn a USB stick** for a new server named `metal`
   (Wi-Fi or Ethernet as the PC will have it). The phone writes and verifies the stick on its own. Keep the
   stick. *(runbook §4: USB burn from a real Android phone; the metal boot happens in Act 4)*
4. Windows: unzip Windows Studio; in PowerShell `setx FLAGSHIP_CONTROL_HOST gym.flagshipserver.com`, then open
   Studio from a NEW window (runbook §6); pair it with the iPhone (typed code, matching SAS on both).
   **Host on this PC** a throwaway server `win-vm`; see it Online on the iPhone; then Delete it from the
   phone. *(runbook §6)*
5. Shut Windows down. Do not open the PC yet.

**Watch for:** the Android burn ends with a verified stick (if it fails, burn the stick from Windows
Studio instead and note it); pairing SAS matches; Restart as administrator works if Windows asks.

## Act 2. Mac Studio server, and the basics on the iPhone (≈ 40 min)

1. Mac: quit any other Studio and start the gym one from Terminal with
   `FLAGSHIP_CONTROL_HOST=gym.flagshipserver.com` (runbook §5); pair with the iPhone, **Host on this Mac** a server `mac-vm`.
   *(runbook §5)*
2. iPhone: the server comes Online and is Leader; the Health card fills in; open its address: valid
   padlock. Open an app name too (install a small app from the phone, e.g. a notes app): its own
   padlock. *(runbook §10: control and apps certificates)*
3. Restart `mac-vm` from Studio: the iPhone gets the unlock request; approve with Face ID. Online again.
   *(runbook §1)*
4. iPhone, server page: the **routine** start-up card should read "It's waiting for its disk key…"
   (not "Is this the machine in front of you?"), since the phone already knows this server. *(runbook §16)*
5. iPhone: **Update this server** if an update is offered (the Rust updater installs it); it comes back
   by itself. *(runbook §14: Rust updater)*

## Act 3. Two phones, one name (≈ 30 min)

1. (The Android already joined A in Act 1.)
2. iPhone: keep the app in the foreground (there is no switch: an admin device in the foreground claims the
   name). From the Chromebook, open `https://<A>.gym.flagship.services/`: a valid padlock for exactly that name
   and `{"present":true,...}`; `/.well-known/flagship-phone` shows the iPhone's key. *(runbook §9: phone name,
   phone certificate)* The old one-time-code session is retired in 0.3 (`/api/phone/session` and `/ping` answer
   403): a website reaches only voi.ci's `live`/`deliver` from its listed origin (runbook §9.4).
3. Both apps in the foreground. Put the iPhone in airplane mode for 2 minutes: the Android takes the name over
   (vacancy). Reload `/.well-known/flagship-phone` on the Chromebook: the Android's key. Turn the iPhone back on
   and open the app: it stays standby, the Android keeps the name.
4. Android: send the app to the background (that lets the name go; there is no Release button); the iPhone
   takes it back.
5. iPhone: **remove the Android** from A (Trusted devices). Within seconds the Android loses the name and
   any session; the Chromebook page no longer reaches it. *(runbook §9)*

## Act 4. Open the PC once: it becomes the `metal` server (≈ 30 min, one opening)

1. Power off, unplug, open the PC, **swap its Windows drive for the spare drive**, close it.
2. Boot from the Act 1 stick (burned by the Android) (choose the USB in the boot menu). The installer runs unattended; the PC
   reboots into Flagship. *(runbook §4: metal boot)*
3. iPhone: approve the first start (first-contact wording here is right: "Is this the machine in front
   of you?"). `metal` comes Online. *(runbook §1, §2)*
4. Release manager checks the boot log on the FLAGSHIP_BOOT partition and the single LUKS key slot.
   *(runbook §2)*

## Act 5. The GPU server (≈ 45 min)

1. iPhone: `metal`'s server page shows the graphics card (read-only qualification). *(runbook §7)*
2. Release manager runs the **NVIDIA mega run** over SSH (debug access granted from the iPhone for 1
   day): `gpu-real` gym group, local AI on the GPU. You only approve the debug-access grant (Face ID).
   *(runbook §7b)*
3. iPhone: install an app that uses local AI; ask it something; it answers from the GPU.
4. Reboot `metal` from the phone; **approve the start-up on the Apple Watch** (Quick approve from watch on).
   *(runbook §8)*

## Act 6. The Chromebook as everyone's browser (≈ 30 min)

1. Chromebook: open the **webapp** (gym), sign in by pairing with the iPhone. Home shows `mac-vm` and
   `metal`; drag to reorder (server order): the Leader badge moves.
2. **Remote** (remote.… gym page): QR shown, scanned by the iPhone, approved: the browser controls `metal`.
3. **App isolation:** open two different apps of `metal` in two tabs; sign in to one; the other does not
   see that session; a member-only app refuses a stranger tab (incognito). *(runbook §12)*
4. **Dead-man line** (server page, iPhone): set `metal` to "7 days". If the line reads "Waiting for an admin to
   open Flagship", the app name stops answering on the Chromebook within about a minute while the server name
   keeps working; send the iPhone app to the background and back after a minute (it signs a lease silently):
   the app answers again. If the line goes straight to "Stays online until…", the phone signed at once (fine).
   Set it back to "Never" (No time limit). *(runbook §11)*
5. Optional: Linux Studio AppImage in Crostini: opens and pairs. *(runbook §6)*

## Act 7. A second person: the friend's account B (≈ 30 min)

1. Android: create **account B** (fresh install of the app data, or Sign out first).
2. iPhone (A): **Share** `metal` with B at "Can view"; Android accepts (admin device of B).
3. iPhone: invite B's person to one app as Member; Android opens the invite: the app opens; ranks show.
4. iPhone: end the share and withdraw the invite: the Android loses both at once.

## Act 8. Internet cut: offline control and Rescue (≈ 40 min)

1. Router: cut the internet, keep the Wi-Fi. iPhone on the same Wi-Fi.
2. iPhone: `metal` is still reachable on the LAN (LAN-direct); offline control works (stop/start an app).
   *(runbook §3)*
3. **Rescue my data** to the iPhone, then import into account B's Android if the runbook's stranger step
   applies. *(runbook §3)*
4. Restore the internet; both servers come back Online on their own.
5. Optional, only if the metal box should also prove the **stack switch**: from the iPhone, switch `metal`
   to the other stack and back (each takes a few minutes; the trial must end "kept"). *(runbook §13)*

## Act 9. Clean up, and the second (last) opening

1. iPhone: Delete `mac-vm` and `metal` from account A (Delete, not Revoke). Delete account A; on the
   Android delete account B, then uninstall the gym app from the friend's phone.
2. Power off the PC, open it, **put the Windows drive back**, close it. Wipe the spare drive later if you
   like (it holds only the deleted server's encrypted data).
3. Tell the release manager: the results go in the sign-off table, and any failure becomes a bug with a fix
   and a regression test before the release goes on.

Optional at any point, once the release manager says the gym relay mesh is up: Activity shows "Moved to another
Flagship relay" rows *(runbook §15)*.

## Not covered by these devices

A USB burn from Windows Studio (only if the Android burn fails), a second iPhone (the iOS-to-iOS pairing), a Wear OS watch, and an iPad.
