# 0.3 hardware acceptance

What only real hardware can prove for the 0.3 release. The gyms, mocks and QEMU lanes are green first
(`RELEASE-0.3-JOURNAL.md` stages C and D); this is the last gate before `scripts/release.sh`. The owner
runs it; the release manager (or an agent) prepares the builds, watches the logs and records results.

Record each result in the table at the end (pass / fail / skipped + the build or commit). A failure is
a bug: it gets a fix and a regression test before the release goes on, then the item is run again.
Never use the review account `playstore-test-0725`; use a throwaway account.

**Backend: the GYM, not production.** Production has no 0.3 yet. Every build below talks to
`gym.flagshipserver.com` (control) and `gym.flagship.services` (relay and server names). The one-sitting order
for the owner's own devices is `0.3-hardware-scenario.md`; it points at the step numbers here.

Gym caveats:
- A gym refresh (`scripts/gym-refresh.sh`, also phase 0 of every gym run) redeploys the gym Worker and relay:
  expect about a minute of errors. Tell the release manager before each step; nobody starts a gym run or a
  gym relay change mid-step.
- The gym D1 is **not** wiped between runs: always a **fresh throwaway account name**, never one an
  earlier run used.
- The gym relay is one Fly machine (plus the mesh relays once H10's gym group is up); a Fly edge hiccup
  (tcp-backhaul resets) shows as a single failed request: retry once before calling it a failure.

## 1. Pair, host, unlock (iPhone, then Android)

1. Create the account; add a server (Host on this Mac, or the stick from step 4).
2. Reboot the box once the server is Online. The phone gets the unlock request; approve it with the
   biometric. The box comes back Online.
3. Home shows the server as leader; the Health card fills in; the server's address opens with a valid
   padlock.
4. Do it again from the other phone (add it as a device first).

## 2. Boot log on the real disk

After the reboot in step 1, on the box (debug access from the server page, or the console) read
`/boot/flagship-unlock.log` on the FLAGSHIP_BOOT partition: it must exist and contain the premount
lines for that boot (the ext4 and by-label mount fix, `RELEASE-0.3-JOURNAL.md` B0). If it is empty or
missing, stop: report it, do not continue.

## 3. Offline control and Rescue my data, with the internet cut

On the home network, phone and box on the same Wi-Fi/LAN.

1. Cut the internet at the router (the LAN stays up). Confirm the app shows `.com` unreachable.
2. Settings, Offline control. The server shows "Found on this Wi-Fi"; Connect. Expect "Checked by its
   own key" and no certificate warning (or the expired-certificate note if the cert has lapsed).
3. Start, stop and restart one app: each asks to confirm, and each action works.
4. Rescue my data: save the passcode, make and download the backup; kill the Wi-Fi mid-download once and
   confirm Resume finishes it. Share the file out and open it.
5. Restart the server from the app: it stays locked after the restart (the disk needs Flagship to
   unlock; that is the documented limit). Restore the internet, approve the unlock, the box returns.
6. A stranger: with the second phone signed in to a different account, Offline control must not open a
   session on this box.
7. Restore the internet; in Activity, the offline actions appear in the owner's words.
8. Import the downloaded file on a second throwaway account (Add a server, Import a backup) with the
   passcode: the apps come back with their data.

## 4. USB burn from a real Android phone, and a metal boot

1. In the Android app: add a server, choose a USB stick burn; plug the stick through OTG. The burn writes
   the seed and the recipe. Gym: the stick must ask `boot.gym.flagshipserver.com` for its unlock; only an APK
   with the 2026-11-02 burn boot-host fix (`AssetPreseedSource`) bakes the gym's boot worker in, an older one
   bakes production's and the installed box never gets its unlock.
2. Boot a spare machine from the stick (UEFI and, if the machine has it, legacy BIOS). The installer
   runs with no prompts, powers off at the end, and the server registers and reaches Online after the
   first boot (unlock from the phone).
3. `cryptsetup luksDump` on the installed disk (debug access): exactly one key slot.
4. Record the seed hash the phone showed against the published one
   (`flagshipserver.com/security/iso-seed.html`).

## 5. Mac Studio hosting

Gym: start Studio from Terminal so it inherits the gym host (a Finder launch talks to production):
`FLAGSHIP_CONTROL_HOST=gym.flagshipserver.com "/Applications/Flagship Studio.app/Contents/MacOS/FlagshipBuilder"` (or the
dev bundle the release manager names). Quit any other copy of Studio first.

Install the DMG built for 0.3 (signed and notarized by `scripts/release-studio.sh`), host a server from
the published appliance, pair a phone, unlock, stop and restart from the Studio menu (no corruption on
the next start). Quit Studio during an update once: the box recovers on its own.

## 6. Windows and Linux Studio

Hand `docs/runbooks/device-test-agent.md` and `docs/runbooks/desktop-windows-linux-validation.md` to the
agent on that machine. Gym: Windows, set it for the user once in PowerShell, then open a NEW window and start Studio
(a user variable, so an elevated "Restart as administrator" should see it too: check the server it makes asks the gym): `setx FLAGSHIP_CONTROL_HOST gym.flagshipserver.com`;
remove it afterwards with `reg delete HKCU\Environment /v FLAGSHIP_CONTROL_HOST /f`. Linux:
`FLAGSHIP_CONTROL_HOST=gym.flagshipserver.com ./Flagship-Studio-*.AppImage`. A USB stick burned by a gym-pointed Studio
asks `boot.gym.flagshipserver.com` for its unlock (the Windows burn does so only from the build that carries the
`NativeBuildPipeline` boot-host fix of 2026-11-02). Results go on a `device-results/<machine>-<date>` branch, never `main`. The 0.3
Studios stay labelled Experimental until a run passes.

## 7. Local AI on the CPU, and a graphics card (read-only)

1. Server page, Local AI: download the smallest model; ask it something from an app or a build. The
   answer arrives; the box made no other outside connection (Activity).
2. With a card installed: the server page shows the card as detected but **not** approved until you
   approve it. Approve it, then withdraw the approval; both appear in Activity. Nothing is installed or
   changed on the box by looking. The card is not used for apps until it is qualified.

## 7b. One mega run on the NVIDIA box (owner, 2026-10-30)

One sitting covers the GPU receipts together with the phone, Studio and boot steps above. Use a 0.3 gym
build of the phone app (it talks to the gym `.com`), the 0.3 Studio to burn an SSH-enabled USB (debug
access), and boot the PC that has the NVIDIA card from it.

1. Pair, unlock and see the server Online as in steps 1 and 4 (the burn and the metal boot count for both).
2. From the Mac, one command does every GPU stage the card supports (driver, toolkit and gVisor nvproxy
   if missing, with one reboot; H1 CUDA and PyTorch, H2 scrub, H9 render and video, no-device refusal,
   `cargo test --test hardware`, then MIG, multi-GPU and passthrough only where the card has them):
   `GYM_GPU_SSH=root@<box ip> GYM_GPU_SSH_KEY=<key> npx tsx tools/live-e2e/shared-run.ts --groups gpu-real`
   (the check images' bases are pinned by digest in `tools/gpu/bases.env`, CUDA 12.4 to match Debian 13's driver 550;
   `docs/architecture-v2/gpu-runbooks/nvidia-cuda.md` says why and how to override). The receipt directory is copied
   back; `node scripts/gpu-catalog.mjs build` pins it.
3. On the phone: the card shows as detected and not approved; approve it, run a local-AI answer that uses
   it, withdraw the approval; each step appears in Activity and the box stops using the card.
4. Record the receipt directory and the commit under step 9.

## 8. Watch and Wear OS basics

Apple Watch and a Wear OS 4 watch: the server list shows, a box waiting to unlock shows, and Approve
works on the watch where it is enabled (Settings, Quick approve from watch).

## 9. The phone's own name (phone route) and the phone certificate (H2, H3)

Two admin devices of one account: the iPhone and an Android phone (add it as an admin device first). The phone
route needs no switch: an **admin** device that is **in the foreground** gets a certificate for the bare
account name `<account>.gym.flagship.services` (key made on the phone, never uploaded) and claims the name at the
relay. A browser on a third device (Chromebook or laptop) is the visitor.

1. **Claim (iPhone).** Open the app on the iPhone and leave it in the foreground. In the browser open
   `https://<account>.gym.flagship.services/`: a valid padlock whose certificate names exactly the bare name (look
   at the certificate details: one name, issued by Let's Encrypt), and a JSON answer `{"present":true,...}`.
   `https://<account>.gym.flagship.services/.well-known/flagship-phone` shows `phoneRoutePub`: write down its
   first 8 characters (the iPhone's).
2. **Background releases nothing silently.** Send the iPhone app to the background: within about a minute the bare
   name stops answering (no box ever answers for it: a server page here is a failure).
3. **One holder at a time; handover by vacancy.** Bring both phones' apps to the foreground, iPhone first. The
   well-known answer stays the iPhone's (the Android waits as a standby). Put the iPhone in airplane mode: within
   about a minute the answer is the Android's `phoneRoutePub`. Turn the iPhone back on and open the app: the
   Android **keeps** the name (no preemption) until it goes to the background, then the iPhone takes it.
4. **One-time code page.** *Known gap 2026-11-02:* the endpoint has the one-time-code session
   (`POST /api/phone/session`), but no app screen shows the code yet and the bare name serves JSON, not a page.
   Record "blocked (no UI)" unless a later build adds it; when it exists: the code opens a session in that
   browser only, a second use of the code is refused, a request from another app's origin is refused.
5. **Certificate reuse.** Repeat step 3 twice: no new certificate per handover (the certificate's serial in the
   browser stays the same for each phone).
6. **Revocation.** On the iPhone, Settings, Trusted devices: remove the Android. Within seconds the Android can no
   longer hold the name: with only the Android in the foreground the bare name stops answering; its standby
   connection is closed. Activity shows the removal.
7. **Not an admin.** A non-admin device of the account (if you have one) never holds the name.

Look for: the padlock (iOS Secure Enclave key or Keychain fallback, Android StrongBox or TEE: the first run of
either on hardware), no certificate warning ever, and no box content on the bare name.

## 10. Certificates through `.com` (H1, H9)

On a server installed with this build (step 1): open its address `https://<server>.<account>.gym.flagship.services/`
and an app's address (install a small app from the phone first, then open it from the app's page). Both show a
valid padlock; the server name's certificate names only the server (the control certificate), the app's names the
app wildcards (the apps certificate), and neither names the bare `<account>` name. Restart the server: same
certificates come back, no new order (the box renews only in the last third of a certificate's life).

## 11. The dead-man line (H4, H8)

On the server page (admin device): one line, "No time limit" by default.

1. Tap it, choose **7 days**, Stop serving its apps, Save (Face ID). The line reads "Stays online until <date> if no
   admin opens Flagship · 7 days" (the phone signed a lease at once) or, briefly, "Waiting for an admin to open
   Flagship".
2. If it reads "Waiting for an admin...": in the browser the **app** name stops answering within about a minute
   while the **server** name keeps working (the control name is never cut). Bring the app to the background and
   back after a minute: the phone signs a lease silently, the line becomes "Stays online until...", the app
   answers again within seconds. (If the line went straight to "Stays online", the stop half is the gym's
   `serving` group; record "lease signed at once".)
3. Set it back to **Never** ("No time limit"), Save.
4. The same line and editor on the Android (and in the webapp).

## 12. App isolation (H5)

Two apps on one server, opened in two tabs of one browser. Sign in to one (as a member): the other tab is not
signed in by it. A member-only app refuses a private (incognito) window with the knock page. Nothing in one app's
page can read or change the other (no shared cookie: the cookies are host-only).

## 13. Stack switch (metal box only, optional)

Server page, **Container stack**: "This server runs the classic stack (Docker)." Tap **Move to the new stack**:
the plan ("What the move does", free space) shows; **Move now** (Face ID). The server restarts; the card reads
"On trial until <date>..." and later "Moved on <date>."; apps come back with their data. Then **Go back to the
classic stack** the same way. A move that fails must read "The move was undone: <reason>" and the server keeps
working.

## 14. Update from the phone (the Rust updater, G1)

When the server page offers an update: **Update this server** (Face ID). The server goes away for about 2 to 5
minutes and comes back by itself; the update card's last-update line shows the new release and success. If
debug access is on, the box journal line ends "(flagship-updater)". Never power the box off during an update.

## 15. Relay rows in Activity (optional: only once the gym relay mesh is up)

Only when the release manager says the gym runs more than one relay (H10). Activity, the server's section: a
move shows "Moved to another Flagship relay" (or "Stayed on its current relay" with a reason); the server stays
Online through it. Skip it otherwise.

## 16. Wording fixed after the store screenshots

On the phones, compare with the store contact sheet:
- A server this phone already knows (its key is pinned) asking to start: "It's waiting for its disk key. Unlock it
  only if you expected it to restart." A server seen for the first time: "Is this the machine in front of you?
  Only approve if you recognise it."
- App titles are words from the app's name, not its slug ("Chess club", not "Chess-Club"); "· 4 apps" is
  pluralised in every language you try; on Android, Admin / Change / Download / Delete are translated.
- Backups read "this device", not "this phone", on the iPad.
