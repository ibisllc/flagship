# 0.3 hardware acceptance

What only real hardware can prove for the 0.3 release. The gyms, mocks and QEMU lanes are green first
(`RELEASE-0.3-JOURNAL.md` stages C and D); this is the last gate before `scripts/release.sh`. The owner
runs it; the release manager (or an agent) prepares the builds, watches the logs and records results.

Record each result in the table at the end (pass / fail / skipped + the build or commit). A failure is
a bug: it gets a fix and a regression test before the release goes on, then the item is run again.
Never use the review account `playstore-test-0725`; use a throwaway account.

**Backend: the GYM, not production.** Production has no 0.3 yet. Every build below talks to
`gym.flagshipserver.com` (control) and `gym.flagship.services` (relay and server names). The one-sitting order
for the owner's own devices is `0.3-hardware-scenario.md`; it points at the step numbers here.

Gym caveats:
- A gym refresh (`scripts/gym-refresh.sh`, also phase 0 of every gym run) redeploys the gym Worker and relay:
  expect about a minute of errors. Tell the release manager before each step; nobody starts a gym run or a
  gym relay change mid-step.
- The gym D1 is **not** wiped between runs: always a **fresh throwaway account name**, never one an
  earlier run used.
- The gym relay is one Fly machine (plus the mesh relays once H10's gym group is up); a Fly edge hiccup
  (tcp-backhaul resets) shows as a single failed request: retry once before calling it a failure.

## 1. Pair, host, unlock (iPhone, then Android)

1. Create the account; add a server (Host on this Mac, or the stick from step 4).
2. Reboot the box once the server is Online. The phone gets the unlock request; approve it with the
   biometric. The box comes back Online.
3. Home shows the server as leader; the Health card fills in; the server's address opens with a valid
   padlock.
4. Do it again from the other phone (add it as a device first).

## 2. Boot log on the real disk

After the reboot in step 1, on the box (debug access from the server page, or the console) read
`/boot/flagship-unlock.log` on the FLAGSHIP_BOOT partition: it must exist and contain the premount
lines for that boot (the ext4 and by-label mount fix, `RELEASE-0.3-JOURNAL.md` B0). If it is empty or
missing, stop: report it, do not continue.

## 3. Offline control and Rescue my data, with the internet cut

On the home network, phone and box on the same Wi-Fi/LAN.

1. Cut the internet at the router (the LAN stays up). Confirm the app shows `.com` unreachable.
2. Settings, Offline control. The server shows "Found on this Wi-Fi"; Connect. Expect "Checked by its
   own key" and no certificate warning (or the expired-certificate note if the cert has lapsed).
3. Start, stop and restart one app: each asks to confirm, and each action works.
4. Rescue my data: save the passcode, make and download the backup; kill the Wi-Fi mid-download once and
   confirm Resume finishes it. Share the file out and open it.
5. Restart the server from the app: it stays locked after the restart (the disk needs Flagship to
   unlock; that is the documented limit). Restore the internet, approve the unlock, the box returns.
6. A stranger: with the second phone signed in to a different account, Offline control must not open a
   session on this box.
7. Restore the internet; in Activity, the offline actions appear in the owner's words.
8. Import the downloaded file on a second throwaway account (Add a server, Import a backup) with the
   passcode: the apps come back with their data.

## 4. USB burn from a real Android phone, and a metal boot

1. In the Android app: add a server, choose a USB stick burn; plug the stick through OTG. The burn writes
   the seed and the recipe. Gym: the stick must ask `boot.gym.flagshipserver.com` for its unlock; only an APK
   with the 2026-11-02 burn boot-host fix (`AssetPreseedSource`) bakes the gym's boot worker in, an older one
   bakes production's and the installed box never gets its unlock.
2. Boot a spare machine from the stick (UEFI and, if the machine has it, legacy BIOS). The installer
   runs with no prompts, powers off at the end, and the server registers and reaches Online after the
   first boot (unlock from the phone).
3. `cryptsetup luksDump` on the installed disk (debug access): exactly one key slot.
4. Record the seed hash the phone showed against the published one
   (`flagshipserver.com/security/iso-seed.html`).

**Pass:** the phone wrote the stick with no computer, the seed hash equals the published one, the machine
installed with no prompts, the server reached Online after the phone approved its unlock, and `luksDump` shows
exactly one key slot. **Fail:** anything else. The release notes, the 0.3 blog post and the Play listing say
"make the installer stick with your phone" (owner, 2026-11-02); on a fail, take those lines out before launch
(`docs/runbooks/0.3-deploy-sheet.md`, "Launch texts").

## 5. Mac Studio hosting

Gym: start Studio from Terminal so it inherits the gym host (a Finder launch talks to production):
`FLAGSHIP_CONTROL_HOST=gym.flagshipserver.com "/Applications/Flagship Studio.app/Contents/MacOS/FlagshipBuilder"` (or the

## 6. Windows and Linux Studio

Hand `docs/runbooks/device-test-agent.md` and `docs/runbooks/desktop-windows-linux-validation.md` to the
agent on that machine. Gym: Windows, set it for the user once in PowerShell, then open a NEW window and start Studio

## 9. The phone's own name (phone route) and the phone certificate (H2, H3)

Two admin devices of one account: the iPhone and an Android phone (add it as an admin device first). The phone
route needs no switch: an **admin** device that is **in the foreground** gets a certificate for the bare
account name `<account>.gym.flagship.services` (key made on the phone, never uploaded) and claims the name at the
relay. A browser on a third device (Chromebook or laptop) is the visitor.

1. **Claim (iPhone).** Open the app on the iPhone and leave it in the foreground. In the browser open
   `https://<account>.gym.flagship.services/`: a valid padlock whose certificate names exactly the bare name (look
   at the certificate details: one name, issued by Let's Encrypt), and a JSON answer `{"present":true,...}`.
   `https://<account>.gym.flagship.services/.well-known/flagship-phone` shows `phoneRoutePub`: write down its
   first 8 characters (the iPhone's).
2. **Background releases nothing silently.** Send the iPhone app to the background: within about a minute the bare
   name stops answering (no box ever answers for it: a server page here is a failure).
3. **One holder at a time; handover by vacancy.** Bring both phones' apps to the foreground, iPhone first. The
   well-known answer stays the iPhone's (the Android waits as a standby). Put the iPhone in airplane mode: within
   about a minute the answer is the Android's `phoneRoutePub`. Turn the iPhone back on and open the app: the
   Android **keeps** the name (no preemption) until it goes to the background, then the iPhone takes it.
4. **What a website can reach on the phone's name (voi.ci only).** The one-time-code browser session
   (`POST /api/phone/session`, `/api/phone/ping`, the `__Host-` cookie) is retired in 0.3: the only operations a
   website reaches are voi.ci's `GET /api/phone/live` and `POST /api/phone/deliver` (docs/voici-and-messages.md
   §8.2), from the listed origin only (`https://gym.voi.ci` on a gym build, `https://voi.ci` on a production
   build). With the iPhone holding the name, from the visitor laptop's terminal (`<acct>` = the account):
   - `curl -si https://<acct>.gym.flagship.services/api/phone/live -H 'origin: https://gym.voi.ci'` answers 200
     (the account has a published page and Accept messages on) or 404 `not-found` (no page), and in both cases
     `access-control-allow-origin: https://gym.voi.ci` and no `access-control-allow-credentials`.
   - The same with `-H 'origin: https://evil.<acct>.gym.flagship.services'` (a sibling app) or
     `-H 'origin: https://<acct>.gym.flagship.services'` (the phone's own name) answers 403 `origin` with no
     `access-control-*` header at all.
   - `curl -si -X POST https://<acct>.gym.flagship.services/api/phone/session -H 'origin: https://<acct>.gym.flagship.services' -d '{"code":"123456"}'`
     answers 403 and no `set-cookie`: the retired session is gone.
   - `curl -si -X OPTIONS https://<acct>.gym.flagship.services/api/phone/deliver -H 'origin: https://gym.voi.ci' -H 'access-control-request-method: POST' -H 'access-control-request-headers: content-type'`
     answers 204 with the allow headers; adding `,authorization` to the request headers answers 403 `preflight`.
   - `curl -si https://<acct>.gym.flagship.services/ -H 'host: evil.<acct>.gym.flagship.services'` answers 421
     `wrong-host`.
   The same on the Android when it holds the name. The live gym group `phone-endpoint` sends these through the
   relay to a simulated phone; this step is the real iOS and Android endpoints (Secure Enclave / StrongBox key,
   their own HTTP code). A 200 from any refused case, a CORS header naming anything but the listed origin, or any
   `set-cookie` is a failure. The delivery itself is act 17.
5. **Certificate reuse.** Repeat step 3 twice: no new certificate per handover (the certificate's serial in the
   browser stays the same for each phone).
6. **Revocation.** On the iPhone, Settings, Trusted devices: remove the Android. Within seconds the Android can no
   longer hold the name: with only the Android in the foreground the bare name stops answering; its standby
   connection is closed. Activity shows the removal.
7. **Not an admin.** A non-admin device of the account (if you have one) never holds the name.

Look for: the padlock (iOS Secure Enclave key or Keychain fallback, Android StrongBox or TEE: the first run of
either on hardware), no certificate warning ever, and no box content on the bare name.

## 10. Certificates through `.com` (H1, H9)

On a server installed with this build (step 1): open its address `https://<server>.<account>.gym.flagship.services/`
and an app's address (install a small app from the phone first, then open it from the app's page). Both show a
valid padlock; the server name's certificate names only the server (the control certificate), the app's names the
app wildcards (the apps certificate), and neither names the bare `<account>` name. Restart the server: same
certificates come back, no new order (the box renews only in the last third of a certificate's life).

## 11. The dead-man line (H4, H8)

On the server page (admin device): one line, "No time limit" by default.

1. Tap it, choose **7 days**, Stop serving its apps, Save (Face ID). The line reads "Stays online until <date> if no
   admin opens Flagship · 7 days" (the phone signed a lease at once) or, briefly, "Waiting for an admin to open
   Flagship".
2. If it reads "Waiting for an admin...": in the browser the **app** name stops answering within about a minute
   while the **server** name keeps working (the control name is never cut). Bring the app to the background and
   back after a minute: the phone signs a lease silently, the line becomes "Stays online until...", the app
   answers again within seconds. (If the line went straight to "Stays online", the stop half is the gym's
   `serving` group; record "lease signed at once".)
3. Set it back to **Never** ("No time limit"), Save.
4. The same line and editor on the Android (and in the webapp).

## 12. App isolation (H5)

Two apps on one server, opened in two tabs of one browser. Sign in to one (as a member): the other tab is not
signed in by it. A member-only app refuses a private (incognito) window with the knock page. Nothing in one app's
page can read or change the other (no shared cookie: the cookies are host-only).

## 17. voi.ci pages and Messages (H11)

Spec: docs/voici-and-messages.md. Needs `VOICI_ENABLED` on in the gym Worker's config (the production
`wrangler.toml` keeps it "off" until the release turns it on, before store submission), the gym voi.ci site
(`https://gym.voi.ci`) and its files host (`files.gym.voi.ci`; production's `files.voi.ci` DNS is a release-day owner
step). The App Attest capability and the DeviceCheck key (iOS), and the Play Integrity project and service account
(Android), are OWNER setup: until they exist the phones enroll on the slower "no attestation" tier (account at least
7 days old, 1 new recipient a day), which is what a first run shows; note which tier you saw. Two throwaway accounts:
**O** (the page owner: the iPhone as admin device, the Android as a second admin device) and **V** (the visitor: any
phone with the gym build, plus a desktop browser).

1. **Publish (iPhone, O).** Messages tab (between Apps and Activity) → Your page → the editor. The warning card
   ("Anyone can see this page. It shares your username with your apps and servers...") shows above the profile
   fields; the first Publish asks to confirm and shows the "Page and message rules" sheet once. Set a photo (pick,
   crop), display name, bio, two links, a theme; turn on **Accept messages**; write a post; Publish (Face ID). Open
   `https://gym.voi.ci/<O>` in the desktop browser: the card, the links, the post and "Send me a message".
2. **Non-admin draft.** On a non-admin device of O (or the webapp signed in as a non-admin device), write a post: it
   shows grayed "Waiting for an admin device to publish". With the iPhone in the foreground (it holds O's bare
   name), the draft reaches it directly; with the iPhone in the background, it waits in the drafts lane and appears
   when the iPhone is next opened. Publish from the iPhone: the page shows the post.
3. **Visitor signs in and writes (V, desktop browser + V's phone).** On `gym.voi.ci/<O>`, Send me a message: a QR
   and a 6-digit code. Scan it with V's phone: the sign-in approval screen shows the same code and O's verified
   display name and photo; Approve (biometric). Write a message, Send.
4. **Delivery, both paths.** With O's iPhone in the foreground the message arrives at once (direct to the phone,
   then forwarded to the mailbox); with every O device in the background it arrives through the mailbox and a
   content-free push ("New message", no text in the notification). O sees "Visitor 4F3A"-style pseudonym, never V's
   username; the thread is under Requests until O replies or taps Accept.
5. **Reply.** O replies from the iPhone; the reply appears in V's browser tab (and, on V's phone, the "You have a
   reply on voi.ci/<O>" row on the next app open). O renames the visitor; the nickname shows on O's Android too.
6. **Links in a thread.** V sends a message with an https link: O's app shows it with its host, and tapping asks
   "Open <host>?" with the full URL before leaving the app. Nothing else in a message is rendered (no images, no
   HTML).
7. **Block and report.** O blocks V's conversation: V's next message is accepted by the site but never reaches O (no
   oracle). O reports a message (Report, optional text): it appears in `npm run voici-abuse -- list` for the gym.
   On the page, "Report this page" from V's browser works too.
8. **Android parity.** Repeat 1 (edit and republish), 4 and 5 on the Android as O, and 3 with the Android as V's
   phone. Note: Android has no visitor-side reply row yet (parity gap in the spec).
9. **Revoke.** On V's phone, Settings → Messages → Websites you're signed in to → revoke `gym.voi.ci`: the browser's
   next send is refused.

Look for: no username of V anywhere on O's devices, no message text in any notification, the warning before the
first publish, every refusal as a sentence (`first-contact-limit` "You can start {0} new conversations a day...",
`unattested-too-new` "New accounts can start conversations from the web after 7 days.").

## 18. A 0.2 Studio hosting the 0.3 appliance (F9 c; manual)

Why manual: a 0.2 Studio is a released GUI app (Mac 0.2.0 DMG; Windows and Linux `studio-v0.1.3` or 0.2.0 from
GitHub Releases) with no automation hook, and the live gym cannot drive a desktop window. What it checks: after
release step 21 overwrites `/downloads/FlagshipVMAppliance-*.json`, a 0.2 Studio that is still installed hosts the
0.3 appliance with its own 0.2 seed and a 0.2 app's recipe (`installerGitRef: "main"`), as
`docs/runbooks/final-deploy.md` "The 0.2 apps, Studios and servers until 0.3 ships" item 6 says (not run on the gym
before this act).

Preconditions:
- The 0.3 VM appliance for this machine's architecture, built by `vm-appliance.yml` from the 0.3 box release: its
  qcow2 (parts joined) whose SHA-256 equals the manifest's `sha256`, and its manifest with `"version": 1` and
  `"installerGitRef": "main"` (the 0.2 Studio refuses any other ref with a "built for a different installer ref"
  message and falls back to the Debian installer, which is a different test).
- A 0.2 app (iOS 1.1 build 5, Android 9, or webapp shell v156) pointed at the gym, which writes
  `installerGitRef: "main"` in its recipes. Note the recipe file you export.
- Before release step 21, a 0.2 Studio reads the manifest from `https://flagshipserver.com/downloads/` (production,
  still 0.2) and has no switch to read it elsewhere, except the local override on Mac and Linux:
  `FLAGSHIP_VM_APPLIANCE_BASE=<the 0.3 qcow2>` and `FLAGSHIP_VM_APPLIANCE_MANIFEST=<its manifest .json>` (Linux
  defaults the manifest to `<base>.json`). The 0.2 Windows Studio has no override: run its half only after step 21,
  against production's published manifest.

Steps (Mac, then Linux; Windows after step 21):
1. Start the 0.2 Studio from a terminal with `FLAGSHIP_CONTROL_HOST=gym.flagshipserver.com` and the two appliance
   variables above (Mac: `FLAGSHIP_CONTROL_HOST=... FLAGSHIP_VM_APPLIANCE_BASE=... FLAGSHIP_VM_APPLIANCE_MANIFEST=...
   open -a "Flagship Studio"`, or run the binary inside the app bundle so the environment reaches it).
2. Open the 0.2 app's recipe, choose Host on this computer (simple mode, not "Force the installer"). The log shows
   `+ verified appliance ... sha256=<the 0.3 sha256>` and the server's disk is created on the prebuilt image.
3. Start it, approve the unlock on the 0.2 phone, and wait for Online.

Expected:
- **Pass**: the box comes up on the 0.3 release (the server page's software line names the 0.3 commit), registers,
  gets its certificates through `.com` (padlock on `https://<server>.<acct>.gym.flagship.services/`), and the 0.2
  app shows it Online. A 0.3 app shows no "Needs an update" pill for it (it sends `boxLevel` 3).
- **Refusal before boot** `refMismatch` / "built for a different installer ref": the manifest's `installerGitRef`
  is not `main`; the appliance was built for the wrong ref (a release bug: step 21 must publish `main`).
- **Hash or format error**: the qcow2 does not match the manifest; rebuild the inputs, not a product finding.
- **Boots but never registers / stays "Waiting for you to unlock"**: the 0.2 seed and the 0.3 first-boot
  specializer disagree (the seed carries `installerGitRef: "main"`, which the 0.3 bootstrap must resolve to its own
  release rather than refuse). That is a product failure: stop, keep the VM, collect its serial console log, and
  report it before release step 21; a 0.2 Studio user would hit it on release day.
- Windows half (after step 21): the same result from the production manifest; a 0.2 Studio that pairs after the
  `.com` redeploy with `STUDIO_PIPE_MIN` on is refused with "This version of Flagship Studio is out of date..." and
  cannot reach this step (record that as the expected end state).

## 18b. The 0.2 store apps against the store-review demo server on 0.3 (F9; owner decision 2026-11-03)

Why: Apple and Google reviewers use the 0.2 store apps (iOS 1.1 build 5, Android versionCode 9) on the demo account
`playstore-test-0725`. That account's server is updated to 0.3 before the mesh is turned on. The replay suite
`tools/compat-0.2/tests/compat02.test.ts` covers the requests the apps send. Only a real phone shows pinning, the
streams and the relay. Never tear the server down, and never order a second update while a review is open.

Before you start:
- Read the box's `/var/flagship/config.json` (debug access) and confirm it holds `adminRootPubHex`, and that it
  equals `.com`'s admin root for the account. With the mesh on, a 0.3 box that pins only its IRK keeps its control
  name but serves no app (`admin-keys-differ` in the relay log). If it is missing, stop and fix this before the
  mesh flip.
- Do not let a 0.3 device on this account set a serving time limit or turn on strict (PQ-only) signing. A 0.2 app
  can neither renew a lease nor send a hybrid signature, so either one stops the demo after the grace period.
- Do not sign the "update required" notice (release step 35) until both stores have approved 0.3. That notice locks
