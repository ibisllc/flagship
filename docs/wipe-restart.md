# Wipe & restart — the v1.1 nuclear option

A user has lost their phone, the recovery passkey is stuck in the
cloud, and they want to start over **at the same username** without
waiting for the 24-hour re-pair grace period.

Wipe & restart is that escape hatch. It is destructive: every pod the
user owns becomes unreachable until that user re-pairs each one with
the new keys. Apps installed on pods stay installed; user data on the
pods stays intact (the pods are still LUKS-encrypted with the same
boot key). But the new phone-trust device is *not* the same identity
as the old one — it cannot impersonate the old device's audit trail,
its paired sessions, or its push subscriptions.

> This is **not for v1**. v1 ships "Replace device" only. Wipe &
> restart lands in v1.1 once the ceremony has been live-exercised and
> the audit trail proven robust.

## Threat model

| Adversary | What wipe-restart denies them |
|---|---|
| Someone who stole the user's phone | The old IRK private key on the phone is now useless against the user's pods — IRK rotation invalidates its signatures. |
| Cloud staff at flagshipserver.com | We never see the new UMK; only the *wrapped* envelope crosses our wire. |
| A peer pod that thought it had a paired-session | Its `device_id` no longer matches any `paired_sessions` row for that username; first sync fails with a recognizable error code (E7 peer-detection). |

Wipe-restart does **not** defend against an adversary who has *both*
the old phone *and* the recovery passkey. That's a separate threat
("compromised root of trust") and is handled by [[recovery-rotated]]
(future doc) — proactive recovery rotation.

## Ceremony, step by step

1. User opens the app on a new device → "I already have an account".
2. WebAuthn-PRF ceremony with the recovery passkey → unwraps the cloud-stored UMK.
3. PostRecoveryChoice shows three options. User picks **"Wipe & restart"**.
4. Scare sheet: "This will disconnect every device on this account and start fresh. Apps stay installed; their data stays on the pods. Continue?"
5. New device generates:
   - Fresh IRK keypair (Secure Enclave / Keystore).
   - Fresh UMK (256 bits, never leaves the device).
   - Fresh recovery WebAuthn passkey (PRF salt re-rolled).
6. New device signs `WipeRestart(oldIrkPub, newIrkPub, newCredentialId, ts)` with the recovered UMK-derived key.
7. POST `/api/users/:u/wipe-restart` with `If-Match: "<etag>"`.
8. Worker atomically (single D1 transaction):
   - Drops the old `recovery_envelopes` row.
   - Inserts the new `recovery_envelopes` row (new credentialID + new wrappedUmk).
   - Swaps `users.irk_pub_hex` (CAS on the old value).
   - Inserts a `wipe-restart` audit row.
9. Worker returns 200 with a fresh ETag.
10. New device fans out a notification to every push subscription on the old account: "your account was reset on another device" (E7).
11. Old paired-sessions and push-tokens are GC'd on next access (lazy cleanup keyed by IRK mismatch).

## Why "atomic" matters

If steps in (8) happened in separate transactions and we crashed
mid-flight, we could end up in a state where the IRK has rotated but
the recovery envelope still points at the old credentialID — the user
could re-derive the *old* UMK on the *new* IRK and re-pair, which is
worse than not doing anything at all.

D1 supports single-statement atomicity natively and a `BEGIN
DEFERRED` transaction wraps the four writes. The handler also takes a
distributed lock keyed by `username` (Cloudflare Workers D1 lock) to
serialize concurrent wipe attempts.

## Rate limit

1 per hour per username. The handler reads the most-recent audit row
with kind `wipe-restart` for that username; if its `postedAt` is
within the last 3600s, returns 429. This is to prevent a stolen
recovery passkey from being used to spam-rotate the account out from
under the user before they can re-pair their other devices.

## Idempotency

The endpoint takes an `idempotencyKey` (a 16-byte random nonce
generated by the client). The Worker dedupes by `(username,
idempotencyKey)` — if the same key arrives twice within 5 minutes, the
second call returns the same response as the first. This is so a
client that gets a timeout on step 7 can safely retry without
double-rotating.

## What stays vs. what goes

| Stays | Goes |
|---|---|
| Pod data (LUKS-encrypted with the boot key, which is preserved) | Old IRK pubkey → invalidated |
| Apps installed on pods | Old paired-sessions → become orphaned |
| Marketplace receipts | Old push tokens → become orphaned |
| `users.username` itself | Old recovery envelope → replaced |
| Audit history (we *prepend* a wipe-restart row, don't truncate) | Old credentialID → no longer in D1 |

## Open questions

- Should we offer a "soft erase" instead — just rotate IRK without
  re-rolling UMK? We considered this and decided no: a stolen
  recovery passkey could still decrypt the *old* UMK, so the IRK
  rotation alone doesn't break the chain. UMK has to rotate too.
- Should the user be able to *cancel* a wipe within the 24-hour
  re-pair grace? Currently the answer is no — wipe-restart bypasses
  the grace deliberately (that's the whole point). But this is worth
  revisiting after the v1.1 live exercise.
