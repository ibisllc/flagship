# Rust early boot (BO01): v1 parity, swap plan, v2 hook

Status: **candidate, not shipped.** `rust/crates/flagship-boot` reproduces the
v1 early-boot unlock exactly. Nothing that ships to a box calls it yet;
`installer/boot-stage.sh`, the Go helper and the initramfs generator are
unchanged. This is step one of IMPLEMENTATION-PLAN.md §7.

## 1. What the crate is

One binary, `flagship-boot`, with two entry points over one implementation of
the wire formats:

| Invocation | Behaviour |
|---|---|
| `flagship-boot <go flags>` | The v1 `flagship-unseal` CLI, byte for byte: same flags (Go `flag` parsing rules, usage block, error text), stdin/stdout, exit codes 0/1, stderr. Drop-in for `/boot/flagship-unseal`. |
| `flagship-boot unlock …` | The whole shell flow (`unlock_via_box_lease`, `unlock_via_relay`, the two-tier dispatch, the one-shot lock) plus the cryptsetup hand-off in one process. |

Modules: `seal` (sealed blob and `SealedSecretResponse`), `canonical`
(`SecretRequest`, box-auth envelope, worker-gate oracle), `identity`
(`/boot/identity.pem`), `goflag`/`gohex`/`gojson` (Go-exact CLI parsing),
`compat` (the v1 CLI), `unlock::{flow,policy,transport,handoff,system}`,
`hardening` (no core dumps, not dumpable on Linux).

Dependencies (exact pins, all at least two weeks old on 2026-10-23, RustCrypto
for all crypto): `ed25519-dalek 3.0.0`, `x25519-dalek 3.0.0`, `sha2 0.11.0`,
`hkdf 0.13.0`, `aes-gcm 0.11.1`, `zeroize 1.9.1`, `base64ct 1.8.3`,
`getrandom 0.4.3`, `serde 1.0.228`, `serde_json 1.0.150`, `ureq 3.4.2`
(rustls 0.23.45 + ring 0.17.14, `webpki-roots 1.0.9`; no OpenSSL), and on
Linux `rustix 1.1.4`. Transitive crates newer than 2026-10-09 were pinned
back in `Cargo.lock` (rustls, rustls-webpki, webpki-roots, ureq-proto, inout,
ctutils, libc, cc, find-msvc-tools, unicode-ident).

### `unlock` options

```
flagship-boot unlock --handoff cryptsetup --device DEV --name NAME [options]
flagship-boot unlock --handoff stdout [options] | cryptsetup luksOpen --key-file - DEV NAME
  --boot-dir DIR (/boot)  --lock-once-marker PATH  --boot-host URL  --mode auto|approve
  --policy compat|strict  --allow-host HOST…  --ca-bundle PEM  --http-timeout-secs 30
  --relay-window-secs N (FLAGSHIP_RELAY_WINDOW_SECS, else 31536000)
  --heartbeat-secs N (FLAGSHIP_RELAY_HEARTBEAT_SECS, else 120)
  --console /dev/console  --cryptsetup PATH  --allow-loopback-http (tests)
exit 0 opened · 1 no key · cryptsetup's own code · 64 usage
```

The retry policy is today's, unchanged: one lease GET (30 s); one announce,
fatal if refused; polls with a fresh header each time, backoff 3, 6, 9, 12,
15 s then 15 s; heartbeat re-announce of the *same* signed request every
120 s; stop at the window. A 200 whose payload is missing or does not open
ends the relay without retry, as today.

Secret handling: the STK seed is read from `identity.pem` inside the process;
the key goes into cryptsetup's stdin (`luksOpen --key-file -`) as raw bytes,
or to stdout only when stdout is not a terminal. Never argv, environment or a
file; seed, X25519 scalar, shared secret, HKDF key and plaintext are in
`Zeroizing` buffers. Core dumps are off and the process is non-dumpable.

Endpoint policy: HTTPS only (plain HTTP only to loopback with
`--allow-loopback-http`), the configured origin must be `scheme://host[:port]`
(no path, query or user info), no redirects followed, no proxy environment,
Mozilla roots baked in (or `--ca-bundle`). Approved hosts: built-in
`boot.flagshipserver.com`, `--allow-host`, and lines of
`/boot/flagship-boot-allowed-hosts`. `compat` (default) uses an unapproved
host from `/boot/flagship-boot-host` with a warning, because enterprise clones
and the gym repoint the worker through that file today; `strict` refuses it,
treats an unknown mode value as `approve`, and ignores `--console` unless
`/boot/flagship-debug-mode` exists.

## 2. Interop evidence

Shared vectors: `packages/protocol/test-vectors/boot-unseal/vectors.json`,
generated by `node --import tsx tools/boot-unseal-vectors.mjs`. Seals use fixed
ephemeral keys and nonces built from the same noble primitives as
`encryption.ts`; the generator refuses to write a case the real protocol
opener disagrees with. They reuse the frozen pinned vector from
`tools/unseal-crosscheck/tests/pinned-vector.json`.

- 19 unseal cases: lease OK, pinned raw, high-bit ephemeral u (ignored per
  RFC 7748), tampered ciphertext/tag/nonce/ephemeral key, lease for another
  box (wrong server), truncated header, sub-tag ciphertext, low-order point;
  response OK, pinned response, replayed (other request nonce), repurposed
  (other purpose), sealed for another box, tampered, overlong context
  length, short payload. Each negative carries the Go helper's error text.
- Signed requests: the `SecretRequest` canonical bytes, signature and the
  exact JSON body; box-auth canonical bytes and the exact `Authorization`
  value for lease GET, request POST and response poll; a request signed by
  another box.
- 9 gate cases: fresh, skew inside the window, expired (+5 min 1 ms), from
  the future, replayed nonce, aimed at another server, wrong route, another
  box's STK, tampered signature.

| Implementation | Test | What it checks |
|---|---|---|
| TS protocol | `packages/protocol/tests/bootUnsealVectors.test.ts` | every unseal case; request bytes, signatures, headers (`signBootAuth` equals the vector header) |
| TS worker gate | `packages/boot-core/tests/bootUnsealVectors.test.ts` | the 9 gate verdicts with the real `gate()` |

| Rust flow | `tests/flow.rs` (in-process worker applying the gate rules) and `tests/cli.rs` (real binary, real HTTP client over loopback, stand-in cryptsetup) | lease, 404/423 fallback, approve never reads a lease, backoff and identical heartbeat bodies, replayed/repurposed/foreign replies refused, empty reply, refused announce, transport errors, window bound, console `manual`, skewed clock refused by the worker, lock-once marker, redirects not followed, key only on cryptsetup's stdin (not argv, env or the log), cryptsetup's exit code, strict policy, usage errors |

The Go side was run with the local Go 1.26.3; box CI builds the helper with
the Go from `go.mod` (1.22). The low-order-point message
(`crypto/ecdh: bad X25519 remote ECDH input: low order point`) is the same
on every Go since 1.20.

Known residual differences in compat mode, none on a path the shell uses:
`unlock` as the first argument is the new subcommand (Go would say
`--identity-priv-hex is required`); JSON syntax-error wording; a JSON member
nested more than 128 deep is refused (serde_json's limit; Go allows 10,000);
a closed stdout exits 1 instead of dying of SIGPIPE; uncommon errno texts.

## 3. Where the helper lives today

Built:

  (`GOARCH` amd64/arm64), unless `--unseal-binary` supplies one; CI
  `.github/workflows/box-artifact.yml` (matrix amd64/arm64, Go from
  `installer/unseal-helper/go.mod`). `installer/unseal-helper/Makefile` is the
  local reproducible build. The README's "build-at-install with golang-go" is
  stale.

Packaged:
- `tools/box-artifact/assemble.ts`: `app/installer/flagship-unseal` (0755) in
  the signed release tarball.
- `installer/install-box-artifact.sh` (embedded as `INSTALL_BOX_ARTIFACT_SH` in
  `packages/flagship-builder/src/boxInstallerScripts.ts`,
  `packages/control-plane/src/boxInstallerScripts.ts` and the bundled
  `preseed-engine.js`): refuses an artifact without an executable
  `installer/flagship-unseal`.
- VM appliance factory, `packages/flagship-builder/src/appliance.ts`: copies it
  to `/usr/local/lib/flagship-appliance/flagship-unseal` (built by
  `vm-appliance.yml`).

Installed and invoked (`packages/flagship-builder/src/userdata.ts`,
`buildLuksBootstrapBlock`, only when `encryptRoot`):
- C1: `install -m 755 … /boot/flagship-unseal` from the appliance copy or the
  release. Baked once, at install.
- C2: initramfs hook `/etc/initramfs-tools/hooks/flagship-unlock`
  (`copy_exec /boot/flagship-unseal /bin/flagship-unseal`, plus openssl, curl,
  xxd, sed, ip, cryptsetup, lvm, NSS modules, the CA bundle, `/boot`
  identity/domain/host/mode) and the premount
  `/etc/initramfs-tools/scripts/local-top/flagship-unlock`, which signs with
  openssl, talks with curl, calls `/bin/flagship-unseal` twice (lease:
  `--sealed-hex`; relay: `--response-json /run/flagship-unseal-input.json`) and
  ends `xxd -r -p /run/unlock-key | cryptsetup luksOpen --key-file -
  <crypto_LUKS dev> <crypttab name>` then `vgchange -ay`. The Wi-Fi path adds
  an init-premount (`buildInitramfsWifiBlock`). `update-initramfs -u` rebuilds.
- `installer/boot-stage.sh` is a reference copy of the same functions; nothing
  on `main` runs it at boot, and it has drifted from the premount (below).

Every Studio and the phone generate this same script: the bundle
`packages/flagship-builder/engine/preseed-engine.js` is embedded by Mac Studio

## 4. What a swap needs

Stage A, drop-in (no script change). Build `flagship-boot` for
`x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` as a static PIE,
`--locked`, `--release` (workspace profile: LTO thin, one codegen unit,
`panic = abort`, stripped), `--remap-path-prefix`, `SOURCE_DATE_EPOCH`, and
prove two builds are byte-identical, as the Go Makefile does. ring needs a C
cross-compiler for musl (musl-gcc, `cross`, or `zig cc`) pinned in CI; the
musl targets must be added to `rust/rust-toolchain.toml`. Hand it to
`tools/box-artifact/build.ts --unseal-binary` and it lands at
`app/installer/flagship-unseal`; the artifact check, appliance copy, C1 and the
hook stay as they are. Size budget: the Go helper is about 2.5 MB; the Rust
release size is not measured yet (debug builds only on this machine). Measure
it in CI and keep it at or under 3 MB.

Stage B, the `unlock` subcommand (generator change, all ports regenerate):
- Premount body: keep net-ensure, resolv-ensure, the lock-once mount, the log
  file and `vgchange`; replace the shell functions and the terminal unlock with
  `/bin/flagship-unseal unlock --boot-dir /boot --lock-once-marker
  "$LOCK_ONCE_FILE" --console /dev/console --handoff cryptsetup --device
  "$ROOT_LUKS_PART" --name "$CRYPT_NAME" 2>&1 | tee -a "$UNLOCK_LOG"` (with
  `pipefail` or a status file, since `tee` hides the exit code), then consume
  the marker on success as today.
- Hook: openssl, curl, xxd, the NSS modules and `nsswitch.conf` are no longer
  needed by the unlock (a static musl binary reads `/etc/resolv.conf` itself;
  roots are baked in, or keep the bundle and pass `--ca-bundle`). Keep sed and
  ip if the Wi-Fi premount still uses them.
- Regenerate `preseed-engine.js` and its Mac and Android copies; update the
  userdata, Swift, Kotlin and C# engine golden tests.
- Existing boxes: `/boot/flagship-unseal` and the initrd are only written at
  install. An endorsed update changes `/opt/flagship/installer/flagship-unseal`
  but not `/boot`, so the swap needs a daemon migration that installs the new
  binary to `/boot`, rewrites the hook and premount, runs `update-initramfs -u`
  and verifies the result, with a recorded rollback.

Rescue path (required before Stage B): keep the Go helper as
`/boot/flagship-unseal.v1` and the shell functions in the premount as a
fallback taken only when the Rust binary cannot run (exit 126/127 or killed by
a signal), not when it refuses a reply. Keep cryptroot's own prompt after the
premount (today's last resort). Prove on both arches: first boot, reboot,
lease, relay, lock-once, a corrupt binary, a removed binary, Wi-Fi, and a
Studio-hosted VM.

## 5. Findings: today's flow against §7

These are recorded, not fixed in the shipping path. Where `flagship-boot
unlock` behaves differently, it says so.

1. **Secrets on argv.** The premount passes the STK seed as
   `--identity-priv-hex` (readable in `/proc/<pid>/cmdline`). The v1 CLI
   contract requires it, so compat mode accepts it; `unlock` reads the PEM
   itself.
2. **Secrets in files.** The key's hex is written to `/run/unlock-key` and
   `/run/unlock-key.hex`; `shred` on tmpfs means nothing. With `set -e`, a
   failed `luksOpen` leaves `/run/unlock-key` in place, and initramfs `/run`
   is moved into the booted system if someone then unlocks by hand. `unlock`
   pipes raw bytes to cryptsetup.
3. **No endpoint policy.** `/boot/flagship-boot-host` is used unvalidated (any
   scheme including `http://`, any host, a path that breaks the signed path);
   curl honours proxy variables; the hook's CA-bundle copy fails silently
   (`|| true`), which would end in a TLS failure and a box that never unlocks.
   `unlock` enforces HTTPS, one origin, no redirects or proxies, an approved
   list (warn in compat, refuse in strict) and baked roots.
4. **No authenticated time.** `issuedAt` comes from the initramfs clock (whole
   seconds under busybox). A clock more than 5 minutes off makes every request
   stale and the box never unlocks (`tests/flow.rs` reproduces it). Neither
   flow corrects from an authenticated source; the TLS-authenticated `Date`
   of a worker reply is a candidate, but needs review before use.
5. **The box checks nothing about the lease or the reply beyond the seal.** It
   ignores the lease's IRK `signature`, `expiresAt` and `maxUses`, and the
   reply's `issuedAt`. A worker that kept a revoked lease can still unlock the
   box: lease freshness and revocation are entirely the worker's (N10). The
   reply is bound to this boot's nonce, so replay across boots fails.
6. **Effectively unbounded relay.** The window is a year with no cap on the
   override. In the premount, `read -t … < /dev/console` returns at once when
   the console is unreadable or at EOF, so the loop polls with no backoff at
   all. `unlock` falls back to sleeping.
7. **Drift between the premount and `boot-stage.sh`.** The premount offers the
   `manual` console fallback in production (boot-stage gates it on
   `/boot/flagship-debug-mode`), exits 0 when `identity.pem` is missing, and
   has no 423 branch (harmless: same fallback). `strict` honours `--console`
   only on a debug burn.
8. **Mode fails open.** Anything in `flagship-boot-unlock-mode` other than
   exactly `approve` (blank, corrupt, `Approve`) selects `auto`, so a damaged
   file downgrades an approve-only box to self-unlock. Compat keeps this with
   a warning; strict asks the phone.
9. **The heartbeat re-sends one `SecretRequest` for up to a year.** The worker
   checks freshness only on the header, not on the body's `issuedAt`.
10. **A lost 200 loses the reply.** The poll consumes the reply; if the answer
    is lost in transit the box polls 404 until the phone approves again.
11. **Parsing by `sed`.** `sealedKey`/`sealed` are pulled with a greedy regex
    over the whole body. `unlock` parses JSON.

## 6. Where v2 plugs in (design sketch only)

Depends on the PQ suite selection (another agent's draft), security N10's TPM
policy review, keyd custody, and Q03. Nothing below is implemented.

- **Request.** Per boot, generate in memory an ephemeral hybrid KEM key pair
  (X25519 plus the approved ML-KEM parameter set), a nonce, and read the boot,
  authority and suspension generations and the policy digest. Sign
  `flagship/boot-session/v2|…` with the STK (and the approved PQ signature once
  the box holds one). On the verified profile, add a TPM quote over a fresh
  phone challenge and the request hash, with the event log, bound to the
  enrolled attestation identity and the measured UKI and boot policy (BO02).
- **Response.** The phone (or the reviewed unattended-release policy)
  encapsulates to the ephemeral keys and seals the disk secret with AEAD whose
  associated data is the transcript hash. It opens once: the ephemeral private
  key is zeroized after the first open, so a captured reply is useless and no
  reusable blob exists. Today's box-sealed lease does not survive in this
  profile; unattended release becomes the TPM policy N10 approves.
- **Downgrade.** A box enrolled in v2 refuses v1 replies and leases unless the
  owner's signed policy selects compatibility (§3.1 opt-out); the selection is
  part of the measured boot configuration, not a file the network can change.
- **Code.** `canonical` gains the v2 transcript; `seal` gains the hybrid open;
  `unlock::flow` gains `via_session_v2` behind the same `Transport`, `Clock`
  and hand-off; the CLI gains `--protocol v1|v2` (default from policy). The
  worker stays ciphertext-only on new `/api/boot/v2/*` routes. Vectors go in
  `test-vectors/boot-session-v2` with the same three-language gate.
