# v1.2 security cascade — account-type model, 2FA, longer grace, new-device quarantine

**Status:** plan; not yet implemented.

**Goal.** Sharpen the real-account threat model into two clean
profiles — *Single-device* (simple, recovery is a slow waiting period)
vs. *Multi-device + 2FA* (complex, recovery is fast but requires an
out-of-Apple second factor) — and add a 14-day quarantine on newly-
admitted devices' ability to kick out others.

This plan is **independent of Plan A** (`sample-user-vps-plan.md`).
Demo accounts route around the security model entirely (no IRK, no
2FA, anyone-can-join); the changes here affect only real accounts.

---

## Motivation

v1.1 shipped Replace device / Wipe & restart / self-revoke / peer-reset
detection / audit log. The remaining defenses against an
iCloud-Keychain-compromise-then-takeover are:

1. **24h grace is too short.** A user on vacation, asleep, or just not
   looking at their phone for a day can miss the alert window.
2. **No 2FA option.** Apple's iCloud Keychain + device passcode is the
   only barrier between an attacker and your account. For users who
   want a stronger guarantee, there's no path.
3. **No quarantine on newly-admitted devices.** Once a device is in,
   it can immediately revoke any other device. A successful takeover
   can lock the legitimate owner out instantly.

This cascade addresses all three.

## Migration of existing accounts

- All accounts in D1 today are implicitly **single-device** (no 2FA
  enrolled, no other devices on the IRK). Default the new
  `account_type` column to `'single'`.
- Existing pending re-pair (J.3) rows in flight when the migration
  lands continue with their original **24h grace** — don't move the
  goalposts mid-flow.
- New re-pair attempts that land after the migration get **7-day
  grace** if the target account is single-device.
- The 14-day quarantine field defaults to `0` (already-trusted) for
  all pre-existing devices in the trusted-devices set. New devices
  admitted after the migration get a non-zero quarantine.

No forced 2FA enrollment for existing users. Surface a prominent
banner offering enrollment; otherwise opt-in only.

## Phase 1 — schema + account-type concept

Migration `packages/storage/migrations/0028_account_type.sql`:

```sql
ALTER TABLE users ADD COLUMN account_type TEXT NOT NULL DEFAULT 'single';
ALTER TABLE users ADD COLUMN totp_secret_encrypted TEXT;
ALTER TABLE users ADD COLUMN recovery_codes_hashes_json TEXT;
ALTER TABLE users ADD COLUMN totp_enrolled_at INTEGER;

-- pending_re_pairs already exists from v1.1; we add a grace-end column
-- and a 2FA-required flag.
ALTER TABLE pending_re_pairs ADD COLUMN grace_seconds INTEGER NOT NULL DEFAULT 86400;
ALTER TABLE pending_re_pairs ADD COLUMN totp_required INTEGER NOT NULL DEFAULT 0;
ALTER TABLE pending_re_pairs ADD COLUMN totp_proof_consumed INTEGER NOT NULL DEFAULT 0;

-- paired_sessions get a quarantine-until field; 0 means already-trusted.
ALTER TABLE paired_sessions ADD COLUMN quarantine_until INTEGER NOT NULL DEFAULT 0;

CREATE INDEX idx_paired_sessions_quarantine ON paired_sessions(quarantine_until);
```

`recovery_codes_hashes_json` is JSON array of `argon2id` hashes — each
unique, each single-use, each consumed atomically when redeemed.

`totp_secret_encrypted` is encrypted at rest with a Worker-side KEK
derived from `FLAGSHIP_TOTP_KEK` (new secret).

Acceptance: migration applied to `flagship-state`; schema in-memory
tests cover the new columns; existing tests stay green.

## Phase 2 — 7-day single-device grace + 14-day quarantine

### Re-pair J.3 grace extension

`handleRePair` in `apps/com/src/`:

- When `account_type === 'single'`: set grace to **7 days** (604_800
  seconds) instead of 24h. The pending row's `grace_seconds` field
  captures it explicitly so concurrent migrations remain bisectable.
- When `account_type === 'multi'`: set grace to **24h** AND set
  `totp_required = 1`. The new IRK's `RePairInitiate` must include a
  valid TOTP proof OR a single-use recovery-code proof; otherwise
  reject with 401 before even starting the grace timer.

### Push notifications during grace

Existing v1.1 push-on-IRK-rotation logic fires through `pushBridge`.
Extend so that during a single-device grace, push goes out:
- T+0  (immediately)
- T+1d
- T+3d
- T+6d (one-day warning)
- T+7d (window closing in 1h)

Each push surfaces the recovery as **informational**, not as an
"object" affordance. The pre-W1 design exposed an objection UI on
existing devices that could sign a `RePairObject` with the OLD IRK.
**That was a security mistake** — a device-thief is in possession of
the OLD IRK and could veto the legitimate owner's recovery from a
fresh device.

### Recovery threat model (W1, post-2026-05-20 revision)

Credentials are the SOLE gate for recovery. Whoever holds
`(admin iCloud + admin 2FA)` has, by definition, proven they are the
admin. Existing devices cannot block — they hold an IRK the credential-
holder can rotate, not a meta-power that supersedes credentials.

Once recovery is initiated:

1. The 7-day (or 24h with TOTP) grace IS a soft-migrate window, NOT
   a veto window. Push alerts go to every paired device of the OLD
   IRK to surface the recovery — "if not you, your credentials are
   compromised; the takeover lands at T+grace; use this time to
   format pods or exfil data if you must."
2. The takeover IS INEVITABLE at T+grace. No device-side action
   can stop it.
3. The lock (`pending_re_pairs.username` PK) is held while the
   grace runs — no two concurrent admin recoveries can race.
4. The `/api/users/:u/re-pair/object` endpoint exists only as a
   self-cancel UNDO for the recoverer themselves: the NEW IRK
   signs ("I started this recovery, now I want to abort it").
   The OLD-IRK-signed veto path is REMOVED.

Why credentials-are-the-gate is honest: device-theft and credential-
theft are correlated. A laptop thief usually also acquires the iCloud
keychain via the saved password manager. Pretending the device
provides a separate proof of identity is wishful — and giving the
device meta-power-over-credentials means giving the thief that power.

### Recovery wipe policy (W6, 2026-05-20)

Pre-W6, a successful recovery rotated the cloud root IRK and every
DeviceCapabilityGrant signed by the OLD IRK silently failed signature
verification under the new root. Family / non-admin devices LOST
access through no fault of their own — and `requireDeviceScope`'s
defense-in-depth re-verify (see `packages/control-plane/src/
deviceCapabilityGrants.ts`) refuses to trust a row whose signature
doesn't bind to the cloud's current root.

W6 makes this a **per-cloud policy** chosen at cloud creation
(`usernames.recovery_wipe_policy`, migration 0032):

- **`strict`** (corporate opt-in) — every active grant is revoked at
  swap time. The new admin must re-mint grants for every device that
  needs continued access. The forced re-onboarding is the point: IT
  proves who's still a member after a recovery. The `/complete`
  response surfaces `wipedGrantIds` so the recovering device's UI can
  render "All other devices need to re-onboard."

- **`graceful`** (default — family/personal) — the `/complete` RPC
  body carries `refreshedGrants` signed by the NEW IRK; the handler
  validates each refreshed grant under the new IRK pub (which is
  what the swap is about to install), confirms each `devicePubKey`
  matches an existing active grant for the user, refuses any scope
  inflation (refreshed scopes MUST be a SUBSET of the old grant's
  scopes — never a superset), and atomically swaps the old grants
  for the new. Family devices keep working with the same scopes.

The Worker CANNOT do the re-sign server-side: the new IRK's private
key lives ONLY on the recovering device. So `graceful` mode requires
the recovering device to sign the refreshed grants during the
ceremony and POST them in the `/complete` body. Concretely, the
phone-UI flow for a graceful recovery is:

1. Phone fetches existing active grants from `/api/users/:u/device-
   grants` BEFORE calling `/complete`.
2. UI surfaces "Keep <N> family devices working" with the per-device
   list (locally decrypted profile name + scopes).
3. User taps "Refresh all" (or per-device pick); phone signs a fresh
   `DeviceCapabilityGrant` (new `grantId`, same `(deviceId,
   devicePubKey, scopes, expiresAt)`) under the new IRK for each.
4. Phone calls `/complete` with `{ refreshedGrants: [...] }`.
5. Worker validates + persists in one transaction. Response surfaces
   `refreshedGrantIds` so the UI can render "Kept N devices working."

Strict policy IGNORES any `refreshedGrants` in the body — the wipe
is the point, and silently dropping the re-signs is fine (the
recovering device will see the wipe in the response and prompt the
user to re-onboard family devices via the normal mint flow).

Validation failures on `refreshedGrants` return BEFORE the IRK swap
so a partial failure leaves the cloud in a clean (pre-swap) state —
the recovering device sees a clear 4xx, fixes the body, and retries.

### 14-day quarantine on revoke-others power

When a new IRK takes over OR a new paired-session is added:
- The corresponding `paired_sessions.quarantine_until` is set to
  `now + 14 days`.
- ALL endpoints that revoke other devices (`/api/users/:u/devices/
  :id/disconnect`, `/api/re-pair`) check the calling session's
  quarantine and reject if `quarantine_until > now`.
- The error is a clean 403 `{ reason: "quarantine", until: <ts> }`
  that the UI surfaces sensibly ("Wait until <date> to remove other
  devices from this new device. Or use a device you've had for
  longer.").
- The legitimate owner's existing devices have `quarantine_until = 0`
  and can revoke the quarantined new device immediately.

This is the "wait, don't let the new device lock me out" defense.

Acceptance: protocol envelopes extended with `gracePeriodHint` etc.;
Worker handler tests cover all four (single+TOTP, multi+TOTP, single+
no-TOTP, multi+no-TOTP) and quarantine enforcement.

## Phase 3 — TOTP enrollment + verification

### Endpoints

| Method | Path | Auth | Body | Effect |
|---|---|---|---|---|
| POST | `/api/users/:u/totp/enroll-begin` | IRK-signed | `{}` | Generates TOTP secret, stores encrypted, returns `{ secret, otpauthUrl, qrPngBase64 }` |
| POST | `/api/users/:u/totp/enroll-confirm` | IRK-signed + sample TOTP | `{ code }` | Verifies code; on success sets `totp_enrolled_at`; flips `account_type` from `single` → `multi`; returns 10 recovery codes (one-time view) |
| POST | `/api/users/:u/totp/verify` | n/a | `{ code }` | Used as proof embedded in `RePairInitiate` for multi-device recovery |
| POST | `/api/users/:u/totp/disable` | IRK + TOTP code | `{ code }` | Drops TOTP secret; flips `account_type` back to `single` (with a 7-day grace re-pair lockdown). Only allowed if no other paired-sessions exist (single-device path requires single-device state). |

### TOTP library choice

**`otpauth`** (npm) — pure TypeScript, RFC 6238 compliant, 5kB.
Already in some workspaces. Vetting note in the commit body.

### Recovery codes

- 10 codes, 10 characters each, base32-encoded
- Argon2id-hashed in D1 (`m=64M, t=3, p=1`)
- Single-use; consumption is atomic via `UPDATE ... WHERE
  hash=? AND consumed=0`
- Replenishment requires `enroll-confirm` again (re-prints fresh codes)

### `RePairInitiate.totpProof` field

Protocol envelope extension:

```ts
export interface RePairInitiate {
  username: string;
  newIrkPub: Bytes;
  oldIrkPub: Bytes;
  issuedAt: number;
  /** OPTIONAL — required if target account_type === 'multi' */
  totpProof?: {
    code: string;          // 6-digit TOTP OR 10-char recovery code
    method: "totp" | "recovery";
  };
}
```

The proof is **NOT** in the canonical-bytes signed envelope (since
codes are short-lived and shouldn't be persisted). The Worker validates
the proof against the stored TOTP secret + the recovery-codes table
synchronously at the same time it validates the IRK signature.

Acceptance: TOTP enrollment flow tested end-to-end; replay attacks
prevented (consumed codes can't reuse); rate-limit verify endpoint to
5 attempts per 15 min per username.

## Phase 4 — mobile UI

### iOS / Android / Webapp parallel surfaces

**Settings → Multi-device + 2FA**:
1. Toggle "Enable multi-device + 2FA"
2. Show QR code + manual key entry
3. "Scan with your authenticator app (1Password / Google Authenticator / Authy / …)"
4. Enter a sample 6-digit code → verify → switch from `single` to `multi`
5. Show 10 recovery codes; "Print these. Store them somewhere safe.
   You'll need one of them if your authenticator is ever lost."
6. Confirm: "Yes, I've saved them"

**Settings → Account type badge**:
- "Single-device account" (with explainer about 7-day recovery)
- "Multi-device + 2FA" (with explainer about 24h grace + TOTP)

**Re-pair recovery flow**:
- After WebAuthn-PRF passkey unwraps wrapped-UMK successfully:
  - If account is single-device: show "Recovering your account.
    Existing devices will be alerted for 7 days. Once 7 days pass with
    no objection, your new device will take over."
  - If account is multi-device + 2FA: show TOTP prompt → on success,
    24h grace begins.

**Add device** (multi-device only):
- Initiator device → "Approve new device" → existing device taps
  approve → new device gets IRK shard
- New device shows "You're approved. Note: for the next 14 days, you
  can't remove other devices from this account. This is a safety
  measure."

**Quarantine indicator**:
- On Settings → Trusted devices, devices in quarantine get a clock
  icon + tooltip
- The "Remove" / "Replace" actions are greyed out on a quarantined
  device until its quarantine expires
- If you try to remove from a quarantined device, the toast says
  "This device is in quarantine until <date>. Use another device."

Acceptance: iOS + Android + Webapp all show the matrix-correct
state for each account type; conformance tests verify the UI branches
on the response shape.

## Phase 5 — audit + push enhancements

### Audit log

Extend `audit_events` with:
- `account_type_at_event` (snapshotted, since type can change)
- `quarantine_until` (when applicable, e.g., on `device-admitted`)
- `recovery_method` (`totp`, `recovery-code`, `none`)

New event kinds:
- `totp-enrolled`
- `totp-disabled`
- `account-type-changed-single-to-multi`
- `account-type-changed-multi-to-single`
- `recovery-code-consumed` (single-use, useful for auditing)
- `quarantine-blocked-revoke` (someone tried to revoke from a
  quarantined session)

### Push notifications on attempted re-pairs

Every `RePairInitiate` fires push to ALL currently-trusted devices
(across iOS / Android / Webapp). Body: "A new device is trying to take
over your account. Tap to review or object." Deep-link goes to the
audit-and-object UI.

Re-pairs without trusted devices (the "lost everything" case) skip
push but log every step in the audit.

Failed TOTP attempts above threshold (5 in 15 min) fire alerts:
"Several incorrect 2FA codes for your account. If this isn't you,
your authenticator might be compromised — re-enroll or contact
support."

Acceptance: push fans out correctly; tests cover deep-link payloads;
rate-limited audit-event-emission survives a stampede.

## Threat-model claims after this cascade

| Adversary capability | Defeated by |
|---|---|
| Just has your Apple ID password | Apple HSMs + device-passcode requirement |
| Apple ID + 2nd unlocked device passcode (e.g., shoulder-surfed) | **7-day grace** (single-device) OR **TOTP** (multi-device); peer-reset; audit |
| Apple ID + permanent stolen phone (single-device account) | 7-day grace; user reports via another channel within 7d |
| Apple ID + permanent stolen phone (multi-device + 2FA account) | TOTP secret is on user's authenticator app, not on the stolen phone |
| Stolen iCloud-synced authenticator app (e.g., 1Password) | User SHOULD avoid this — recommend non-iCloud-synced TOTP for the strongest model. Recovery codes are the fallback. |
| Apple ID + stolen phone + access to user's password manager containing TOTP | Recovery codes if user has them somewhere else; ultimately the user has chosen "all eggs in one basket" and accepts the residual |
| Newly-admitted-device (legitimately or not) trying to instantly kick out others | **14-day quarantine** on revoke-others power |

The "Apple ID + stolen phone + access to TOTP" path is the last remaining
residual. Hardening v2 directions:

- **Threshold IRK** — require N-of-M existing devices to bless a new
  one. Adding the third device to a 2-device account already needs
  approval from one of the existing two; threshold IRK would require
  both.
- **Hardware attestation pinning** — the IRK must come from real Apple
  / Google / vendor-attested hardware authenticator.
- **NFC tap from a paired wearable as 2nd factor** — instead of TOTP,
  the wearable signs a challenge. Strong UX, requires implementation.
- **Recovery contacts** — designate a trusted contact whose approval is
  required for cloud-only recovery.
- **Per-device permissions (corporate-deployment angle)** — grant
  per-device capability scopes signed under the user's IRK, so an admin
  can say: this tablet browses but can't install foreign apps; that
  laptop installs + vibe-codes; that phone is read-only; and only
  certain devices may add NEW devices (defeats a stolen-device-piles-on
  attack).

  **NOT via addressing.** An earlier draft proposed a second URL level,
  `<user>.<device-label>` → `USERKEYHASH.DEVICEKEYHASH`, with a
  human-meaningful label set at pairing. That is dead: devices carry an
  immutable random account-scoped `deviceId`, are never named in
  canonical bytes or on the wire, and are not publicly addressable at
  all. Scopes attach to the `deviceId` via `DeviceCapabilityGrant`;
  any name a device shows is an encrypted profile decrypted locally.

  The capability grants would be a new envelope on top of the
  existing IRK signature chain (similar to ServiceGrant in
  `packages/protocol/src/auth.ts` but device-scoped). A device's
  ALLOWED operations are checked at the daemon + the Worker + the
  mobile UI before action.

  Defers neatly to v2 because:
  - The single-device default uses USERKEYHASH.* and is unchanged.
  - Multi-device + 2FA accounts continue to work via today's IRK
    sharing.
  - Adding per-device scopes is a strict superset that doesn't break
    existing deployments.

  Implementation sketch (NOT for v1.2):
  - Each device carries an immutable random account-scoped `deviceId`;
    `paired_sessions` rows carry no human label.
  - New `DeviceCapabilityGrant` envelope: signed by the IRK, lists
    `deviceId` + allowed scopes (`install-app`, `vibe-code`,
    `add-device`, `browse`).
  - Worker + daemon read the capability set on every privileged
    operation. Mobile UI surfaces the limits explicitly so a
    restricted device shows e.g. "this device cannot install apps —
    use your work laptop" (the device's name there is decrypted
    locally from its profile, never read from the wire).

  Threat model add: a stolen device whose grant is restrictive cannot
  exfiltrate via apps-install (they're disabled at the daemon).

None of those are blockers for v1.2; they're v2+ work.

## Acceptance for v1.2 launch

- `account_type` column exists; existing users `'single'`; can opt
  into `'multi'` via TOTP enrollment.
- Cloud recovery on a single-device account requires 7 days of
  waiting with audited push alerts.
- Cloud recovery on a multi-device account requires a TOTP proof or
  recovery code AND a 24h grace.
- New devices admitted to a multi-device account cannot revoke other
  devices for 14 days.
- Audit log captures every account-type transition + every TOTP
  enrollment / disable / verify-failure.
- Mobile UI surfaces account-type, enrollment flow, recovery codes,
  quarantine indicators.
- Full `tsc -b` clean; full vitest green; iOS XCTest green; Android
  Gradle test green.
